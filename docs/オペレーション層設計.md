## 0. 核心（1段落で）

TexoS は要求（pull）駆動であり、現状リクエストを発行できるのは人間だけ（▶クリック）。
**オペレーション層＝人間の操作（つなぐ・切る・補充・保留・実行）の記述**を、データ層の上に
重ねる第2のグラフとして形式化する。データ矢印は永久にデータだけを運び、制御（発行・通過・
経路選択）はすべてオペレーション層が担う。モジュール（部分グラフ）＝畳み込まれた名詞、
オペレーション層＝それを駆動する動詞。

## 1. 決定事項（2026-07-02 ユーザー合意）

1. **制御の分離**: exit code 分岐を含む制御はオペレーション層へ一本化。データ矢印
   （relations kind='flow'）は**後方互換のままデータ専用**（多くの人間の思考はここ止まりで
   完結してよい＝オペ層なしでも従来どおり使える）。旧案「flow 矢印に成功時/失敗時属性」は廃止
   （v1.4.10 §4.3 の拡張点アンカーは「オペ層との接続点」として再解釈）。
2. **権能の限定**: オペレーション層は**リクエストの発行・通過・経路選択のみ**。
   カードの追加・ありえない接続・物理的な差し替えは**できない**（構造は書き換えない）。
   「カードの差し替え」の実体は**スイッチャ/セレクタによる選択**——分岐先カードが2枚以上ある、
   入力に複数枚あってどれを選ぶか——であり、選択肢は構築時に人間（＋AI支援）が可視に用意する。
   ＝暴走原因の大半はコンストラクション時に発見できる構造。
3. **表現**: データ上はカードと同様の持ち方でよい（kind='op' 系＋spec JSON＋relations
   kind='op' の方向。付箋統一で確立した「kind派生＋センチネル実身＋spec列」パターンの適用候補）。
   ただし**ビジュアルは明確に非カード**——ノード形かフロー形かは要デザイン。人間はビジュアルで
   高速に思考するため、カードのコンストラクションとオペレーションのコンストラクションが
   一目で区別できることが必須。構築時は見え隠れ（表示トグル）、運用時も ▶/■ ボタンは残す。
4. **状態語彙**: カードは「オペ層から読み取れるシグナル」を用意する（シグナル色・実体の有無・
   mtime・exit code・前回実行結果…の形式化）。人間が目で見ているものの列挙＝閉じた語彙にする。
5. **段階分け**: v1.5＝発行・通過・選択（グラフを読むが書き換えない）。構築の自律化
   （カード構成構築→オペ層構築→運用の順で AI へ委任）は V2.0 のリクエスタ/アーキテクト/
   コンストラクタ＋作用クラスの門とセット。
6. **AI支援の位置**: オペレーション層の**コンストラクション時に AI 支援**が入る——これが
   MCP 開放の意義（ライブラリを丸ごとツール化するのではなく、**受容体の粒度**で外部 AI が
   リクエストを差す・構築を支援する。細部は V2.0 で設計）。
7. **発振（ループ）対策**: while(true) 型の再発火（自己出力をウォッチャが拾う等）への3段構え——
   ①**コンストラクション時の検出支援**（AI によるグラフ検査）②**運用前評価コマンド**
   （静的チェック: 循環・自己出力監視・ヒューズ未設定の警告。dry-run 系）③実行時の
   ヒューズ（並行上限）＋中央 kill（凍結仕様＝ジョブレジストリが担う）。
   **メタ認知カードのパターン**（AI カードに事象判定をさせ、後段 AI がループの意味を判断する
   組み方＝ユーザー実証済み）を推奨イディオムとしてチップス化する。

## 2. オペレーションノードの語彙（原案メモより・ジョブレジストリ対応）

| ノード | 役割 | 既存部品との対応 |
|---|---|---|
| トリガ | リクエスト発行（スタートボタン） | ▶クリックの置換 |
| タイマ | 定期/時限のリクエスト発行 | （旧タイマーカード案を吸収） |
| データ/ファイル/フォルダウォッチャ | 状態変化→リクエスト発行 | OSイベント→反応的 pull |
| ゲート | リクエストの通過制御・保留 | ジョブの Queued 状態（凍結仕様(B)） |
| リクエストスイッチャ | 条件（exit code・状態語彙）で経路選択 | 旧「exit code 分岐」の移住先 |
| セレクタ | 複数 IN から選ぶ | 多入力の選択 |
| 受容体 receptor | リクエストを受け付ける口 | モジュール OUT（pull の入口）・将来の MCP 口 |
| 要求体 requester | リクエストを発行する主体 | 上記発行系の総称・V2.0 自律の前身 |

**リクエスト＝ジョブの前身**。オペ層は「ジョブを生成・保留・選別する層」であり、
実装基盤は凍結仕様 (B) ジョブレジストリ（実装順: (B) が先、で変わらず）。

## 5. 改訂（2026-07-04 ディスカッション合意）— ノードカード方式への収斂

原案: ユーザー提案「オペレータカード（ノードカード）＝AIカードの拡張として、判断が必要な
カードの間に挟む」。検討の結果、§1 の T0 合意と対立せず**収斂**することを確認した。
以下は §1〜§3 への上書き・具体化。

### 5.1 決定の更新

1. **レーン分離は「層の分離」から「エッジ/ポートの型の分離」へ縮退**。
   独立した隠しレイヤーは作らない。データの矢印とリクエストの矢印（破線・別色・表示トグル）
   の2種のエッジが**両方ともカードに付く**。§1-3 の「ビジュアルは非カード」は撤回し、
   オペレータ（統合系）は**普通のカード**として表現する。
2. **セレクタ/統合判定はデータレーンの住人**（オペレータカード）。pull＝遅延評価では
   「どの上流を評価するか」の選択がそのまま制御であり、eval_filter の再帰 pull に
   無改造で乗る。選ばれなかった枝は実行すらされない。
3. **スイッチャは廃止（IN側条件に吸収）**。§2 の「リクエストスイッチャ」ノードは不要。
   pull では選択は常に「引く側の IN」に置ける: 成功時下流と失敗時下流が両方リクエストを
   発行し、条件（例「exit code 0 のときだけ受け取る」）は**下流のINポートの属性**として書く。
   カードの OUT は現行どおり**シングル**（産出物1ファイル）のまま＝ T2 ポート工事は
   IN 側だけで済む（`{inN}` 位置指定が足場）。
4. **no-data の一級化**（実装の急所）: 「枝が取られなかった/材料がなかった」を表す結果を
   eval_filter に導入する。エラーでも空ファイル実身でもない。カードごとに2つの振る舞い:
   - **伝搬型**（既定）: 必須入力が no-data なら自分も no-data（NULL伝搬）
   - **吸収型**（統合系）: 欠けは欠けたまま、返ってきたものだけで統合する
   spec にフラグとして持たせる。
5. **実行単位メモ化**: 複数下流が同じカードを pull しても二重評価しない（副作用のある
   上流＝録音/AI 呼び出しで実バグになる）。ジョブスコープのメモ表＝ジョブレジストリ(B)と同居。
6. **自動発行（1.5 に含める）**: タイマ・ウォッチャ（ファイル到着/カメラ変化/音声検知…
   IoT 機器と同型）は「事象を検知して**下流の成果に代理でリクエストを発行する**」主体。
   pull の純粋形では「事象が起きたから流れる」のではなく「検知した誰かが成果を要求する」。
   この発行点だけはカードの IN で表現できない＝リクエストレーンが小さく残る根拠。
7. **作用カードの受容体 IN**: 手動起動カードに「指令待ちの IN」を持たせる案は
   §2 の受容体そのもの。シンクの下流には誰もいない（pull では誰も引きに来ない）ため
   リクエスト注入口が必須、という再確認。遠隔起動の解禁は**ジョブレジストリ(B)が先**。

### 5.2 判定エンジンの段階（1.5/2.0 の精密化）

「動的」は一枚岩ではなく2段階に分離する。器（カードとグラフ）は全段階で共通、
判定エンジンだけが差し替わる:

| | v1.5 | V2.0 前期 | V2.0 後期 |
|---|---|---|---|
| 統合系の判定 | 決定的ルール（状態語彙への条件表） | AI判定（**描かれた候補の中から**選ぶ。グラフ不変） | AIが構築ごと組み替え（カタログから処理系を実体化） |
| 安全根拠 | 再現可能・構築時に全経路可視 | 構造を書き換えない＝ T0 §1-2 の権能内 | リクエスタ/アーキテクト/コンストラクタ＋作用クラスの門 |

実行時 AI 判定を 1.5 に入れない理由: 再現性（同入力で別経路はデバッグ不能）・速度
（ジャンクション毎に数秒）・安全順序（ヒューズ/中央kill より先に自律作用を入れない）。

## 5.4 確定事項（2026-07-05 ディスカッション合意）— §5.3 アジェンダの決着

### 5.4.1 ノードカードの確定リスト

**グループA: データレーンの住人**（pull 評価に乗る・フィルタカードの仲間）

| カード | 確定内容 |
|---|---|
| **セレクタ** | 新 builtin:"select"。**IN 接続順の first-match**（最初に「条件を満たす有データ」を返した枝を採用）。本質は「no-data 吸収＋first-match」 |
| **統合系** | **新カードは立てない**。既存の集約実行（`{in*}`）＋吸収フラグ（`nodata:"absorb"`）で表現。不便に感じたら改修 |

exit code 分岐の組み方（推奨イディオム）: 成功枝・失敗枝の両下流が同じ上流を pull し
（メモ化で実行は1回）、各矢印の when 条件で片方が no-data 化、終端セレクタが有データ側を採用。
選ばれなかった枝の下流は実行すらされない（§5.1-2 の成立形）。

**グループB: リクエスト発行系**（データを産まない・kind='op' カード）

- **トリガ**（設置型▶・複数対象への一括発行を兼ねる）／**タイマ**（`{op:"timer", every/at}`）／
  **ウォッチャ**（`{op:"watch", path, events, debounce}`）。
- データモデルは付箋統一で確立したパターン（kind 派生＋センチネル実身＋spec 列）＝ **kind='op'**。
- リクエスト矢印 = **relations kind='req'**（破線・別色・表示トグル）。
- 発火の意味論 = §5.1-6 どおり「検知した者が対象カードを終端に run_flow を**代理発行**」
  （凍結仕様(B) ジョブレジストリが前提）。

**グループC: カードにしないもの**

- **受容体** = 作用/シンクカードの **IN 属性**（req 矢印の到達点。届いたらそのカードを終端に run_flow）。
- **ゲート** = ジョブレジストリの Queued 状態（ジョブパネルの保留/再開）。
  ＋ §5.4.2 の `carry:"none"` がエッジ属性版ゲートを兼ねる。
- **スイッチャ** = 廃止済み（§5.1-3。IN 条件へ吸収）。

### 5.4.2 IN 側の改修 = relations.attrs 1本の migration に集約

relations に **attrs JSON 列**を追加（**NULL = 無条件・接続順 = 完全後方互換**）。
条件・運搬・順序を全部ここへ（flow_run.rs の §4.3 拡張点アンカーの場所）:

```
attrs: {
  when:  "success" | "failure" | "always"(既定),  // 通過条件。v1.5 は閉じた語彙（exit: [codes] は必要時に追加）
  carry: "input" | "stderr" | "none",             // 失敗枝が運ぶもの。成功枝は従来どおり上流出力＝指定不要
  port:  n                                        // IN 順の明示。なし = created_at 接続順
}
```

- **失敗の格下げ**: 条件付き矢印が付いた上流の失敗は、フロー全体のエラーではなく
  **経路選択の情報**になる（条件なし矢印は従来どおりエラー伝搬＝後方互換）。
- **carry:"none" = データを捨てて経路情報だけ通す**（信号のみ）。捨てる/採用するの両方が
  選択式で可能（ユーザー確認済み）。エッジ属性版ゲートだが、権能の限定（§1-2）の枠内。
- **no-data の一級化**: eval_filter の結果に NoData を追加。spec に
  `nodata: "propagate"(既定) | "absorb"`（§5.1-4 の実装形）。
- **実行単位メモ化**: ジョブスコープの `HashMap<card_id, NodeResult>`（§5.1-5。(B)と同居）。
- **`{inN}`・OUT シングルは無改修**（§5.1-3 維持＝工事は IN 側だけ）。

### 5.4.3 IN 順のビジュアル = 入りポート方式（案①採用）

3案（①カード左端に入りポート縦並び／②キャンバス位置関係で優先順位／③前置インオペレータ
カード）から **①を採用**（2026-07-05 ユーザー決定）。

- **INポートは接続前は存在しない**。フロー矢印をドラッグインして初めて現れ、追加のたびに
  **均等に広がっていく**。非常に多くなったら上下のエッジへ回り込む——ラインのクロスが
  無ければ順番は読み取れる。
- 表示は「**順番に意味があるカード**」だけ（flow 入力2本以上 かつ `{inN}` 位置指定 or セレクタ）。
  単入力・`{in*}` 集約の見た目は無傷（キャンバスを騒がせない）。
- 並べ替えは2段階: **第1段** = 設定ダイアログの入力一覧＋上下ボタン（attrs.port を書く・フロントのみ）
  → **第2段** = 矢印端点のポート間ドラッグ（直接操作）。第1段だけ先に出して様子を見る。
- **③は独立部品として作らない**: 「前置で順を決めて送るカード」の正体はセレクタ自身であり重複。
  ③の美点（省くと接続順＝下位互換）は **attrs=NULL のフォールバック**が担う。
- **②は意味論には使わない**: キャンバス位置は思考の空間であり、配置整理で優先順位が黙って
  変わる事故を避ける。ただし「**AI が空間配置を手がかり（hint）として読む**」センシングは
  **V2.0 MCP 受容体の論点**として記録（意味でなく手がかりなら安全）。

### 5.4.4 実装順（確認済み・凍結仕様と整合）

**(B) ジョブレジストリ → (C) 資源セマフォ＋背景ジョブパネル → オペ層 Phase1
（relations.attrs＋no-data＋セレクタ＋メモ化）→ 発行系（トリガ/タイマ/ウォッチャ＝kind='op'＋kind='req'）**。
順に固めて進める（2026-07-05 ユーザー合意）。実装指示 = `docs/v1.5_実装指示書.md`。

## 6. 状態語彙と運用前評価（2026-07-05 ディスカッション合意・設計完了の最終節）

### 6.1 状態語彙（閉じた語彙・T0 §1-4 の形式化）

**読む主体で2層に分かれる**（混同しない）:
- **ジョブ内評価結果**（揮発）: `when` 条件が読む「このジョブでの上流評価の結果」
  （exit・data有無）。ジョブと共に消える（§5.4.2 で確定済み）。
- **カード状態語彙**（永続/セッション）: ウォッチャ・運用前評価・将来の AI 判定（メタ認知
  カード）が読む。以下の閉じた表:

| 語 | 値 | 出どころ |
|---|---|---|
| kind | real / virtual / note / filter / launcher / op / shape | virtual_bodies.kind＋committed |
| exists | ok / lost_window / lost_real（赤） | 既存 lost 判定（"cas"/"none"/"real"） |
| mime / ext | 文字列 | real_bodies |
| size | バイト（0=空） | 実体 |
| mtime / age | 時刻／経過 | 実体 |
| last_run | { at, exit, ok, nodata, skipped, **message** } | **要形式化**: 現状の memo テキストログ→構造化保存へ（WS-P1 の migration に同乗） |
| running | bool | ジョブ台帳（WS-B） |
| fresh | bool（緑シグナル＝今セッションで生成・変更） | 既存の緑シグナル機構 |

**エラーメッセージ（last_run.message）は一級の語彙**（2026-07-05 ユーザー・重要）:
意味レベルの不整合——画像生成プロンプトに日本語・MD 想定の口に docx 等——は**自動検出しない**
（オートマチックには困難）。対応は ①**動かして出るエラーメッセージの充実**（最重要の手がかり。
保存・可読・後段接続を保証）②ライブラリ配布・サンプルプロジェクト・コメント文化
（共有とモジュール §10.4）。message は §1-7 の**メタ認知カード**（AI にエラーを判定させる
イディオム）の入力になる——語彙に含める理由はこれ。

### 6.2 運用前評価コマンド

**起動と範囲 = 明示指定の原則**（2026-07-05 ユーザー）:
- **終端カード（または OUT バーチャルカード）の右クリック「運用前評価」**。検査対象＝そこから
  上流へ pull で到達する部分グラフ。**＝実行と同じ到達集合のドライラン**（評価と実行の範囲が
  常に一致＝分かりやすさの根拠）。
- **キャンバス全体の一括評価は作らない**。実行も同じ原則: 図形クリックに実行は入れない。
  動かしたいフローの出力を OUT カードに繋いでおけば一発で起動できる（OUT＝**信管**・§9.3 共有とモジュール）。

**結果 = レポートカード（MD 実身・固定名上書き）**:
- 同名上書きなので**そのまま別フローの入力に使える**（例: AI カードに読ませて判定＝メタ認知の
  入口）。既存の固定名上書きロジック（v1.4.10）を流用。ダイアログは作らない（ほぼ従来どおりの
  カード生成の流儀）。

**検査項目**:

| 級 | 検査 | 中身 |
|---|---|---|
| エラー | データ循環 | flow 矢印の閉路（実行時検出の静的版） |
| エラー | `{inN}` 超過・入力0 | 位置指定が入力本数超／非ジェネレータで入力なし |
| 警告 | 自己発火リスク | ウォッチャの監視パスが、そこから到達可能な下流の出力先（out_dir）と重なる（発振の主犯） |
| 警告 | ヒューズ未設定 | タイマ/ウォッチャの発行上限が無制限に明示変更されている |
| 警告 | 型不一致 | accept_mime（接続時赤矢印の一括レポート版） |
| 警告 | セレクタ全滅可能 | 全 IN に条件が付き全枝 no-data 化があり得る（always 枝なし） |
| 警告 | 出力衝突 | 同一固定名（out_dir＋名前）へ複数フローが書く |
| 警告 | 依存未解決 | 外部プログラム不在・AI エンドポイント不達・ollama モデル/t2i 環境未構築（1.4.6 案内の一括版） |
| 情報 | 排他資源の競合可能性 | 同一録音デバイスを使うフロー同士 |
| 情報 | 未接続 | ターゲットの無い op カード・繋がれていない IN/OUT バーチャルカード |

**ヒューズの標準装備**（2026-07-05 ユーザー採用）:
- タイマ/ウォッチャの spec に **min_interval・max_fires を標準フィールド**として持たせ、
  **安全側の既定値入り**で生成（初期値例: min_interval=5秒・max_fires=100。実測調整）。
- 無制限は明示設定のみ＝評価コマンドが警告。方針＝「**必要に応じて開放していく**」
  （PC 能力差による大量データ投入ハングアップの回避）。
