## 0. 位置づけ — なぜ v2.0 の前にやるのか

v0.1 コンセプトとの照合評価（2026-07-16 ディスカッション）で判明した事実:

- **情報収集経路の弱さは「v2.0 の新課題」ではなく「v0.1 の未完了マイルストーン」**。
  v0.1 仕様 §4.5（外部リンク＝URLリンク＋キャッシュ）と **M1-6（URLキャッシュ機能。
  外部WebViewの仮身として取り込み）** が、フェーズ1で唯一翻訳されずに残った項目。
- v0.1 §2.3 の**キャッシュモデル（ETag差分確認・更新マーク・オフライン継続）は
  そもそも外部実身のために設計された機構**だが、現実装ではローカル実身/仮身にしか
  適用されていない。URLカード（url_ref）は外部ブラウザ起動のみで、キャッシュモデルの
  本来の適用先が空席のまま。
- 現在の入口は「ファイルD&D・ペースト・クリップボード・生成（AI/t2i）・ウォッチャ」＝
  **手元にあるものと自分で作るものだけ**。「ブラウザで見つける→手動保存→D&D」という
  経路は、アーカイブ第01章が批判した「アプリ分断の手作業橋渡し」の残滓。
- スクレイバーは v2.0 新カード群の候補に挙がっていたが、上記の理由により
  **宿題回収として前倒し**する。v2.0（要求駆動・自律化）が「外の情報を素材に考える」
  段階に進む前に、素材の入口が要る。

**v1.7 のテーマ: 「Web を実身化する」。** WebView を埋め込むのではなく、
取得物（本文・キャプチャ・フィード）を実身としてキャンバスに取り込む。
Webページは消えるが実身は残る — 「水泡に帰さない」理念には v0.1 の記述
（WebView埋め込み）よりこちらの方が合致する。

## 1. 設計原則（5か条）

1. **Web取得はフィルタ、取得物は実身。** 新アーキテクチャは作らない。
   カード＝フィルタ統一モデル・`{out*}` 複数出力・ウォッチャ/随時登録・
   外部依存4層基準という既存の型に全部乗せる。
2. **明示 pull 原則。** ユーザーがフィルタを実行した時だけ取りに行く。
   勝手にネットへ出ない（バックグラウンド巡回はしない）。タイマー/トリガーとの
   組み合わせは可能だが、§4 の安全最小セットを同時に守る。
3. **キャッシュモデルの着地。** 取得実身のメタに source_url / fetched_at /
   etag / last_modified を記録。再取得はまず条件付きGET（ETag/Last-Modified）で
   差分確認。**内容が同一なら CAS により同一ハッシュ＝実身は増えない**
   （コンテンツアドレスが重複排除を無償で解決する — v0.1 §2.3 の設計どおり）。
4. **URLカードの意味論回復。** URLカードを「外部ブラウザを開くボタン」から
   「外部実身への仮身」へ昇格させる。取得系譜（URLカード→取得実身）を relations で
   持ち、再チェックでハッシュが変われば**更新マーク**を表示（強制反映なし・v0.1 §2.3）。
5. **配布ミニマムを崩さない。** HTTP は既存の reqwest（rustls・Ollama連携で導入済み）を
   共用＝依存追加ほぼゼロ。パーサ系クレートは軽量・permissive license のみ。
   ブラウザエンジンは同梱しない（キャプチャは OS 搭載の Edge/Chromium を呼ぶ）。

## 2. 部品の4層分類（標準フィルタ充実検討 §2.5 判定を通した結果）

| 部品 | builtin 名（案） | 層 | 根拠 |
|---|---|---|---|
| ページ取得→Markdown実身 | `web_fetch` | **L1 ビルトイン** | reqwest 導入済み＋HTML→MD 変換クレート（htmd 等・要ライセンス確認）。純関数的・OS非依存 |
| ページのスクリーンショット実身 | `web_capture` | **L2 OSアダプタ** | Windows=Edge 標準搭載（`msedge --headless --screenshot`）。macOS/Linux=Chrome/Chromium 検出、未検出は明確なエラー（speak の espeak と同じ扱い） |
| RSS/Atom→記事カード群 | `web_feed` | **L1 ビルトイン** | feed-rs（MIT）等。**1入力→N出力＝ビルトイン複数出力の解禁が必要**（§3 P3） |
| 更新チェック（更新マーク） | （フィルタでなくカード機能） | 本体 | URLカード右クリック「更新を確認」＋取得系譜。§3 P2 |
| Web検索コネクタ | `web_search` | **見送り（§7-1 決着）** | 「検索はブラウザ・取り込みは web_fetch」。v2.0 で再浮上見込み → V2.0課題.md §7 へ送り |

- メニューは「自動化カードを追加 > **Web ...**」グループを新設（「OS機能 ...」と同格）。
- ビルトイン追加の3点チェックリスト（run_builtin＋単体テスト / BUILTIN_SCHEMAS /
  preflight 出力MIME）＋ model.ts filterOutputMime＋メニュー2系統は従来どおり全号で実施。

## 3. 号割り（P1→P4・使いたい順で前後可）

### P1: `web_fetch` — URL→本文md実身（v1.7.0）

**この計画の本丸。これ1つで「見つけたものをキャンバスに置く」が成立する。**

- 入力の形（両対応・新機構なし）:
  - パラメータ欄に URL 直書き（BuiltinFilterDialog のスキーマフォーム）。
  - テキスト実身を入力に接続 → 中身の URL を取得（1行=1URL。複数行は P3 の複数出力と接続）。
- 出力: 本文抽出（readability 相当）→ Markdown 実身（.md）。
  タイトルを語幹＝カード名に。抽出失敗時は素の HTML→MD 全文にフォールバック。
- メタ記録: source_url / fetched_at / etag / last_modified / final_url（リダイレクト後）。
- ページ内画像は**取り込まない**（第1弾はテキスト本文のみ。画像は P2 のキャプチャが受け持つ。
  個別画像が欲しい場合は画像URLを web_fetch に渡せば raw 取得 — content-type が
  text/html 以外なら**そのまま実身化**する仕様にしておくと、md/csv/json/画像の
  直リンク取得が全部この1カードで済む）。
- 安全最小セット（§4）を run_web_fetch 内に同梱。

### P2: URLカードの仮身昇格 — 更新マークと取得系譜（v1.7.1）✅ 実装済み（2026-07-17・リリースはP4後に一括）

v0.1 §2.3 キャッシュモデルの回収。**フィルタではなく本体側の号**。
実装記録＝[更新履歴.md](更新履歴.md)「v1.7 P2」・レシピ＝ユーザーズチップス Tip 10。

- URLカードを web_fetch の入力として接続可能に（実行系: kind='url' の入力は
  url_ref 文字列を渡す — 実行契約に手が入るので P1 と号を分ける）。
- 取得時に relations で URLカード→取得実身の系譜を張る（kind='fetched' 等・新種エッジ）。
- URLカード右クリック「**更新を確認**」: 条件付きGET→ハッシュ比較→変化があれば
  カードに**更新マーク**（窓喪失の薄赤と同系の控えめなシグナル。強制反映なし）。
  「再取得」で新実身を作り系譜を更新 — 旧実身は残る（イミュータブル・履歴が自然に溜まる）。
- 一括「このプロジェクトのURLカードの更新を確認」はメニュー1項目で足す
  （明示操作なので pull 原則と矛盾しない）。

### P3: `web_feed` — RSS/Atom→記事カード群（v1.7.2）✅ 実装済み（2026-07-17・リリースはP4後に一括）

実装記録＝[更新履歴.md](更新履歴.md)「v1.7 P3」・レシピ＝ユーザーズチップス Tip 11。

- フィードURL→エントリごとに「タイトル＋リンク＋要約」の md 実身 N 枚
  （またはリンクを URLカード N 枚で出す — どちらを既定にするかは実装時判断・§7-2）。
  → **実装: md 実身 N 枚**（§7-2 の2段構え。記事URLはメタ source_url に保持・
  本文は web_fetch で。最大件数パラメータ＝新しい方から既定10・0=全件）。
- **ビルトイン複数出力の解禁**: NodeRun.outputs は Vec で受け皿は既にあり、
  標準フィルタ充実検討 §10 で「split は必要になった実例待ち」と据え置いた件の
  **実例がこれ**。run_builtin の複数出力版（`run_builtin_multi()` 等）を足し、
  ついでに text_split も解禁できる（同じ拡張に乗るだけ・任意）。
  → **実装: `run_builtin_multi()` は不要だった** — v1.6 {out*} で受け皿が済んでいて、
  web_fetch と同型の execute_node 分岐1つで N 出力が通った（新機構なし）。
  text_split の解禁は据え置きのまま（実例が builtin 汎用経路に来たときに）。
- 既読管理: guid/リンクをメタに記録し、再実行時は**新着のみ**出力（差分 pull）。
  ウォッチャ→「新規カードを登録」（Tip 8）と対になる「ネット側の随時入口」が完成する。
  → **実装: 台帳＝出力カードの web_meta guid**（別テーブルなし）。**削除済みカードの
  guid も既読に数える**（読んで消した記事が再実行で蘇らない）。全読み直しは
  フィルタカードの作り直しで。

### P4: `web_capture` — ページのスクリーンショット実身（v1.7.3）✅ 実装済み（2026-07-17・リリースは一括）

実装記録＝[更新履歴.md](更新履歴.md)「v1.7 P4」・レシピ＝ユーザーズチップス Tip 12。

- L2 OSアダプタ: Windows=`msedge --headless --screenshot=... --window-size=...`。
  macOS/Linux=Chrome/Chromium を検出（helper_hint 辞書に追加）、なければ明確なエラー。
  → **実装: 検出は web.rs find_headless_browser に集約**（builtin なので helper_hint
  辞書でなくエラー文言に導入ヒントを同梱 — 表示場所が同じで二重管理にならない）。
- 出力: png 実身。web_fetch と同じメタ（source_url / fetched_at）を記録。
  → **実装: ＋capture:true** — キャプチャは取得系譜・「更新を確認」の**対象外**
  （比較基準は本文md ハッシュで png と比較が成立しないため）。
- 用途: マニュアル素材・デザイン参考・「文字にならないページ」の保存。
  P1 の本文md と対で「テキストと見た目」の両方が実身化できる。
- Edge のヘッドレス挙動は環境依存の枯れ具合に注意（実機検証を号内の最初に置く）。
  → **実機検証済み（2026-07-17・Edge 150）**: `--user-data-dir` 必須・同一プロファイル
  並行起動は合流（→直列化）・起動元により初期プロセスの分離挙動が変わる
  （→完了条件は「ファイル出現＋サイズ安定」）。詳細＝更新履歴「v1.7 P4」。

## 4. 安全設計の最小セット — v2.0 ヒューズの先取り

ネットへの自動アクセスは、タイマー/トリガーと組み合わさった瞬間に「自律的に外へ出る
システム」になる。[要求駆動と自律安全設計.md](要求駆動と自律安全設計.md) の
ヒューズ思想から**最小限だけ先取り**する（v1.7 は良い予行演習になる）:

1. **明示 pull 原則**（§1-2）— 巡回デーモンは作らない。
2. **タイムアウト**（既定 30s）・**サイズ上限**（既定 20MB・超過は明確なエラー）・
   **リダイレクト上限**（既定 5）。
3. **同一ホストへの最小間隔**（既定 2s・一括更新確認/複数URL時に直列＋待機）。
4. **User-Agent 明示**（`TexoS/1.7 (+local thinking tool)` 等 — 身元を偽らない）。
5. **プライベートアドレス遮断**: localhost / 127.0.0.1 / 192.168.* / 10.* 等への
   fetch は既定で拒否（t2i デーモン等のローカルポートへの誤爆・SSRF 系の芽を摘む。
   開発者向けに設定で解除可でよい）。
6. robots.txt は単発の明示 pull（＝人がブラウザで見るのと同じ）では対象にしないが、
   タイマー連動の定期取得を組む場合は間隔下限（3 の強化）を必須とする。

## 7. 未決の論点 → 全件決着（2026-07-16 ユーザー回答）

1. ~~Web検索コネクタ（`web_search`）をどうするか~~ → **✅ 決着: (c) 見送り**。
   「検索はブラウザで、取り込みは web_fetch で」。ただし消える問題ではなく、
   **v2.0 以降（要求駆動が外の情報を自分で探す段階）で再浮上する**見込み —
   [V2.0課題.md](V2.0課題.md) §7 に送り済み。再検討時は自律安全設計（ヒューズ）とセットで。
2. ~~web_feed の出力形~~ → **✅ 決着（暫定・実機FBで確定）: 概要＋実アドレスの2段構え**。
   カードは「タイトル＋概要」がわかれば足りる。本文が要るときは記事URL（メタに保持）を
   web_fetch で叩く。試してみないと分からない領域なので、この形で P3 を実装し実機で確定する。
3. ~~取得履歴の見せ方~~ → **✅ 決着: 最新系譜のみ表示・過去は検索で辿れれば十分**。
   本命の懸念はむしろ **CAS 肥大**。対策を P2 の設計に組み込む:
   - 「更新を確認」は取得→ハッシュ比較→**破棄**（更新マークを付けるだけで実身は作らない）。
     実身が増えるのはユーザーが「再取得」を選んだ時だけ — 明示コミットの原則と同型。
   - サイズ上限 20MB（§4-2）が1件あたりの上限を抑える。孤児実身は既存 GC の対象に乗せる。
4. ~~文字コード・文字化け対策~~ → **✅ 決着: text_convert とは分離**（機構共用しない）。
   変換は**実身データを作る瞬間に一度だけ**行う（HTTP ヘッダ/meta charset に従い UTF-8 化）。
   判定不能の怪しいケースは raw のまま実身化し、後段に既存 text_convert を繋いで直す —
   分離してあるからこそ成立するリカバリ経路。
5. ~~relations 意味論・持ち出し~~ → **✅ 決着: 実身化したもの以外は仮身のままでよい**。
   エッジが意味を持つのはライブラリ化・他プロジェクトへの移動時。仮身（URLカード）を
   有効化（再取得）するかは**移動先/利用先で決める** — 元プロジェクト側で強制再現しない。
   commit_all の URL 警告は維持し、取得実身が同梱される場合はその旨を文言で明示する。

**→ §7 は全決着（2026-07-16）。本文書の未決事項はゼロ。P1 から着手可能。**
