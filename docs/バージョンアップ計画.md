## v1.4.x 候補 — フィルタの合成・部品化（2026-06-14 追加）

外部プログラムフィルタが「引数指定コマンド」型で実用に達したことを受けた発展アイデア
（dev実機で gcc.exe による C コンパイル、Python の引数渡し・連番出力、ドロップポイント
自動実行を確認）。**オートフロー本線（v1.4）の自然な具体化**であり、新しい横道ではない。
「使いたい機能優先・実験リビジョンで細かく刻む」方針に沿って、以下を別々の増分として扱う。

1. **`{stdin}` / `{stdout}` カード**（v1.4.x）— パイプの端点を明示カード化する。
   現状の Type「フィルタ（<入力>出力）」が既に stdin→stdout を扱うので、それを
   **キャンバス上の入口/出口カードとして可視化・合成**する増分。UNIX パイプの GUI 化を
   端点まで素直に表現できる。特殊カードの都度作成の流儀に合致。
2. **プログラムのフィルタ化**（v1.4.x → v1.5 へ橋渡し）— あるパイプラインの成果物
   （ビルド済み exe。例: csv.c → Cコンパイラ → **csv.exe**）を、別パイプラインの
   フィルタノードとして再利用する。生成物がそのまま処理部品になる。v1.5「フィルタ
   ライブラリ（横断再利用）」と直結する。
3. **ウィジェット追加の仕組み**（V2.0 へ接続）— ユーザーが作ったプログラムが再利用可能な
   部品（ウィジェット）になる道。制限付きの第一歩は v1.5 ライブラリ経由で芽出し可能。
   本格版は V2.0「キャンバス内実行アプリ／ウィジェット」（サンドボックス・配布形式が前提）。

→ 流れ: **stdin/stdout カード（v1.4.x）→ プログラムのフィルタ化・ライブラリ化
（v1.4.x〜v1.5）→ ウィジェット（V2.0）**。既存ロードマップ（v1.5 ライブラリ／
V2.0 ウィジェット）に乗る。

## 用語統一とコンテキストメニュー再編（v1.3.4 で実装済み 2026-06-14）

機能追加を重ねてメニューの動詞と表記が割れたため、**先に語彙（ドメイン言語）を確定**し、
それを並べ直す方針。語彙が曖昧なまま並び替えても混乱は消えないので、用語 → メニューの順で行った。
v1.3.4 でカード／キャンバス両メニューに反映済み（dev実機で確認）。残課題はリンクカード系
（URL/フォルダ/プロジェクト/フィルタ/ドロップ）の複数選択時インライン削除の重複排除のみ
（横展開は機能追加時に随時）。

### A. 用語統一（実身/仮身モデルと i18n）

根本原因は **2つの比喩の混在**だった。同じ操作なのに、単体カードメニューは git 語
（「コミット」「再コミット」「コミットを取り消す」）、一括メニューは実身/仮身語
（「実身化」「仮身化」）で表記が割れていた。**実身/仮身を主語彙に統一し、「コミット」は
UI ラベルから消す**（コード/コマンド名/CAS など内部にのみ残す）。

由緒: 実身/仮身モデルは坂村健教授・TRON/BTRON の **real-object / virtual-object model** が源流。
ただし定訳の **object** は git の object（blob/tree/commit）と衝突するため、TexoS では
**object → entity** に置換し、TRON の real/virtual の対称性は保ちつつ git 語との被りを外す。

| 概念 | 日本語ラベル（簡潔） | 英語ラベル | 内部コマンド名（不変） |
|------|------------------|-----------|----------------------|
| 実身（名詞） | 実身 | Real entity | — |
| 仮身（名詞） | 仮身 | Virtual entity | — |
| 仮身→実身 | 実身化 | **Materialize** | commit |
| 実身→仮身 | 仮身に戻す | **Dematerialize** | uncommit |
| 編集破棄で作り直し | 実身化し直す | Re-materialize | recommit |
| 同じ実身の別カード | 仮身を複製 | Duplicate | duplicate |
| OSへ持ち出し | クリップボードにコピー | Copy as file(s) | copy_objects_to_clipboard |
| フォルダへ持ち出し | すべて実身化 | Materialize all (export) | commit_all |

- **Materialize ⇔ Dematerialize** は日英とも完全対称で、git の commit/checkout/clone/revert
  のいずれとも衝突しない。「実体を持つ ⇔ 実体を消して参照だけ残す」という操作の意味そのもの。
- 「仮身を複製（Duplicate）」は状態変更ではなく**新規カード生成**（同じ実身を指す別の仮身）。
  実身化/仮身化（状態トグル）とは直交する別軸であることを、配置とツールチップで区別する。
- UI 表示は i18n キー化（`materialize` / `dematerialize` / `duplicate` …）。内部の git 語と
  UI 語を分離し、英語版（ユニバーサル版）でも破綻しない。

### B. ラベルとツールチップの分離（実装方針）

これまでラベル内に小かっこで入れていた説明（例「仮身を複製（同じ実身をもう一枚）」）は、
**ラベルから外して動詞だけに絞り、説明はホバーのツールチップへ移す**。ツールチップは
小かっこより**もう少し丁寧な説明**にする。慣れたユーザー向けに**設定スイッチでオフ**にできる
ようにしておく（将来不要になったら消せる）。

- `MenuItem` に任意フィールド `hint?: string`（ツールチップ本文）を追加。
- ContextMenu 側でホバー時に表示。**自前ツールチップ**にすれば、積み残しの
  「ダイアログ・コンテキストメニューのUIカラーテーマ追従」も同時に拾える（ネイティブ
  `title` 属性はテーマ非追従・遅延ありのため不採用）。
- 設定フラグ `showMenuHints: boolean`（既定 on）。テーマ設定と同じ場所に置く。

ラベル（簡潔）／ツールチップ（丁寧）の対応例:

| ラベル | ツールチップ |
|--------|------------|
| 実身化 | このカードの内容をプロジェクトに保存し、実身（プロジェクトが所有する実体）にします。元ファイルへの参照だった仮身が実体化します。|
| 仮身化 | プロジェクト内の実体を消し、元ファイルへの参照（仮身）に戻します。|
| 仮身を複製 | 同じ実身を指す仮身をもう一枚作ります。内容は複製されず、両方が同じ実体を指します。|
| 実身化し直す | 現在の編集を破棄し、取り込み時点の内容で実身化し直します。|
| クリップボードにコピー | 選択カードをファイルとして OS のクリップボードへ。Explorer や他アプリに貼り付けられます。未保存の仮身は自動で実身化されます。|

### C. メニュー再編（語彙確定後に機械的に展開）

カードメニューを区切り線でグループ化する:

```
「ラベル」
─────────  開く・編集系   既定で開く／アプリ選択／キャンバスで編集・プレビュー／一時閲覧
─────────  配置・表示系   選択にフォーカス／最前面・最背面／フォルダで表示
─────────  実身⇔仮身・持ち出し   実身化／仮身に戻す／実身化し直す／クリップボードにコピー／仮身を複製
─────────  メタ操作      表示名を変更／コメントを編集／削除
```

- **複数選択時の重複解消**: 複数適用できる操作は「まとめて…」サブメニューに一本化し、
  インラインには出さない（現状はクリップボードコピーが2か所、削除もインライン転送と重複）。
- ショートカット併記の検討（Ctrl+C 等をラベル右に表示し、キーとメニューの対応を可視化）。

## v1.5 系 — オートメーション（プロセスコントロール＋ビジュアルコマンド）★次の主役

**方針（2026-06-18 ユーザー決定）**: フィルタで分かったのは「**CMD の子プロセスとして
立ち上げれば、あらゆるプログラムを起動・制御できる**」こと。コマンドラインで制御できる
"お行儀のよい"プログラムは CLI オプションが充実し、**戻り値（exit code）で実行結果が分かる**。
ここを足場に、v1.5 系はオートメーション化に注力する。AI／MCP は UI とシステムが固まって
からなので V2.0 へ送る。設計の練り込みは `docs/オートメーション設計メモ.md`。

### A. プロセスコントロールカード（フィルタの一般化）
- フィルタ（データ→変換→データ）を**プログラムの起動・制御**まで一般化する。既存の足場
  （async 実行・タイムアウト・taskkill ツリー kill・stdout/stderr 捕捉・
  `{in}`/`{out}`/`{in*}`/`{inN}` テンプレート）をそのまま活かせる＝**低リスク**。
- 新しい軸は **exit code による制御フロー（分岐）**: 実行 → 戻り値で成功／失敗を分けて
  下流を選ぶ。キャンバスが**ビジュアルなシェル／Makefile／CI** になる。
- まずは **一括（one-shot）＋ exit code 分岐**から（お行儀のよいバッチ系）。常駐・対話
  プロセス（stdin ストリーム）は pull 評価モデルを壊すので後送り。
- 旧 v1.4.x 候補の `{stdin}`/`{stdout}` カード・**プログラムのフィルタ化**（成果物 exe を
  処理ノード化）は、この系列のサブ項目として吸収する。
- フィルタライブラリ強化（プロジェクト横断の部品再利用）も同系列。ウィジェット（V2.0）への橋渡し。

### B. ビジュアルコマンド（図形＝スコープ）
- 図形は「ビジュアルにもロジックが組める」ことの証明だった（含まれるカードをまとめて
  選択・移動できる）。これを**含まれるカードへコマンドを実行**まで広げる。
- 統一の核: **図形（スコープ）＋プロセスコントロールカード ＝「この領域のカード全部に
  このプログラムをかける」**（空間的な foreach）。空間的包含がループ／スコープという
  プログラム構造になる。`run_flow` を再利用。
- ビジュアルコマンドはプロセスコントロールの**空間ドライバ**であり、別機能ではなく統合。

### C. その他のトリガー
- タイマーカード（定時実行トリガー）／ドロップ受け入れカード（フローのデータ入り口）。
