# TexoS ユーザーズチップス

実際に使える「拡張」のレシピ集。主に**外部プログラムフィルタ**の設定例を、思いついた・必要になった順に追記していく生きたメモ。

TexoS の流儀は「余計なことはしない」。アプリ本体に変換や自動処理を埋め込む代わりに、ユーザーが**明示的にフィルタを組んで**必要なときだけ走らせる。ここはそのフィルタの作り方を貯める場所。

> 対になる資料 → [外部依存プログラム一覧.md](外部依存プログラム一覧.md)（各フィルタが必要とする外部プログラムの入手先・導入方法）

---

## フィルタ設定の基礎（共通）

外部プログラムフィルタは「フィルタ設定ダイアログ」で登録する。最終的に実行されるコマンドは:

```
"<解決したプログラムのフルパス>" <CMD欄の中身>
```

Windows では `cmd /c` 経由なので `<` `>` のリダイレクトがそのまま効く。

| 欄 | 意味 |
|----|------|
| **NAME** | 実行ファイル名。`PATH` 空欄なら `.texos\filters` → 環境変数 PATH の順で解決 |
| **PATH** | 明示パス（最優先）。「参照…」で選び「同梱⬇」で `.texos\filters` にコピーすると、プロジェクトごと持ち運べる |
| **Type** | `filter`（`< 入力 > 出力`）/ `command`（引数で `{in}` `{out}` を渡す）/ `generator`（入力不要） |
| **CMD** | 引数＋リダイレクト。プログラム名は自動で前置されるので**書かない**。`{in}`=入力、`{out}`=出力（共に絶対パス） |
| **IN** | 受け入れ MIME（接続時の型チェック）＋入力拡張子の絞り込み |
| **出力拡張子** | 生成物の拡張子 |
| **OUT** | **空欄＝プロジェクト直下にコミット＝実身化** / フォルダ指定＝窓（仮身）で配置 |
| **制限時間** | 暴走対策。0＝無制限 |

> 仮身に接続したフィルタを実行し、OUT を空欄にすると、変換結果が**実身**として生成される。これが「フィルタによる実身化」。

## Tip 1: テキストを UTF-8 に変換する（nkf フィルタ）

### 背景
非 UTF-8（Shift_JIS・EUC-JP・JIS・UTF-16）のテキスト実身は、**仮身の閲覧では推定デコードして表示できる**（v1.4.13。元バイトは触らない非破壊ビュー）。が、編集＝実身化するには中身を UTF-8 に揃える必要がある。

ここで本体に自動変換を仕込むと、借用元（共有された実身）を黙って書き換えてしまう恐れがあり、流儀に反する。**やってよい時だけ明示的に走らせる UTF-8 化フィルタ**を別建てするのが正解。

### 準備（nkf）
`nkf` は入力の文字コードを自動判定して変換する、stdin/stdout フィルタの定番。Windows 版バイナリ `nkf.exe`（例: `F:\Downloads\nkf32\nkf.exe`）を用意し、フィルタダイアログの「参照…」で選んで「同梱⬇」しておくと可搬になる。

### 設定

| 欄 | 値 |
|----|-----|
| タイトル | `UTF-8化` |
| NAME | `nkf.exe`（同梱推奨） |
| Type | **フィルタ（< 入力 > 出力）** |
| CMD | `-w < "{in}" > "{out}"` |
| IN | テキスト / 拡張子 `txt,csv,md`（任意） |
| 出力拡張子 | `txt` |
| OUT | **空欄**（＝実身としてコミット） |

実行されるコマンドは `"…\nkf.exe" -w < "入力" > "出力"`。

### nkf オプション早見（このマニュアル添付分から）

| オプション | 効果 |
|-----------|------|
| `-w` / `-w80` | UTF-8 出力（**BOM 無し**）← 既定に最適 |
| `-w8` | UTF-8 出力（BOM 付き） |
| `-Lu` | 改行を LF に統一（`-Lw`=CRLF / `-Lm`=CR / 既定は変換しない） |
| `--guess`（`-g`） | 自動判定結果だけを出力（中身は変換しない・確認用） |
| `--ic=<codeset>` / `--oc=<codeset>` | 入出力コードを明示指定（自動判定を上書き。例 `--ic=CP932`） |
| `--overwrite` | 元ファイルを変換結果で上書き（TexoS では使わない。`{out}` へ書く） |

- 自動判定の対象: ISO-2022-JP / Shift_JIS(CP932) / EUC-JP / UTF-8 / UTF-16。
- 改行も LF/CRLF/CR に揃えたいなら CMD を `-w -Lu < "{in}" > "{out}"` のように足す。
- どの文字コードと判定されたか確かめたいときは、一時的に CMD を `--guess < "{in}" > "{out}"` にして実行。

### ライブラリへ登録（再利用）
一度組んだフィルタは**フィルタライブラリ**に名前を付けて登録すると、他のプロジェクトでも一覧から呼び出せる。`UTF-8化` を登録しておけば、次から作り直さずに置ける。

> ⚠️ ライブラリは**アプリ共通**（`%APPDATA%\com.yoshi.texos\filter_library.json`）でプロジェクトフォルダの外にある。つまり**ライブラリ登録はこの PC の自分用**であり、プロジェクトを zip で配っても相手には付いていかない（→ 配布は次節）。

### 使い方の流れ
1. Shift_JIS のテキストファイルを TexoS に取り込む（仮身ができる）。
2. 仮身を `UTF-8化` フィルタカードへ矢印で接続。
3. フィルタを実行 → UTF-8 の実身がプロジェクト直下に生成される。
4. 以後はその実身を普通に閲覧・編集できる（保存時に文字化けしない）。

### 役割分担（覚え書き）
- **仮身ビュー**（`read_view_text` / chardetng）＝**表示のためだけ**のデコード。元バイトは不変。
- **UTF-8化フィルタ**（nkf）＝**実身化**のための実変換。明示実行・非破壊（出力は別ファイル）。

## 配布: サンプルプロジェクトとして配る

「同梱 → ライブラリ登録 → チップスが生きる」の最終形は、**プロジェクトフォルダごと配ること**。TexoS は情報を整理するツールでもあるので、マニュアルそのものを TexoS で作り、フィルタや同梱プログラムと一緒に 1 つのプロジェクトに詰めて `SampleProject.zip` として渡す。受け取った人は解凍して開くだけで、設定済みのフィルタがそのまま動く。

### プロジェクトフォルダの中身（= zip で運ばれるもの）
```
SampleProject/                プロジェクトフォルダ（これを丸ごと zip）
  ├── <コミット済み実身>       人が名付けた編集可能ファイル（UTF-8化の成果物など）
  └── .texos/
      ├── texos.db             カンバスとカード（設定済みフィルタカードを含む）★
      ├── cas/                 不変の実身本体
      └── filters/             同梱プログラム（nkf.exe など）★
```
★ が「動くフィルタ」を成立させる要。`texos.db` に UTF-8化フィルタカードの設定が入り、`nkf.exe` は `.texos\filters` から解決される（PATH 不要）。**両方ともフォルダ内なので zip に乗る**。

### 運ばれないもの
- **フィルタライブラリ** / **ランチャーライブラリ**（`%APPDATA%` 配下・アプリ共通）。配布物はライブラリではなく、**カンバス上に置かれた実物のフィルタカード**で機能を運ぶ。

### だから「マニュアルを TexoS で作る」が効く（→ メモ #2）
- サンプルプロジェクトの中に、TexoS で書いたマニュアル（仮身・ノート・図形で構成）を同梱する。
- マニュアル内に各フィルタの**レシピ（このチップスの設定表）**を載せておけば、受け取った人は自分のライブラリへ再登録できる。
- 「使い方を説明したマニュアル」自体が TexoS の作例になり、ドッグフーディングになる。

### 配布手順（たたき台）
1. 配布用に新規プロジェクト `SampleProject` を作る。
2. 例題ファイル（Shift_JIS の .c など）と `UTF-8化` フィルタカードを配置。
3. nkf.exe を「同梱⬇」して `.texos\filters` に入れる（※開発・動作確認用。配布時は ⚠️ 参照）。
4. マニュアル（ノート・仮身）を TexoS 上で作り、同じカンバスに置く。
5. アプリを閉じてから `SampleProject` フォルダを zip 化 → `SampleProject.zip`。

### ⚠️ 配布時の権利・親切設計の注意
- **他人が作ったプログラムを勝手に同梱して配布しない。** nkf のようなサードパーティ製バイナリは、配布物（zip）からは**抜いておき**、入手先（公式ダウンロード）への案内を添える。同梱機能は「自分の環境で動かす」「ライセンス上配布可能なもの」に使う前提。
- 受け手は案内に従って nkf.exe を入手し、フィルタカードの「参照…→同梱⬇」で自分の `.texos\filters` に入れれば、カードはそのまま動く。
- AI（Ollama）・Whisper の自動導入にはアプリ内ガイドが付いている。**基本フィルタにも、カードの NOTE 欄やマニュアルで「何を入手して、どう設定するか」を説明する**こと（プログラムの実体ではなく、入手と設定の手順を配る）。

## Tip 2: キャンバスをプレゼンテーションにする（図形＝章立て・カメラ滑空）

v1.4.20 のナビゲーションキー＋カメラアニメーションで、キャンバスがそのままスライドデッキになる
（ユーザー発見 2026-07-03。スライドの檻に切り刻む某PPと違い、思考の地形をカメラが飛ぶ方式）。

### 準備
1. 話題ごとにカード群を**図形（角丸四角など）**の上にまとめる（図形＝章・セクション）。
2. 図形に**付箋の見出し**（先頭行を大きく太字）を添えると章タイトルになる。
3. 右下の % クリック → **「フォーカス移動」を「低速」**にする（プレゼン向けのゆったりカメラ）。

### 本番の操作（3キーだけ）
- **Home** ＝ 全体像へ引く（「今日はこの地図を旅します」）
- **図形を軽くクリック** ＝ その章のカードがまとめて選択される
- **F** ＝ その章へカメラが滑空（加速→減速のイージング付き）
- 深掘りしたいカードは単体クリック → **F** でさらに寄る。戻りは **Home**。
- 資料の場所を忘れたら **Ctrl+F** で検索 → クリックでカメラが飛ぶ。

### 覚え書き
- ズームレベル自体が「概要 ↔ 詳細」の軸になる（Prezi 的な表現が標準機能の合成だけで成立）。
- アニメーション中でもホイール／中ボタンを触えば即座に手動操作へ切り替わる（乗っ取られない）。
- 作業に戻るときは「フォーカス移動」を高速か即時に戻すと軽快。

## Tip 3: t2i の Python 環境に任意ライブラリを追加する（例: peft）

### 背景
画像生成（t2i）の Python 環境は、システム Python ではなく **TexoS が uv で構築した管理 venv**（`%APPDATA%\com.yoshi.texos\runtime\envs\t2i\`）。LoRA を使おうとして

> LoRA '…' の適用に失敗しました（peft 未導入なら『pip install peft』が要ります）

と言われたら、この venv に `peft` が入っていないのが原因。

### 注意: `pip install` は直接使えない
uv が作った venv には **pip 自体が入っていない**ので、`python -m pip install` は失敗する。TexoS 同梱の `uv.exe` 経由で入れるのが正解。

### 手順（PowerShell）
```powershell
$root = "$env:APPDATA\com.yoshi.texos\runtime"
& "$root\bin\uv.exe" pip install --python "$root\envs\t2i\Scripts\python.exe" peft
```
`peft` の部分を差し替えれば任意のライブラリが入る。`$env:UV_CACHE_DIR = "$root\cache"` を先にセットしておくと TexoS 本体とキャッシュを共有できる（任意）。

### 落とし穴: TexoS の再起動では反映されない
t2i デーモンは常駐かつ、**健康なら TexoS 再起動後もそのまま再利用される**（版一致＋モデル認識OKなら生かしておく設計）。さらに diffusers は「peft が有るか」を**プロセス起動時に一度だけ判定してキャッシュする**ため、動いているデーモンに後からライブラリを入れても認識されない。

反映するには**デーモン自体を止める**: 画像生成の設定ダイアログの**サーバー停止**ボタン（VRAM解放と同じボタン）を押す。次の生成時に新しいプロセスが自動起動し、追加したライブラリが有効になる。

### 場所の早見
| もの | 場所 |
|------|------|
| 管理 venv（t2i） | `%APPDATA%\com.yoshi.texos\runtime\envs\t2i\` |
| uv 本体 | `%APPDATA%\com.yoshi.texos\runtime\bin\uv.exe` |
| uv キャッシュ | `%APPDATA%\com.yoshi.texos\runtime\cache\` |

### 覚え書き
- 手動で入れたライブラリは、**環境を作り直すと消える**（「環境を構築する」で再構築した場合など）。恒久的に必要なものはアプリ側の要件定義（`src-tauri/src/runtime/python.rs` の `ENV_REQUIREMENTS`）に追記する。
- `peft` は v1.5 系で `ENV_REQUIREMENTS` に追加済みなので、以後の新規構築では最初から入る。既存環境には上の手順で足す。

## Tip 4: LoRA のベースモデルを見分ける（safetensors ヘッダ解析）

### 背景
LoRA はベースモデル（SD1.5 / SDXL / FLUX / Krea 2 …）ごとに別物で、合わないモデルに載せると

> LoRA '…' は現在のモデル（sd）に適合しません＝対応する層が無く未適用でした
> No modules were targeted for adaptation. …

のようなエラーになる。厄介なのは**ファイル名が当てにならない**こと。実例: `SDXLrender_v2.0.safetensors` は名前に反して **SD1.5 用**（「SDXL風の絵を SD1.5 で出す」LoRA）。逆に何の表記もない `hkstyleV5` が SDXL 用だったりする。

### 判定法（手動）
safetensors はファイル先頭にテンソル一覧の JSON ヘッダを持つので、**全体を読まずに数秒で判定できる**。t2i の venv で:

```powershell
& "$env:APPDATA\com.yoshi.texos\runtime\envs\t2i\Scripts\python.exe" -c @'
import json, struct, os, glob
d = os.path.expandvars(r"%APPDATA%\com.yoshi.texos\t2i\loras")
for f in sorted(glob.glob(os.path.join(d, "*.safetensors"))):
    with open(f, "rb") as fh:
        n = struct.unpack("<Q", fh.read(8))[0]
        hdr = json.loads(fh.read(n))
    md = hdr.pop("__metadata__", {})
    dims = {v["shape"][-1] for k, v in hdr.items()
            if "attn2" in k and ("to_k" in k or "to_v" in k)
            and ("lora_down" in k or "lora_A" in k)}
    if any("double_blocks" in k or "single_blocks" in k for k in hdr): arch = "FLUX"
    elif 2048 in dims: arch = "SDXL"
    elif 768 in dims:  arch = "SD1.5"
    else:              arch = "別アーキ（DiT系?）"
    base = md.get("ss_base_model_version", "")
    print(f"{os.path.basename(f)}: {arch}" + (f"（メタデータ: {base}）" if base else ""))
'@
```

### 判定の理屈
1. **学習メタデータ** `ss_base_model_version`（kohya 系で学習されたものに入る。例 `sdxl_base_v1-0`、`krea2`）。ただし無いファイルも多い。
2. **UNet cross-attention の入力次元**（テキスト埋め込み次元）が確実: **768 = SD1.5 / 2048 = SDXL**。キー名 `..attn2..to_k..lora_down` の shape 末尾を見る。
3. `double_blocks` / `single_blocks` キー → **FLUX**。`diffusion_model.blocks…` 等どれにも当てはまらないキー構造 → SD/SDXL/FLUX 以外の DiT 系（Krea 2 など）＝ TexoS では現状使えない。

### 覚え書き
- CivitAI で探すときは「Base Model」フィルタで手持ちモデルの系統に絞るのが確実。
- TexoS は単ファイルモデル（`.safetensors` 直置き）を同じ流儀のキー解析で sd / sdxl / flux 自動判定している（`t2i_server.py` の `_sniff_single_file_kind`）。**LoRA 側にも同じ判定を載せれば、実行前に「この LoRA は SDXL 用です（現在のモデル: sd）」と警告できる**＝アセット一覧 `/assets` にアーキ情報を含める拡張のヒント。エラーが出てから悩むより先に教える方が親切。

## Tip 5: 個人ライブラリの持ち運び — 配布と復元の使い分け（v1.5.8/1.5.9）

### 背景
個人ライブラリ（ユーザーのフィルタ・ランチャー・モジュール）は**アプリ共通の置き場
（AppData）**にあり、プロジェクトを zip で渡しても**付いていかない**（勝手に他人へ渡らない設計・
共有とモジュール設計 §10.1）。持ち運びは目的別に2ルート。

### ルートA: 他人に渡す（配布）
**ライブラリバックアップの無い**配布用プロジェクトを作り、キャンバスに必要なモジュールを
展開して渡す（「自動化カードを追加 → ユーザーのモジュール 📦」）。

1. 配布用プロジェクトを新規作成
2. 渡したいモジュールをキャンバスに展開（データ実身も CAS ごと付いてくる）
3. 案内コメント（付箋・**矢印なし**）で使い方や「このカードは環境に合わせて編集」を添える
4. プロジェクトフォルダごと zip → 受け手は開いて、ロック済み図形の右クリック
   「**ライブラリに登録（モジュール）**」で自分の道具箱へ

> 受け手の環境に外部プログラムや AI が無くても、展開時に**注意カード**が自動で立つ（§10.3）。

### ルートB: 自分の復元・別PCへの移植
「整理・書き出し → **個人ライブラリをプロジェクトへ書き出し**」でプロジェクト直下に
`ライブラリバックアップ/`（フィルタ・ランチャー・モジュール全部の写し）を作っておく。

戻すときは、そのプロジェクトを開いて「整理・書き出し →
**ライブラリバックアップから取り込み**」→ 一覧から**選んで**戻す（1件ずつ・すべて取り込みも可。
同名は上書き＝復元の意味論。事前にラベルで「（同名を上書き）」と知らせる）。

- ライブラリを壊した/消したとき → バックアップ入りプロジェクトから選んで復元
- 別PCへの移植 → バックアップ入りプロジェクトをコピーして開き、まとめて取り込み

### 覚え書き
- バックアップは実行のたびに**丸ごと上書き**される（定期的に実行すれば常に最新）。
- 手動で戻す場合の置き場は `%APPDATA%\com.yoshi.texos\`（filter_library.json /
  launcher_library.json / modules\）。ただしコマンドがあるので通常は不要。

## Tip 6: awk で「内蔵フィルタの上の段」— スクリプトをカードで持つ

### 背景
内蔵の text_*（grep / cut / sort …）の組み合わせでは届かない「条件付きの集計・フィールド演算・
整形」は、awk なら1行〜数行で書ける。日本語テキストのフィールド処理には **gawk-mbcs**（日本語対応
gawk。同梱の `igawk.exe` が日本語対応版で、内部で `gawk.exe` を呼ぶ）を使う
（jgawk は 16bit のみ・開発停止のため断念。入手先・ライセンス注意・構成は
[外部依存プログラム一覧.md](外部依存プログラム一覧.md)）。

### 準備（gawk-mbcs）
`gawk-mbcs-win32` の zip を展開し、**フォルダごと**プログラムフォルダに配置して **PATH を通す**
（igawk.exe は同フォルダの gawk.exe を呼ぶため、単体 exe の「同梱⬇」には向かない）。
コマンドラインはユーザーが独自に組む＝ **CMD に awk プログラムを直接書く**のが基本形。

### 型A: 短いプログラムは CMD に直接書く（基本形）

| 欄 | 値 |
|----|-----|
| タイトル | `1列目の合計` |
| NAME | `igawk.exe`（PATH） |
| Type | **フィルタ（< 入力 > 出力）** |
| CMD | `"{ sum += $1 } END { print sum }" < "{in}" > "{out}"` |
| IN | テキスト |
| 出力拡張子 | `txt` |

### 型B: 長いスクリプトは「実身カード」で持つ（v1.5 複数入力）

スクリプトを `集計.awk`（テキスト実身）としてキャンバスに置き、フィルタへ**2本目の入力**として
つなぐ。スクリプトもカードなので、**編集も配布（SampleProject.zip）もカードの流儀のまま**。

| 欄 | 値 |
|----|-----|
| タイトル | `awk スクリプト実行` |
| NAME | `igawk.exe`（PATH） |
| Type | **コマンド（引数で渡す）** |
| CMD | `-f "{in2}" "{in1}" > "{out}"` |
| IN | `*/*`（データとスクリプトの両方を受ける） |
| 出力拡張子 | `txt` |

- 配線: **入力1 = データ、入力2 = スクリプト**。`{inN}` の番号は矢印の port 順（port 指定が
  なければ接続順）。逆に繋いだら矢印を張り直すか、矢印の port で順序を固定する。
- `{in2}` を含む CMD は**集約実行**（入力が揃ってから1回実行）になる。
- 応用: スクリプトカードを差し替えれば同じフィルタで別の処理になる＝「プログラムもデータ」。

### 覚え書き
- gawk-mbcs は GPL。**配布物にバイナリは同梱せず**、スクリプトカード＋フィルタ定義＋入手案内で配る
  （受け取った人はバイナリだけ用意すれば動く）。
- UTF-8 で足りるなら GNU gawk＋前段に内蔵「文字コード変換」でも代替できる
  （gawk 未検出時は💡入手のヒントが出る・v1.5.15）。

## Tip 7: Python GUI をデスクアクセサリにする（pythonw ランチャー）

### 背景
時計・電卓のような「クラシックだが手元に欲しい」小物は、TexoS に埋め込まなくても
**Python スクリプト＋ランチャーカード**でネイティブに動かせる（2026-07-14 実証:
tkinter 製アナログ時計）。フィルタ（同期ジョブ・実行中パネル・Stop-all 対象）ではなく
**ランチャー**（detached 起動・待たない・台帳外）を使うのがポイント。常駐アプリを
フィルタで起動すると実行中パネルに載り続け、Stop-all の巻き込み事故のもとになる。

### 設定

| 欄 | 値 |
|----|-----|
| 種別 | **ランチャーカード**（フィルタではない） |
| プログラム | `pythonw.exe`（**w 付き** — コンソールなしインタプリタ。python.exe だと黒い窓が一緒に出る） |
| PATH 例 | `C:\Users\<名前>\AppData\Local\Programs\Python\Python310\pythonw.exe` |
| 配線 | スクリプト実身（例: `tokei.py`）→ ランチャー。起動時に引数として渡される |

### 覚え書き
- 最前面表示・枠なし・透明度などの「アクセサリらしさ」は**スクリプト側**（tkinter の
  `-topmost` / `overrideredirect` / `-alpha`）で持たせる。TexoS は起動役に徹する。
- 終了はアプリ自身の UI（右クリックメニュー等）で。detached なので TexoS からは止めない。
- スクリプトもカードなので、編集・配布はカードの流儀のまま（Tip 6 型B と同じ思想）。
- 標準ライブラリだけのスクリプトなら venv 不要でどの Python でも動く。

## Tip 8: 随時登録 — ウォッチャ＋「新規カードを登録」でアプリの成果物を自動回収（v1.6.0）

外部アプリ（GUI でもスクリプトでも）がフォルダへ書き出すファイルを、**現れるたびに
自動でキャンバスのカードにする**定番パターン。実例: ChillChordMaker（LoFi シンセ）の
BATCH EXPORT がコードごとの WAV を書き出す → その場でカードとして並ぶ。

### 組み方（カード2枚・同じフォルダパスを書くだけ）

1. **ウォッチャ**（メニュー: オペレーション）: 監視パス＝回収したいフォルダ。
   反応するイベント＝「作成のみ」・静穏時間 2 秒（書き込み途中を掴まない）。
2. **新規カードを登録**（メニュー: OS機能）: 対象フォルダ＝**ウォッチャと同じパス**
   （空ならプロジェクトフォルダ直下）。
3. ウォッチャ → 新規カードを登録 へ**リクエスト矢印**を引き、ウォッチャの「▶ 稼働開始」。

### 挙動

- 登録済み・一時ファイル（`~`/`.` 始まり・`.tmp` `.part` など）は自動スキップ＝二重登録しない。
- **プロジェクト内のファイルは実身、外部フォルダのファイルは窓（仮身）**として登録される。
- 新カードは「新規カードを登録」カードの下にグリッドで並ぶ（ファイル名順）。
- エクスプローラからフォルダへ直接コピーしたファイルも同じように拾われる（出所を問わない＝観測）。

### 使い分け

- **TexoS がプログラムを実行して成果を受け取る**（同期・一括）→ フィルタ/ジェネレータの
  `{out}`（単一）/`{out*}`（複数）。→ 正本: [カード化プログラム作成規約.md](カード化プログラム作成規約.md)
- **アプリが勝手に書き出すのを見張って拾う**（非同期・随時）→ 本 Tip。
  ランチャー起動（Tip 7）した対話的アプリとの相性が特に良い。

## Tip 9: Webページを実身化して読む — web_fetch＋AI要約（v1.7.0）

ブラウザで見つけたページを「手動保存→D&D」せずに、**URL を貼るだけでキャンバスの
Markdown 実身にする**基本レシピ。ページは消えても実身は残る（水泡に帰さない）。

### 最小（カード1枚）

1. **ページ取得**（メニュー: Web）: 作成時に URL を貼る（あとから設定ダイアログでも変更可）。
2. ▶ 実行 → 本文が Markdown 実身になる（**ページタイトル＝カード名**・出典URL/取得日時はメタに記録）。

### 定番3カード（外部依存ゼロの初見デモ）

**付箋（URL）→ ページ取得 → AI変換（要約）** — 気になるページの URL を付箋に貼って▶。
Ollama があれば要約まで、なくても実身化までが動く。テキストカード接続時は**1行目の URL**を読む。

### 挙動と決め事

- 本文抽出（readability 相当）に失敗したページは**全文 HTML→Markdown** にフォールバック。
- **HTML 以外の直リンクはそのままの形式で実身化**: 画像 URL → 画像カード・CSV → csv・JSON → json。
  「直リンクの取り込みは全部この1カード」で覚えればよい。
- 文字コードは取得の瞬間に一度だけ UTF-8 化（ヘッダ/meta charset 準拠）。判定できない
  怪しいページは **raw の .html のまま実身化**されるので、Tip 1 の text_convert を後段に繋いで直す。
- 安全策は同梱: タイムアウト30秒・上限20MB・リダイレクト5回・同一ホスト2秒間隔・
  localhost やプライベートIPへの取得は既定で拒否（開発者は spec JSON の `"allow_private": true`）。
- 取りに行くのは**実行した時だけ**（勝手に巡回しない）。URL カードの「更新を確認」は Tip 10 へ。

## Tip 10: URLカードの更新マーク — 仮身としてのURL（v1.7 P2）

URLカードは「ブラウザを開くボタン」ではなく**外部実身への仮身**。取得済みのページに
変化がないかを、実身を増やさずに確認できる。

### 使い方

1. **URLカード → ページ取得（web_fetch）** を矢印で繋いで▶（URLカードがそのまま入力になる）。
   取得すると **URLカード→取得実身にグレー点線の系譜**が付く。
   （フィルタを使わず、URLカード右クリック「**再取得**」でも初回取得できる）
2. しばらくして、URLカード右クリック「**更新を確認**」— ページを取得して**比較だけ**して捨てる
   （実身は作らない）。変化があればカードに**薄赤のドット＋「更新あり」**が付く。
3. 中身を新しくしたければ「**再取得（新しい実身を作る）**」— 新しい実身カードができ、
   系譜がそちらへ張り替わる。**前の実身は残る**ので、版の履歴が自然に溜まる。
4. まとめて確認したいときは、キャンバス右クリック → 整理・書き出し →
   「**URLカードの更新を確認...**」（取得済みカードだけが対象・同一サイトへは間隔を空けて直列）。

### 決め事（覚えること）

- **マークは付くだけ**。勝手に実身を書き換えない（反映は常にユーザーの「再取得」）。
- **内容が変わっていなければ実身は増えない**。「再取得」も web_fetch の再実行も、
  前回と同一内容なら「変化なし」と告げるだけ（取得日時・ETag は最新化される）。
  新しい実身カードができる＝本当に変わったとき、と覚えてよい。
- 確認は ETag/Last-Modified の**条件付きGET**なので、変わっていなければ転送も比較も最小。
  サーバが対応していなくても、本文を同じ変換に通した**内容比較**で判定する
  （広告や日付だけ変わるページでは「更新あり」になることがある — 本文抽出である程度吸収）。
- 系譜（点線）は**最新の1本だけ**表示。過去の取得実身はカードとして残り、検索で辿れる。

## Tip 11: RSSで新着をカード化する — web_feed の差分取得（v1.7 P3）

ブログやニュースの**フィード（RSS/Atom）を「随時入口」にする**レシピ。Tip 8 の
随時登録（ウォッチャ＝手元のファイル）のネット版で、**再実行すると新着だけ**が
キャンバスに増える。

### 使い方

1. **フィード取得**（メニュー: Web）: 作成時にフィードURL（`…/feed.xml`・`…/rss` 等）を貼る。
2. ▶ 実行 → **記事ごとに「タイトル＋概要＋記事リンク」の Markdown 実身**ができる
   （1記事=1カード・タイトル＝カード名・新しい方から既定10件。件数は設定で・0=全件）。
3. また▶ → **前回から増えた記事だけ**がカードになる（取り込み済みは「既読・実身は
   増やしません」）。読み終えて消したカードも既読のまま＝**再実行で蘇らない**。
4. 本文まで読みたい記事は、その md の「記事: URL」を **URLカード（またはテキスト）→
   ページ取得（web_fetch）** に通す — Tip 9・10 にそのまま繋がる。

### 決め事（覚えること）

- カードは**概要まで**。本文はメタに保持した記事URLを web_fetch で（2段構え）。
- 既読の台帳は**出力カードそのもの**（メタの guid）。全部読み直したいときは
  フィルタカードを作り直せば台帳が空になる。
- タイマー（周期実行）と組み合わせれば定期チェックになるが、取りに行くのは
  発火した時だけ（巡回デーモンは居ない）。安全策（タイムアウト・上限・同一ホスト間隔・
  プライベートIP拒否）は web_fetch と共通。

## Tip 12: ページの見た目を保存する — web_capture（v1.7 P4）

web_fetch が**本文（テキスト）**なら、こちらは**見た目（画像）**。ページの
スクリーンショットを PNG 実身にする。マニュアル素材・デザイン参考・
「文字にならないページ」（図表やレイアウトが主役のページ）の保存に。

### 使い方

1. **ページキャプチャ**（メニュー: Web）: 作成時に URL を貼る（空欄=テキスト/URLカード接続）。
2. ▶ 実行 → ページの見た目が PNG 実身になる（出典URL・取得日時はメタに記録）。
3. 同じ URL を**ページ取得（web_fetch）にも**繋げば、「テキストと見た目」の両方が残る。

### 決め事（覚えること）

- **ブラウザは同梱しない**: OS の Edge（Windows 標準搭載）/ Chrome / Chromium を
  ヘッドレスで使う。見つからないときはエラーに導入ヒントが出る。
- 写るのは**指定した表示領域**（既定 1280×1600）。設定の高さを増やすとページの
  下の方まで写る（ページ全体の自動計測はしない）。
- キャプチャには**更新マークは付かない**（見た目の比較は成立しないため、取得系譜の
  対象外）。ページの変化を追いたい URL は Tip 10 の web_fetch＋更新確認で。
- 安全策（タイムアウト30秒・プライベートIP拒否・同一ホスト間隔）は web_fetch と共通。
  JS の多いページは描画を待ってから撮る（仮想時間8秒）。

## Tip 13: URLをカードにする — リンクの受け皿と URLカード化（v1.7 P5）

URL は3つの経路でカード（リンク）になる。役割で使い分ける。

### ① ドラッグイン（手動・1本）

ブラウザのアドレスバーやリンクを**キャンバスへドラッグ**するだけで URL カードになる
（前からある機能）。テキストの1行目が URL ならドロップでも同じ。

### ② リンクの受け皿（定点・1枚を更新し続ける）

**フィルタから既存の URL カードへ矢印を引いておく**と、実行のたびにフィルタの出力
テキストから最初の URL がそのカードに流し込まれる（新カードは増えない）。
「最新号のリンク」「今日のトップ記事」のような**定点リンク**に。
矢印引き出しメニュー「URLリンクを追加...」でその場に作って繋ぐのが早い。

- ラベルを付けていれば名前は保たれる（ラベルが URL のままなら新 URL に追従）。
- URL が変わると旧の取得系譜・更新マークは畳まれる（新しいページとして仕切り直し）。

### ③ URLカード化フィルタ（量産・テキスト→リンク集）

**URLカード化**（メニュー: Web）は、入力テキストの中の URL を**全部**拾って
1つにつき1枚の URL カードにする。定番レシピ:

**フィード取得 → 抽出（text_grep「^記事: 」）→ URLカード化** ＝ 記事のリンク集。
カード名は記事タイトルを引き継ぐ。再実行しても**出したことのあるリンクは増えない**
（消したリンクも復活しない — フィードの既読と同じ流儀）。

できた URL カードは普通の URL カードなので、Tip 10 の「更新を確認」や
web_fetch（本文の実身化）にそのまま繋がる。

### 量を制御する（設定2つ）

- **対象リンク**: すべて／ページ（HTML）／画像／音声・動画・ファイル。ニュースページを
  丸ごと通すと数十枚になるので、欲しい種類だけに絞るとよい（分類は URL の拡張子）。
- **カード名**: 既定で**リンク先のページタイトル**を軽量取得して付ける（先頭だけ読む・
  本文は取り込まない）。同一サイトへは間隔を空けるため件数が多いと時間がかかる —
  急ぐときは「取得しない」（URL のファイル名になる）。
- 増えすぎたカードは**フロー矢印ごと選択**（つながりを選択／矩形選択）でまとめて
  移動・削除できる。

### URL カードから先へ（取り出す・実身化する）

- URL カードの**右端ハンドルから矢印を引けば**、URL がテキスト（1行）として次の
  フィルタに渡る（Tip 10 と同じ実行契約）。空きキャンバスに落とせばその場に
  フィルタを作って繋げる。
- **画像リンクの URL カードは、右クリック「再取得（新しい実身を作る）」で画像の
  実身カードになる**（HTML 以外の直リンクはそのままの形式で実身化 — Tip 9 の規則。
  取得系譜も付くので「更新を確認」も効く）。CSV・PDF なども同じ。
  まとめてやるなら URL カード群 → ページ取得（web_fetch）を繋いで▶。
