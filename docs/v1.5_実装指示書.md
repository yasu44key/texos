## WS-B: ジョブレジストリ（v1.5.0）

### 目的（why の要約・詳細は凍結仕様 §4）
singleton（同時1つを物理強制する AppState フィールド群）を JobId キーの台帳に置き換える。
= 中央 kill スイッチ（`cancel_all`）の獲得・WS-C 並行解禁の土台。

### スコープ（やる）

1. **git 準備**: ✅ **済（2026-07-05）** — `v1.4-stable` ブランチを 59ac27a（release: v1.4.30）に
   作成し push 済み。WS-B スレッドは main でそのまま作業を始めてよい。
2. **Jobs 台帳**（凍結仕様 §12.B の型を実装）:
   - `Jobs { map: Mutex<HashMap<JobId, Arc<Job>>> }` を AppState に追加。JobId = プロセス内連番
     （`AtomicU64`）。ジョブは揮発（凍結 §11.5・永続化しない）。
   - `Job { id, kind: JobKind(Flow|Chat), label, started_at, cancel: AtomicBool,
     control: StdinSlot, project_root: String }`。`project_root` は**束縛の形だけ**
     （記録のみ・検査/撤廃は WS-C）。
3. **singleton 撤廃**: AppState の `flow_cancel` / `chat_cancel` / `rec_stdin` / `flow_running` を
   削除し台帳へ移送。参照は 19 箇所（lib.rs 9・flow_run.rs 4・ai.rs 3・runtime/ollama.rs 2・
   proc.rs 1。シンボル grep: `flow_cancel|chat_cancel|rec_stdin|flow_running|RunningGuard|ensure_no_flow_running`）。
4. **コマンド改修（一気置き換え・併設なし）**:
   - `run_flow` は**完了同期返しを維持**（`#[tauri::command(async)]` のまま）。起動時に Job 登録＋
     **`job:started {job_id, kind, label}` を emit**、完了/失敗で **`job:done` / `job:failed {job_id}`**
     （WS-C 全規格の先行最小3種。progress は WS-C）。フロントは job_id をこれで受け取り以後の制御に使う。
   - `break_flow(job_id)`・`flow_send_stdin(job_id, text)`・チャット中断も Job.cancel 経由
     （チャット起動時も Job 登録）。新設 `list_jobs()`・`cancel_all()`（＝中央 kill。
     `taskkill /T` ツリー kill は既存流用）。
5. **同時実行ルール（WS-B の間は従来同等）**: kind=Flow は同時1（実行中なら**ロック前に**従来文言で
   即拒否＝flow_run.rs:441 のガードの台帳版）・Chat は現状どおり単一・Flow と Chat は相互並行可。
   `ensure_no_flow_running` は「台帳に Flow ジョブが存在するか」の判定に置換（呼び出し側の挙動不変）。
6. **プロジェクト切替ガード維持**（撤廃は WS-C。2026-07-05 ユーザー決定）: project.rs / objects.rs の
   `ensure_no_flow_running` 呼び出し箇所は挙動不変。
7. **t2i 生成の中断を実効化**（ユーザー指摘: 現状は最後まで走るか、エラーまで止まらない）:
   - `python/t2i_server.py` に **/abort エンドポイント**を追加（ThreadingHTTPServer なので生成中も
     受けられる）。生成に step コールバック（diffusers `callback_on_step_end`）を渡し、abort フラグを
     検査して中断（例外 or pipeline の interrupt）。中断後もデーモンは次のリクエストを受けられること。
   - Rust 側（runtime/t2i.rs・t2i 実行ノード）: `Job.cancel` 検知で `/abort` を POST。
8. **UI 最小改修**: 「フロー実行中…」1行パネルに **Stop-all ボタン**（`cancel_all` 呼び出し）を追加。
   フロントは `job:started` の job_id を保持して `break_flow` / `flow_send_stdin` に渡す
   （背景ジョブパネルは WS-C）。

### 非目標（WS-B ではやらない）

- 並行解禁（同時N）・資源セマフォ・背景ジョブパネル・`job:progress` の全面規格化（→ WS-C）。
- セットアップ系（whisper DL・uv 環境構築・Ollama 導入・t2i デーモン起動）のジョブ化（→ WS-C。
  方針メモ 2026-07-05: インストール中は**当該カードの使用不能化＝ファイルロック程度の軽い保護**で
  よい・DL中に他の作業ができることが目的）。
- プロジェクト切替ガードの撤廃（→ WS-C）。ジョブの永続化（恒久にやらない＝凍結 §11.5）。

### touchpoint（v1.4.29 のモジュール分割後）

lib.rs（AppState・RunningGuard・ensure_no_flow_running）／flow_run.rs（run_flow のガード・
break_flow・flow_send_stdin）／ai.rs・runtime/ollama.rs（chat_cancel）／proc.rs（StdinSlot）／
runtime/t2i.rs＋python/t2i_server.py（中断）／フロント: App.tsx（実行中パネル・job:started 購読・
Stop-all）・チャットUI（中断ボタンの job_id 化）。

- **スコープ 1〜8 実装完了**（cargo test 35件緑・tsc 緑。実機確認→リリースは本表参照）。

  v1.4.14（2026-07-01）で `/cancel`＋`callback_on_step_end`＋`pipe._interrupt` として実装済みと
  判明（本書起票時の把握漏れ）。今回の実効化の中身は①中断後に diffusers が返す**部分画像の破棄**
  （execute_node の Ai/T2i 分岐で cancel 検知→「中断されました」エラー化。従来は中途半端な

  `flow_send_stdin`（Job.control）は録音停止ボタンの実体かつ凍結仕様 §7.1 の汎用制御チャネル
  （将来の一時停止/再開の共通口）なので存続。**シェルカードへの GUI stdin 公開はしない**
  （スロットを開くのは record:true のジェネレータのみ＝v1.4.9 設計のまま。シェルは
  ウィンドウ自体が入力面・hidden は非対話）。

## WS-C: 資源セマフォ＋背景ジョブパネル（v1.5.2）— 詳細（2026-07-07 着手時に詳細化）

### 目的（why の要約・詳細は凍結仕様 §5〜§8・§11・§12.C）

並行解禁の目標像（2026-07-05 ユーザー）: 「**画像生成のような重い処理が1本走っている間に、
他のフローの編集・実行・通常作業ができる**」。資源ごとの調停（セマフォ＝ヒューズと同一機構）と
背景ジョブパネル（中央 kill スイッチの表面）で、並行を**資源許可が許す限り**解禁する。
同一フローの多重起動は**拒否のまま**（個人ツール想定・v1.4.10 再入エラーの一般化）。
ファイル共有サーバ経由の複数PC同時アクセスは想定外（V2.0系）。

### スコープ（やる）

1. **ResourceLimits**（凍結仕様 §6・§11.2〜11.3）を AppState に追加:
   - `heavy`: 重い外部プロセスの並行上限。既定 = `available_parallelism()`（下限2）。
     超過は**待つ（FIFO）**。待機ループは job.cancel を検査（待ち中も中断可能）し、
     待ち始めに `job:progress {note:"順番待ち…"}` を1回出す。
   - `ai`: **正規化エンドポイント**（trim・ホスト小文字・末尾`/`除去）単位のセマフォ。
     既定許可数 = 1。超過は**即拒否＋案内**。t2i デーモン（127.0.0.1:8765）も同じ機構に乗る。
     （エンドポイント別許可数の設定UIは将来。既定1で開始＝§11.3）
   - `device`: 入力デバイス名単位の排他（=1）。超過は**即拒否＋案内**。デバイス名は
     record ジェネレータの CMD から `audio="…"`（dshow）を抽出。抽出できなければ
     固定キー「既定デバイス」（安全側＝録音同士は常に排他）。
   - permit は RAII（Drop で release）。セマフォは Condvar＋チケットの自前 FIFO
     （std に Semaphore が無い・tokio に依存しない）。
2. **資源導出はノード単位**（凍結 §5「NodeKind＋spec から導出」の適用形）:
   eval_filter が execute_node を呼ぶ**直前に**そのノードの必要資源を取得し、実行終了で解放。
   - record ジェネレータ → device ／ Ai → ai(spec の endpoint) ／ T2i → ai(t2i エンドポイント)
   - External・非 record の Generator → heavy ／ Builtin → 取得なし
   - 1ノードが複数取る場合も**取得順序は device→ai→heavy 固定**（§12.D デッドロック防止）。
     ノードは実行中しか permit を持たない（収集フェーズの再帰では持たない）＝入れ子保持なし。
   - チャット（ai_chat_send）もストリーム中は ai permit を取得（フロー AI ノードと相互拒否＝
     同一エンドポイントは同時1）。
3. **並行解禁**: `register_flow_exclusive`（全 Flow 同時1）を撤廃し、**同一終端カード**の Flow が
   実行中のときだけ拒否する `register_flow(card_id)` へ。run_flow は `#[command(async)]`（既存）
   のままワーカースレッドで複数走る。フロントの二度押し抑止（flowRunningRef）も**カード単位**に。
4. **ジョブの起動元プロジェクト束縛（切替ガード撤廃の実体)**: run_flow / ai_chat_send は起動時に
   **ジョブ専用の SQLite 接続**（open_project_at(root)）を開き、評価・materialize・ログ更新の
   全 DB 接触をそれで行う（state.current に依存しない）。実行中にプロジェクトを切り替えても
   ジョブは起動元へ書き続ける（materialize は起動元へ）。
   - `db::open` に `busy_timeout` を追加（複数接続の書き込み競合を SQLite 側で吸収。WAL は既存）。
   - eval_filter / collect_context の with_db(state) 呼びはジョブ接続の直接参照へ戻す
     （v1.4.11 の短ロック規律は「UI と接続を分ける」ことで構造的に不要になる。UI の
     state.current はジョブ実行中も自由）。
   - **切替ガード撤廃**: new_project / open_project / open_project_object / open_origin_project の
     `ensure_no_flow_running` を削除。**send_selection_to_project だけは精密化して維持**＝
     「現在のプロジェクトに束縛された実行中ジョブがあるとき拒否」（カード移動はフロー評価中の
     構造破壊になるため。単なる切替と違い保護が要る）。
5. **materialize／seq 採番の直列化**（凍結 §11.4）: プロジェクトルート単位の採番ロックを
   AppState に持ち、run_flow の materialize＋seq 書き戻しブロックをロック内で行う
   （同一プロジェクトで並行フローが同じ固定名/連番へ書く競合の防止）。
6. **イベント規格化**（凍結 §7.2・§11.6）:
   - `job:started {job_id, kind, label, card?}` — **flow にも card（終端カードid）を載せる**
     （パネルが録音対応/停止コマンドを spec から引くため。chat は WS-B から搭載済み）。
   - `job:progress {job_id, note?, percent?}` — スロットル ~10/s（ジョブ別 last-emit 時刻）。
     発生源: eval_filter のノード実行開始（note=カード名）・heavy 順番待ち・セットアップ系の
     DL 進捗（既存個別イベントは併存＝ダイアログ用途のまま）。
   - `job:done` / `job:failed` は WS-B から搭載済み。**`job:stdout` は名前だけ予約**
     （現状の外部実行は stdout を {out}/null へ向けており生産者がいない。ライブ stdout の
     配管はモジュール実行（WS-M 以降）と一緒に設計）。
7. **t2i /cancel の的確化**: `Job.t2i_active`（生成 HTTP 中のみ true）を追加し、`break_flow` は
   対象ジョブが t2i 実行中のときだけデーモンへ /cancel を POST（並行時に他ジョブの生成を
   誤って止めない）。cancel_all は従来どおり無条件 POST（全部止めるのが目的）。
8. **セットアップ系のジョブ台帳化**（JobKind::Setup 追加）: whisper_install / whisper_install_ffmpeg /
   whisper_download_model / ai_install_ollama / ai_pull_model / t2i_download_model / python_build_env
   を台帳登録（job:started/done/failed を emit・パネルに出る・同一ラベルの Setup 実行中は二重起動拒否）。
   DL ループ（whisper 2種・ollama pull・t2i poll）は job.cancel を検査して**中断可能**に
   （.part 掃除つき）。winget 系（ffmpeg/Ollama 導入）と uv 環境構築は登録のみ・中断は非対応
   （プロセス wait 型。ベストエフォート）。
   - **インストール中カードの使用不能化**は「軽い保護でよい」（2026-07-05 方針メモ）＝
     コンポーネント不在による自然な失敗＋案内文言（1.4.6 既存）と、ダイアログ側の進捗表示で
     満たすものとする（専用ロック機構は作らない）。
9. **UI: 背景ジョブパネル**（凍結 §8）: 「フロー実行中…」1行パネルを実行中ジョブ一覧へ。
   各行 = 種別アイコン／ラベル／経過時間／進捗（note・percent）／**停止**（record 対応
   フローのみ・flow_send_stdin）／**中断**（break_flow=job.cancel。全 kind 共通）。
   最下部に **Stop-all**（cancel_all）。ジョブがある間だけ表示・プロジェクト切替後も残る
   （§6.3「最後の物理停止」）。テーマは --panel-* 変数追従（ビュワー系＝2026-06-26 方針）。
   マウント時に list_jobs で復元（イベント欠落保険）。
   - run_flow 完了時のフロント処理は「起動時と同じプロジェクトのときだけ」refresh／緑シグナル／
     UNDO 登録を行う（切替後に完了したジョブの結果は起動元プロジェクトを開き直すと見える）。

### 非目標（WS-C ではやらない）

- 同一フローの多重並行（拒否のまま）。エンドポイント別許可数の設定UI（既定1固定）。
- `job:stdout` のライブ配管（名前の予約のみ）。ジョブ間ストリーム＝モジュール実行と co-design。
- 作用クラスの門（人間ゲート）＝capability 層（凍結 §12.E）。ジョブの永続化・分散実行。
- 来歴（provenance）の拡張 — 緑シグナル＋relations の現状で足りる（凍結 §8 の記述は現状追認）。

## WS-P1: オペレーション層 Phase1（v1.5.3）— 詳細（2026-07-07 着手時に詳細化）

### 目的（why の要約・正本 = オペレーション層設計.md §5.4＋§6.1）

pull 評価に「経路の選択」を導入する土台。**IN 側だけの工事**（OUT はシングルのまま＝§5.1-3）で、
exit code 分岐・セレクタ・no-data・メモ化を eval_filter に織り込む。データモデルの変更は
relations.attrs 1本の migration に集約（NULL=無条件・接続順＝完全後方互換）＋ last_run 構造化の同乗。

### スコープ（やる）

1. **migration（db.rs・同じ号に2列）**: `relations.attrs TEXT`（JSON・NULL=従来）と
   `virtual_bodies.last_run TEXT`（JSON・§6.1 の構造化実行記録）。既存の
   「ALTER TABLE ... ADD COLUMN を握りつぶす」方式を踏襲。
2. **attrs の語彙（§5.4.2 の実装形）**: `{when, carry, port}`。
   - `when`: "success" | "failure" | "always"(既定=キー無し)。**ジョブ内評価結果**
     （上流の ok/exit・data有無）を読む揮発判定。
   - `carry`: 枝が取られたとき運ぶもの。既定=成功枝は上流出力（従来どおり）・
     **失敗枝の既定は "stderr"**（エラーメッセージ＝一級の語彙 §6.1。メタ認知カードの入力）。
     "input"=失敗したノードに入った入力を横流し（リトライ材料）・"none"=データを捨てて
     経路情報だけ通す（エッジ属性版ゲート）。
   - `port`: IN 順の明示（なし=created_at 接続順。並びは port 昇順→created_at）。
     `{inN}` の番号・セレクタの first-match 順がこれに従う。
3. **評価結果の一級化（EvalOut）**: eval_filter の返り値を
   `EvalOut { payloads, nodata, ok, exit, errors, failed_inputs }` へ。
   - **失敗の格下げはエッジが決める**: ノード実行エラーは report へ直接 push せず EvalOut.errors に
     持ち上げ、**消費側エッジ**が when=always なら従来どおり report.errors へ（後方互換）、
     when 付きなら経路選択の情報として黙って分岐する（§5.4.2）。
   - **no-data**: エラーでも空ファイルでもない第三の結果。上流 nodata は when に関わらず
     エッジ nodata（NULL伝搬）。spec に `nodata: "propagate"(既定) | "absorb"`。
     propagate=入力エッジに1つでも nodata があればノード自身 nodata（実行しない）／
     absorb=nodata エッジを落とし残りで実行（全滅なら nodata）。
   - `failed_inputs` = 失敗時の入力スナップショット（carry:"input" 用。失敗時のみ保持）。
4. **builtin:"select"（セレクタ・§5.4.1）**: NodeKind::Select 新設。実行はせず
   **port 順の first-match**（最初に「有データ」を返した枝の payloads を採用）。
   nodata 吸収を内包・全滅なら自分が nodata。execute_node には到達しない（eval 側で完結）。
5. **ジョブスコープメモ化（§5.1-5）**: `HashMap<card_id, EvalOut>` を run_flow / チャット1ターン
   ごとに持ち、複数下流が同じカードを pull しても実行は1回（録音・AI の二重実行バグ防止）。
   visited（循環検出）は従来どおり併用。
6. **last_run の構造化（§6.1）**: 評価した各フィルタカードに
   `{at, exit, ok, nodata, skipped, message}` を JSON で保存（ジョブ専用接続・短い UPDATE）。
   message = そのノードで起きたエラー文言（stderr 込み）。終端カードの memo 人間向けログは
   従来どおり併存。list_objects が last_run を返す（WS-P2 のウォッチャ・運用前評価の口）。
7. **エッジ条件の UI**: フロー矢印のクリックを「削除」から**小メニュー**へ
   （削除／通過条件=常に・成功時のみ・失敗時のみ／運ぶもの=既定・エラーメッセージ・
   失敗時の入力・なし(信号のみ)）。リンク矢印（kind='link'）はクリック=削除のまま。
   条件付き矢印は中点に小ラベル（「成功時」「失敗時」）を表示。
   新コマンド `set_relation_attrs`（JSON マージ・NULL 化で従来復帰）。
8. **IN 順の並べ替え第1段（§5.4.3 案①の第1段）**: カード右クリック「入力の順序 ...」→

  - fired_count は 1発火=1カウント（対象数は数えない）。書き戻しは serde flatten で未知キー温存。

    builtin キーを入れない・asList=events のカンマ区切り→配列）。作成/編集兼用化も同 PR。
  - 背景発火の結果表示: job:done でキャンバス refresh（緑シグナルは付けない・二重 refresh 無害）。
  - **既知の割り切り**: dev 版とリリース版が同じプロジェクトを同時に開くと両方のスケジューラが
    発火する（v1.5 は個人ツール前提）。スケジューラの last_fire は揮発＝再起動でリセット

## WS-M: モジュール（v1.5.6+ 目安）— 概要＋実装の刻み方（2026-07-07 Fable 事前整理）

> 正本 = 共有とモジュール設計.md **§8（境界=図形＋ロック）・§9（IN/OUT バーチャルカード）・
> §10（シリアライズと配布）**。設計は T1〜T3 で決着済み — 実装順と落とし穴だけここに書く。
> **2〜3リビジョンに割る**のを推奨。

### M1（v1.5.6 目安）: 図形ロック＋モジュール化＋IN/OUT カード

1. **図形「メンバーをロック」**（§8.1）: shapes に locked 列（migration）。ロック中は
   メンバーの**アウト不可**（図形外へのドラッグを弾く）・**イン警告**。メンバー判定は
   既存の「図形上のカード」当たり判定（重なり=所属・§8.2 非階層多重所属）。
2. **モジュール化コマンド**（図形右クリック）: またぎ矢印（境界を横切る flow）の位置に
   **IN/OUT バーチャルカード（kind='op'・op:"in"/"out"・§9.4）を自動挿入**し矢印を繋ぎ替え。
   手動設置も可（§9.1）。**溶解**=右クリックで IN/OUT を消して矢印を直結に戻す（§9.2）。
3. **OUT = ▶付き実行トリガー**（§9.3 受容体の最小形）: OUT の▶はさかのぼり pull 実行
   （run_flow_for の流用・結果カードが横に生まれる）。
4. 落とし穴: 仮身分裂（§8.3）は**後回しでよい**（ロック済み図形の重なり運用が生じてから）。
   IN/OUT は eval_filter で**透過**（op:"in"/"out" は素通しノード＝入力をそのまま返す）。

### M2（v1.5.7 目安）: ライブラリ＋配布

1. **1モジュール=1フォルダ**（§10.1）: AppData/modules/<name>/{module.json, blobs/}。
   module.json = カード列・矢印列（attrs 込み）・図形・相対座標。**実身は常にコピー同梱**
   （§10.2・巨大時は合計サイズ警告）。
2. **書き出し/取り込み**: 図形右クリック「ライブラリに登録」→ 展開はキャンバスメニュー
   「ユーザーのモジュール」。**ID は取り込み時に全再割当**（send_selection_to_project の
   id_map 方式をそのまま流用——実績のあるコード）。
3. **依存 = spec 自動収集＋初回実行アテンション**（§10.3）: module.json に requires
   （外部プログラム名・AI モデル名）を自動記録し、展開時に所在チェック→注意カードを添える。
4. **「全個人フィルタ・モジュールをプロジェクトへ書き出し」**コマンド（バックアップ代用・
   T3 決着）。
5. 配布 = プロジェクト zip（キャンバス展開済み）→受け手が「ライブラリに登録」（§10.1。
   専用配布機構は作らない）。

### WS-M の前提・接続点

- IN/OUT カードは WS-P2 の kind='op' 基盤の上に乗る（op:"in"/"out" は発火しない静的 op）。
- モジュール内の並行実行・ジョブ間ストリームは**塞がないだけ**（凍結 §12.E）。
