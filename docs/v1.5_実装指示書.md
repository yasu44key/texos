## 全体方針（2026-07-05 ユーザー決定）

1. **v1.4系はフリーズ**: **v1.4.30**（2026-07-05・コメントDel修正＋中間トーン8色）を安定版として
   残す。**WS-B の最初に `v1.4-stable` ブランチを v1.4.30 のリリースコミットに作成して push**。
   以後 main は v1.5 系列。
2. **v1.5.0 からスタート**。OSS 公開は v1.5 系から予定（インストーラはリポジトリに含めず
   GitHub Releases へ、の既定方針＝NEXT_SESSION.md 並走レーン）。
3. **内部コマンドAPIは一気に置き換え**（旧コマンド併設なし。凍結仕様 §12.B の「併設で吸収」は
   2026-07-05 改訂済み）。1.5系はマルチフロー・マルチタスク・V2.0 の MCP／複数ユーザー対応への
   **踏み台**——内部の形は遠慮なく変える。
4. **実装順: WS-B → WS-C → WS-P1 → WS-M**（依存順）。各WS完了ごとにリリース（実験リビジョン刻み。
   号数は目安・確定は `docs/更新履歴.md`）。リリース手順は従来どおり:
   実機確認 → 更新履歴記入 → `npm run release -- x.y.z` → commit/push。

## WS-B: ジョブレジストリ（v1.5.0）

### 目的（why の要約・詳細は凍結仕様 §4）
singleton（同時1つを物理強制する AppState フィールド群）を JobId キーの台帳に置き換える。
= 中央 kill スイッチ（`cancel_all`）の獲得・WS-C 並行解禁の土台。

### スコープ（やる）

1. **git 準備**: ✅ **済（2026-07-05）** — `v1.4-stable` ブランチを 59ac27a（release: v1.4.30）に
   作成し push 済み。WS-B スレッドは main でそのまま作業を始めてよい。
2. **Jobs 台帳**（凍結仕様 §12.B の型を実装）:
   - `Jobs { map: Mutex<HashMap<JobId, Arc<Job>>> }` を AppState に追加。JobId = プロセス内連番
     （`AtomicU64`）。ジョブは揮発（凍結 §11.5・永続化しない）。
   - `Job { id, kind: JobKind(Flow|Chat), label, started_at, cancel: AtomicBool,
     control: StdinSlot, project_root: String }`。`project_root` は**束縛の形だけ**
     （記録のみ・検査/撤廃は WS-C）。
3. **singleton 撤廃**: AppState の `flow_cancel` / `chat_cancel` / `rec_stdin` / `flow_running` を
   削除し台帳へ移送。参照は 19 箇所（lib.rs 9・flow_run.rs 4・ai.rs 3・runtime/ollama.rs 2・
   proc.rs 1。シンボル grep: `flow_cancel|chat_cancel|rec_stdin|flow_running|RunningGuard|ensure_no_flow_running`）。
4. **コマンド改修（一気置き換え・併設なし）**:
   - `run_flow` は**完了同期返しを維持**（`#[tauri::command(async)]` のまま）。起動時に Job 登録＋
     **`job:started {job_id, kind, label}` を emit**、完了/失敗で **`job:done` / `job:failed {job_id}`**
     （WS-C 全規格の先行最小3種。progress は WS-C）。フロントは job_id をこれで受け取り以後の制御に使う。
   - `break_flow(job_id)`・`flow_send_stdin(job_id, text)`・チャット中断も Job.cancel 経由
     （チャット起動時も Job 登録）。新設 `list_jobs()`・`cancel_all()`（＝中央 kill。
     `taskkill /T` ツリー kill は既存流用）。
5. **同時実行ルール（WS-B の間は従来同等）**: kind=Flow は同時1（実行中なら**ロック前に**従来文言で
   即拒否＝flow_run.rs:441 のガードの台帳版）・Chat は現状どおり単一・Flow と Chat は相互並行可。
   `ensure_no_flow_running` は「台帳に Flow ジョブが存在するか」の判定に置換（呼び出し側の挙動不変）。
6. **プロジェクト切替ガード維持**（撤廃は WS-C。2026-07-05 ユーザー決定）: project.rs / objects.rs の
   `ensure_no_flow_running` 呼び出し箇所は挙動不変。
7. **t2i 生成の中断を実効化**（ユーザー指摘: 現状は最後まで走るか、エラーまで止まらない）:
   - `python/t2i_server.py` に **/abort エンドポイント**を追加（ThreadingHTTPServer なので生成中も
     受けられる）。生成に step コールバック（diffusers `callback_on_step_end`）を渡し、abort フラグを
     検査して中断（例外 or pipeline の interrupt）。中断後もデーモンは次のリクエストを受けられること。
   - Rust 側（runtime/t2i.rs・t2i 実行ノード）: `Job.cancel` 検知で `/abort` を POST。
8. **UI 最小改修**: 「フロー実行中…」1行パネルに **Stop-all ボタン**（`cancel_all` 呼び出し）を追加。
   フロントは `job:started` の job_id を保持して `break_flow` / `flow_send_stdin` に渡す
   （背景ジョブパネルは WS-C）。

### 非目標（WS-B ではやらない）

- 並行解禁（同時N）・資源セマフォ・背景ジョブパネル・`job:progress` の全面規格化（→ WS-C）。
- セットアップ系（whisper DL・uv 環境構築・Ollama 導入・t2i デーモン起動）のジョブ化（→ WS-C。
  方針メモ 2026-07-05: インストール中は**当該カードの使用不能化＝ファイルロック程度の軽い保護**で
  よい・DL中に他の作業ができることが目的）。
- プロジェクト切替ガードの撤廃（→ WS-C）。ジョブの永続化（恒久にやらない＝凍結 §11.5）。

### touchpoint（v1.4.29 のモジュール分割後）

lib.rs（AppState・RunningGuard・ensure_no_flow_running）／flow_run.rs（run_flow のガード・
break_flow・flow_send_stdin）／ai.rs・runtime/ollama.rs（chat_cancel）／proc.rs（StdinSlot）／
runtime/t2i.rs＋python/t2i_server.py（中断）／フロント: App.tsx（実行中パネル・job:started 購読・
Stop-all）・チャットUI（中断ボタンの job_id 化）。

### 受け入れ基準

- cargo check / cargo test 緑（35件・ライブOllama要3件 ignored は従来どおり）・tsc 緑。
- 実機:
  1. フロー実行 → **Stop-all で停止**（外部コマンド・AI・録音・**t2i 生成**の各系統で確認。
     t2i は数ステップ以内に止まり、デーモンは次の生成を受けられる）。
  2. 録音の「停止」（'q' 送信＝flow_send_stdin の job_id 版）が従来どおり動く。
  3. チャット中断が従来どおり動く。フロー実行中にチャットが並行できる（従来どおり）。
  4. 同時2フロー起動は従来文言で即拒否。フロー実行中のプロジェクト切替も従来どおり拒否。
- リリース: `v1.4-stable` push 済み → 更新履歴 v1.5.0 記入 → `npm run release -- 1.5.0` → commit/push。

## WS-C: 資源セマフォ＋背景ジョブパネル（v1.5.1 目安）— 概要（着手時に本書へ詳細化）

- 正本 = 凍結仕様 §12.C（ResourceLimits・permit RAII・取得順序 device→ai→heavy・job:* 全規格化・
  progress スロットル ~10/s・背景ジョブパネル）。
- **並行解禁の目標像（2026-07-05 ユーザー）**: 「**画像生成のような重い処理が1本走っている間に、
  他のフローの編集・実行・通常作業ができる**」。同一フローの多重起動は**拒否のまま**（個人ツール
  想定・v1.4.10 再入エラーの一般化）。ファイル共有サーバ経由の複数PC同時アクセスは想定外（V2.0系）。
- セットアップ系ジョブの台帳化＋**インストール中カードの使用不能化**（ファイルロック程度）。
- プロジェクト切替ガード撤廃（ジョブは起動元プロジェクトに束縛・materialize は起動元へ）。

## WS-M: モジュール（v1.5.4+ 目安）— 概要

- 正本 = 共有とモジュール設計.md §8〜§10。内容: 図形「メンバーをロック」→ モジュール化コマンド
  （またぎ点に IN/OUT 自動付与）→ ライブラリ（AppData・**1モジュール=1フォルダ**=module.json＋blobs・
  実身コピー同梱・巨大時警告）→ IN/OUT バーチャルカード（kind='op' の op:"in"/"out"・溶解コマンド・
  OUT に ▶）→「全個人フィルタ・モジュールをプロジェクトへ書き出し」コマンド（バックアップ代用）。
- 仮身分裂（§8.3）はロック済み図形の重なり運用が生じてからでも可（本線の後に回してよい）。
