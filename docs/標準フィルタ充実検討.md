# 標準フィルタ充実検討 — ビルトイン／TexoS提供／ユーザー用意の線引き（2026-07-11）

[外部依存プログラム一覧.md](外部依存プログラム一覧.md)・[ユーザーズチップス.md](ユーザーズチップス.md) の続き。
「Unix の標準的なフィルタを充実させたい。ビルトインで持つか、外部プログラムで持つか。
pandoc / ffmpeg / Windows のカメラ・読み上げなど、いままでユーザー任せだったものを
TexoS 側で提供できないか。グループ単位で段階的に足せて、不要になれば消せること」の検討記録。

---

## 0. 合意事項（2026-07-11 議論の結果）

- **配布はミニマム・軽快を最優先**。この前提で以下を決定。
- **L1 第1候補（text_head / tail / sort / count / cut / convert）は標準装備**。grep（text_grep）と
  同等の位置づけでビルトイン組み込みし、そのまま配布する。
- **cat / diff / paste（集約系）も考え方としてはビルトイン対象**。実行系の拡張（入力1個制約の解除）が
  要るため、投入時期は別途判断。ここまでがビルトインの境界線。
- **pandoc / ffmpeg / whisper は従来どおり導入スクリプト支援（L3）**。新機構は作らない。
  t2i は別格（常駐デーモン＋モデル管理の専用機構）として現状維持。
- **旧L2「Windowsパック（JSON定義プリセット）」は方針変更 → OSアダプタ・ビルトイン**にする。
  builtin は共通名（例: `speak`）で持ち、実装内部で OS を見て切り替えるだけ
  （Windows=SAPI / macOS=say / Linux=espeak 等）。カード定義は OS 非依存に保たれ、
  プロジェクトの可搬性とマルチプラットフォーム方針に整合する。
- **今後は「追加したい機能のアイデアが出るごとに、この4層基準で分類して追加する」**。
  §2.5 の分類手順を判定チャートとして維持する。

## 1. 現状の棚卸し

### 実行系（コードで確認した事実）

- **ビルトイン**（`flow.rs run_builtin`）: `text_grep` / `text_replace` / `img_resize` / `img_convert` / `md_codeblock` の5種。
  入力は**必ず1個**（`flow_run.rs execute_node`: Builtin は inputs[0] のみ）。
- **特殊経路ビルトイン**: `ai`（Ollama）・`t2i`（diffusers デーモン）・`whisper`・`select`（実行なし・枝選択）。
- **外部フィルタ**: `name` を「指定パス → `.texos\filters`（プロジェクト同梱）→ PATH」の3段で解決（`flow::resolve_program`）。
- **フィルタライブラリ**（`filter_library.json`・アプリ共通）: 名前付き spec の登録・削除が既にある。
- **導入支援の実績**: Ollama（winget＋モデル取得）、whisper.cpp（バイナリ＋モデル自動DL → `%APPDATA%` 管理）、ffmpeg（winget 案内）。
- **UI**: `BuiltinFilterDialog.tsx` が builtin ごとのパラメータスキーマからフォーム自動生成。
  `preflight.rs:268` がビルトインの出力 MIME を静的検査用に列挙。

### 方針（既定のもの）

- 配布物（SampleProject.zip 等）に**サードパーティバイナリは同梱しない**（ライセンス・サイズ）。入手案内を添える。
- 設計理念:「OSS に乗る・全部自前で持たない」「軽量配布」。
- v2.0 でマルチプラットフォーム化 → **基盤は OS 非依存を保つ**（OS固有は外殻へ）。

## 2. 結論の骨子 — 「4層モデル」

「ビルトインか外部か」の二択ではなく、**提供の深さを4層**に分ける。
判定基準は「実装の小ささ×OS非依存性×ライセンス×更新頻度」。

| 層 | 何を配るか | 対象の性質 | 例 |
|---|---|---|---|
| **L1 ビルトイン** | Rust実装（アプリ本体） | 純関数・小実装・OS非依存・決定的 | text_sort, 文字コード変換 |
| **L2 OSアダプタ・ビルトイン** | Rust実装（内部でOS切替） | OS内蔵機能を呼ぶだけ・導入不要 | 読み上げ, カメラ |
| **L3 導入支援** | 検出＋winget/自動DL案内（既存機構） | 巨大・専門・更新が速いOSS | pandoc, ffmpeg, whisper |
| **L4 ユーザー用意** | ドキュメント（チップス）のみ | 環境依存が強い・用途が個別 | gcc, Python, nkf(→L1で不要化) |

- **バイナリは今後も配らない**。TexoS が配るのは「Rustコード（L1/L2）」と「導入支援ロジック（L3・既存）」。
  理念（自前で持たない・軽量）とライセンス方針を崩さずに「TexoS側で提供」できる。
- L2 の実体は「builtin の match アームの中で OS を見るだけ」。カード定義（spec）は全OS共通に保つ。

### 2.5 新機能の分類手順（アイデアが出たらここを通す）

0. **GPUで動く生成モデルか？** → 4層の外＝**G層（生成デーモン系・t2x ファミリー）**。
   → [生成カード群企画.md](生成カード群企画.md) へ（ai / t2i の仲間。3D・動画・音源など）。
1. **純関数で、Rust＋軽量クレートだけで書けるか？** → L1 ビルトイン（`text_*` 等）。
2. **OS に最初から入っている機能を呼ぶだけか？** → L2 OSアダプタ・ビルトイン
   （共通名の builtin、内部で OS 切替。未対応 OS では明確なエラー）。
3. **外部 OSS が必要だが、定番で入手経路が安定しているか？** → L3 導入支援
   （winget / 自動DL 案内。whisper / Ollama / ffmpeg の既存パターンを踏襲）。
4. **それ以外（環境依存が強い・用途が個別）** → L4 ユーザー用意
   （[外部依存プログラム一覧.md](外部依存プログラム一覧.md) に入手案内、
   [ユーザーズチップス.md](ユーザーズチップス.md) にレシピを追記）。

判定に迷ったら下の層に置く（軽い方に倒す）。後から上の層へ昇格させるのは容易
（L4→L3=導入支援を書く、L3→L1=Rustで再実装）だが、逆は既存カードを壊しうる。

## 3. L1: Unix標準テキストフィルタのビルトイン化（グループ `text_*`）

`text_grep` / `text_replace` と同型（&[u8] in → (bytes, ext, mime) out）で足せるもの。
Rust 標準＋既存クレートで完結し、外部依存ゼロ・全OS共通。**マルチプラットフォーム化の布石としても効く**
（外部バイナリ依存を増やさない方向）。

### 第1候補（実装小・需要確実）— ✅ 合意 → **実装済み（2026-07-11・v1.5.12後の作業ツリー）**

> 実装メモ: `text_head` / `text_tail` / `text_sort`（数値比較=compare:"number"・重複除去=unique:"remove"
> で uniq を吸収）/ `text_count`（wc） / `text_cut` / `text_convert`（auto は閲覧ビューと同じ
> BOM→UTF-8→chardetng 推定）。flow.rs run_builtin＋単体テスト・BuiltinFilterDialog スキーマ・
> preflight/model.ts の出力MIME・メニュー2系統（新規作成/矢印引き出し）に追加。
> §8論点1は「text_sort のオプションで uniq を吸収」で決着。

| builtin | Unix相当 | パラメータ案 | 備考 |
|---|---|---|---|
| `text_head` | head | lines（既定10） | |
| `text_tail` | tail | lines（既定10） | |
| `text_sort` | sort | order(asc/desc), numeric, unique | uniq の大半を吸収 |
| `text_uniq` | uniq | adjacent(隣接のみ)/global | sort+unique で足りるなら省略可 |
| `text_count` | wc | mode(lines/words/chars/all) | 出力はテキストレポート |
| `text_cut` | cut / awk '{print $n}' | delimiter(tab/comma/空白/任意), fields("1,3-5") | CSV/TSV列抽出。AI前処理に効く |
| `text_convert` | **nkf / iconv** | to(utf8固定でも可), from(auto/sjis/eucjp/…) | `encoding_rs`＋`chardetng`（共にMIT/Apache）。**入手性最悪の nkf を不要化**できる本命 |

### 第2候補（アーキテクチャ拡張が要るもの）— ✅ ビルトイン対象と位置づけ・投入時期は別途判断

- `text_concat`（cat 複数入力）・`text_diff`（diff 2入力）・`text_paste`（paste）:
  **ビルトインは現状「入力1個」固定**。集約は External（`{in*}`）だけの概念なので、
  ビルトインに集約フラグを足す拡張が要る（`is_aggregate` の Builtin 対応＋ `run_builtin` の複数入力版）。
  実装自体は小さいが実行系に手が入るので**第2段**。
- `text_split`（split・1入力→複数出力）: `NodeRun.outputs` は Vec なので受け皿はあるが、
  ビルトインで複数出力を返す前例がない。同じく第2段。
- sed 相当は `text_replace`（正規表現置換）が既にカバー。行アドレス指定等が欲しくなったら拡張。
- jq / xmllint 相当: 実装が膨らむ。まずは L4（外部 jq）で様子見。

### 実装時に必ず触る3点（新ビルトイン共通のチェックリスト）

1. `flow.rs run_builtin` に match アーム追加（＋単体テスト）。
2. `BuiltinFilterDialog.tsx` の `BUILTIN_SCHEMAS` にフォーム定義追加。
3. `preflight.rs`（±267）の出力 MIME 列挙に追加（静的検査が「不明」にならないように）。

### 「不要になったら削除」の考え方（L1）

ビルトインはバイナリサイズ・保守コストがごく小さいので、**コードは消さず「メニューでの見せ方」で制御**する。
新規作成メニューを「テキスト」「画像」「AI/メディア」等のグループに畳み、設定で
グループの表示 on/off を持てば十分（既存カードは表示 off でも動き続ける＝過去プロジェクトを壊さない）。

## 4. L2: OSアダプタ・ビルトイン（読み上げ・カメラなど）✅ 方針変更で合意

当初案は「動作確認済みの定義（JSON）を Windows パックとして配る」だったが、
**各OSに代替機能があるので、OS を見て切り替えるビルトインにする**方針へ変更。
「OS の機能を使って実現するか」のスイッチが builtin 実装の中にあるだけで、
カード定義（spec）は全 OS 共通 — プロジェクトの可搬性が保たれる。

| builtin 案 | Windows | macOS | Linux |
|---|---|---|---|
| `speak`（テキスト読み上げ） | SAPI（PowerShell `System.Speech`） | `say` | `espeak` 等 |
| `camera`（カメラ起動） | `start microsoft.windows.camera:` | Photo Booth / `imagesnap` | 環境依存（未対応エラーでも可） |
| ほか候補 | クリップボード出し入れ・`explorer /select`・ファイルハッシュ 等 | 対応相当 | 対応相当 |

- 実装は run_builtin の match アーム内で `cfg!(target_os)` / 実行時判定により分岐。
  未対応 OS では「この環境では使えません」を明確に返す（黙って失敗しない）。
- fire-and-forget（出力なしで完結）は実行系対応済みなので camera 系はそのまま乗る。
- 「基盤は OS 非依存」の原則に対しては、**OS 差を builtin の内側に閉じ込める**ことで整合
  （V2.0 マルチプラットフォーム検討の「外殻」を builtin 実装内に局所化した形）。

## 5. L3: 導入支援（pandoc / ffmpeg / whisper）✅ 従来どおり維持で合意

whisper セットアップダイアログ・Ollama 導入・ffmpeg winget 案内という**既存の導入スクリプト支援を
そのまま続ける**。新機構は作らない。t2i は常駐デーモン＋モデル管理を持つ別格の専用機構として現状維持。

- pandoc をこの列に加える場合も同じパターン: `check_filter_program`（既存）で存在確認 →
  未導入なら「winget install JohnMacFarlane.Pandoc」を案内。
  ⚠️ md→PDF は LaTeX が別途要る点は案内に明記。
- （将来案・棚上げ）動作確認済みのフィルタ定義そのものを配りたくなったら、定義＋依存を JSON に
  まとめた「パックマニフェスト」→ `filter_library.json` への一括登録/削除という形が使える。
  登録・削除の器（`save_filter_library` / `delete_filter_library`）は既にあるので、
  必要になった時点で足せばよい。今は必要になっていない。

## 8. 未決の論点

1. `text_sort + unique` で `text_uniq` を省くか（ビルトイン数を絞るか、Unix の語彙に忠実にするか）。
2. P2（集約系 cat/diff/paste）の投入時期 — v1.5 熟成期間中に入れるか、v2.0 側に回すか。
3. OSアダプタ・ビルトインの第1弾を何にするか（speak が最有力か。camera は Linux 対応が薄い）。
4. ビルトインが増えたときのメニュー構成 — グループ折りたたみ（テキスト/画像/AI・メディア/OS）と
   表示 on/off をどこに置くか（設定ダイアログ vs メニュー内トグル）。
