## 0. ビジョン（全体像）

キャンバスに置ける「ちょっとしたアプリ」＝ウィジェット。例: アナログ時計／ミニ電卓／
Webデータモニタ／カメラ。さらにユーザーの狙いは **レゴブロックのように組む個人ワークフロー
の可視化** —— 例「時計 → カレンダ → ToDoリスト → Google へエクスポート」を、データの流れと
**動き（dynamics）ごとキャンバス上で見える化**する。

到達点の段階：
- **V2.0**: 共通インターフェースを持つウィジェットモジュールをカードとして埋め込む。
  オートフロー（フィルタ）と同じノードグラフに乗せ、データ束縛で「生きたダッシュボード」化。
- **V3.0+**: 外部アプリの画面をキャンバスのウィンドウにフィードバックし、**組み込まれた
  アプリのように見せる**。最終的には **OS ネイティブのインターフェースの置き換え** につながる
  （デスクトップ/シェルの再発明 ＝ データ関係性で表現する作業環境）。
  - 種は既にある: フィルタの**ジェネレータ機能で出力をファイルにすれば、普通に OS アプリを
    起動できる**。あとは「起動したアプリの画面をキャンバス窓に取り込む」ピースが加われば、
    埋め込みアプリ体験になる。

## 1. 概念面

### 1.1 ウィジェット＝フィルタの「インタラクション版」
- フィルタ = データ → データ（変換）。ウィジェット = データ → 見た目／操作 → データ（描画・入力）。
- 両者は同じ「**ポートを持つノード**」: 入力ポート・出力ポート・設定・本体。
  → キャンバス全体が **フィルタ＋ウィジェット＋データの統一ノードグラフ**になる。
- これがユーザーの言う「共通インターフェースのモジュール」の正体。電卓も「2入力＋1出力の
  ノード」と見ればフロー部品として再利用できる。

### 1.2 3概念モデル（実身/仮身/関係）への収まり
新テーブルを足さない（`カード統一モデル検討結果.md` の原則）:
- **ウィジェット本体（コード/manifest）= 実身**（CAS、`codec_ref`/`ui_contract` で参照）
- **設置した1個 = `kind='widget'` の仮身**。設定・状態は仮身の JSON 列（`filter_ref` と同作法）
- **同じ時計を3つ = 1実身を指す3仮身**（実身/仮身の二重性そのもの）
- **データ供給 = `relations kind='flow'`**（フィルタと同じ配線）
- ビューア（コンテンツ束縛のウィジェット）と独立ウィジェット（時計等）は **同一機構**。
  ui_contract を「コンテンツに束縛された／されないウィジェット」の共通契約に統一する。

### 1.3 能力（capability）のスペクトラム ← 設計の肝
例は1種類ではない。必要な"力"で分け、宣言された分だけ host が許可する設計に。

| 種別 | 例 | 必要能力 | 信頼度 |
|---|---|---|---|
| 自己完結・生成系 | 電卓・ロジック | 計算のみ | 安全（無条件配布可）|
| 時間系 | アナログ時計・カレンダ | システム時刻 | 安全 |
| データ束縛系 | Webモニタ・グラフ・ゲージ | ネット（許可ドメイン）/ flow入力 | 要許可 |
| デバイス系 | カメラ・マイク | ハード権限 | 要明示許可 |
| 外部アプリ埋め込み（V3.0）| 任意アプリの画面取込 | プロセス起動＋画面キャプチャ | 最高リスク |

## 2. 技術面

### 2.1 実行・サンドボックス（候補）
- **(推奨) サンドボックス iframe ＋ postMessage ケイパビリティ・ブリッジ ＋ manifest**
  - 各ウィジェット = HTML/JS バンドル。`sandbox` 属性＋CSP で隔離。
  - host が postMessage 越しに「時刻」「fetch（許可ドメイン）」「flow入出力」「camera権限」を
    **宣言された分だけ**注入。Web技術の時計/電卓/モニタが大量流用でき、Tauri/React と好相性。
  - **V2.0 の現実解**。
- **Wasm（`ui_contract`/codec_ref の既定路線）**: 隔離最強・移植性高。UI描画は面倒。
  重い計算コア/コーデックに向く。**iframe と併用**（UIはiframe、重処理はWasm）が落としどころ。
- **ネイティブ Tauri command**: デバイス/高速処理に要るが移植性とサンドボックスを壊す。最小限。

### 2.2 ウィジェット契約（manifest / ui_contract 案）
- メタ: 名前・アイコン・バージョン・既定サイズ
- 宣言能力: none / time / network:domains[] / device:camera / storage / flow-in / flow-out
- ポート: 入力ポート（型つき）・出力ポート（データ/イベント）
- 設定スキーマ（永続・Undo対象）
- ライフサイクル: init(props/state) → render → on_input → emit_output → resize → suspend/resume

### 2.3 V3.0「外部アプリの画面フィードバック」
- ジェネレータ→ファイル→OSアプリ起動（**今できる**）を起点に、起動アプリの window を
  キャプチャ/合成してキャンバス窓へ描画 → 埋め込みアプリ風。
- 技術前提（要調査）: ウィンドウキャプチャ（OS依存）、入力フォワード、レイテンシ、
  プロセス管理。OS依存が重いので `src-tauri/src/win/` 隔離方針（`カード統一モデル §3`）に乗せる。

## 3. ユーザビリティ

### 3.1 レゴ的ワークフロー合成（中核体験）
- 「時計 → カレンダ → ToDo → Google エクスポート」のように、**部品を線でつなぐだけ**で
  個人ワークフローが組め、**データの流れと動きが見える**。
- 入力ウィジェット（スライダー/フォーム/ボタン）→ フローへ出力 → 下流のフィルタ/ウィジェットを
  駆動。双方向化で「自作の小さな道具」が無限に作れる。
- フィルタ＋ウィジェットの統一ノードグラフだから、既存のフロー実機（矢印・自動実行・
  ドロップポイント）がそのまま使える。

### 3.2 ライブダッシュボード
- グラフ ← パイプライン出力、モニタ ← ソースをポーリング。データが流れて常時更新。
- 他のキャンバスツールに無い TexoS 固有の価値（静的な付箋ボードではなく**動く作業環境**）。

### 3.3 ライフサイクルと資源
- 時計は刻む・モニタはポーリング・カメラは配信 → 「**表示中だけ active／畳むと停止**」＋
  個数/レート上限（50個置いても溶けない）。既存の展開/折りたたみモデルに乗せる。

### 3.4 配布・信頼
- v1.5 フィルタライブラリと同じく「**ウィジェット・レジストリ**」。
- 同梱の安全枠（時計・電卓・カレンダ）＋ opt-in の危険枠（ネット/デバイス/外部アプリ）。
- capability 宣言があるので、レビュー/信頼モデルを段階的に作れる。

## 4. 段階導入（ドラフト）

1. **同梱の安全ウィジェット数個**（時計・電卓・メモ）を ui_contract 契約上で実装 ＝ 契約を固める
2. **データ束縛ウィジェット**（グラフ・ゲージ）をオートフローに接続 ＝ ライブダッシュボード実証
3. **入力ウィジェット**（フローへ出力）＝ 双方向化・レゴ合成の本格化
4. **ネット/デバイス系・コミュニティ配布**（capability＋レジストリ）
5. **(V3.0) 外部アプリ画面フィードバック** ＝ 埋め込みアプリ体験 → OS インターフェース置換へ
