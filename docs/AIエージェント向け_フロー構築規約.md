# TexoS フロー構築 規約（AI エージェント依頼用 指示書）

> **これは何か**: TexoS のキャンバス上に**カードと矢印でできた仕組み（フロー）を組み立てる**
> ための規約。「TexoS で○○する仕組みを作って」と AI に依頼するとき、**この文書をそのまま添付**する。
> 設計（どんなカードを何枚、どう繋ぐか）は自由。ただし**実行モデルと配線規約にだけは必ず従うこと**。
>
> 姉妹編＝`docs/カード化プログラム作成規約.md`（あちらは「1枚のカードの中身」、こちらは「カードの並べ方」）。
> 足場＝`scripts/texos_flow.py`（このビルダーを使えば規約違反は例外で弾かれる）。
> 初版 2026-08-08。実例＝`F:\yoshi\Documents\TexoS\AI合議判断` / `…\AI設計審査`。

---

## 0. なぜこの文書が要るか

TexoS の実行モデルは、キャンバスを見ただけでは分からない。実際に組んでみると、
**ソースを読まないと踏み抜く罠が複数ある**（§3）。ここを外すと、動くには動くが
意図と違うものができる — 例えば AI カードに資料を2枚繋ぐと、まとめて読むのではなく
**AI が2回別々に走る**。

だから、この規約の目的は「TexoS の使い方」ではなく、
**エージェントが1周で正しく組み上げるための最小の契約**を渡すことにある。

---

## 1. 実行モデル — 終端から遡る（pull 評価）

TexoS のフローは**押す（push）のではなく引く（pull）**。

- ユーザーが押すのは**終端カードの ▶ 1つだけ**。
- そこから矢印を逆に遡って上流を再帰的に評価し、必要なものだけを実行する。
- 途中のカードの出力は**メモリ上のペイロード**として下流へ渡るだけで、**ファイルにはならない**。
- **ファイルになるのは、そのとき実行した終端カードの出力だけ。**

この帰結が2つ:

1. **中間カードを個別に ▶ することもできる。** そのカードが終端になり、そこまでの
   上流だけが走って、そのカードの出力がファイルになる。
   → 「全部通す」と「途中だけ見る」が同じグラフで両立する。これは設計上の武器。
2. **出力ファイル名は、終端カードの `prefix` だけが決める。** 中間カードの
   `prefix` は、そのカードを単独実行したときにだけ効く。

---

## 2. データモデル（最小限）

プロジェクト＝**フォルダ**。その中に `.texos/texos.db`（SQLite）と `.texos/cas/`。
実ファイルはフォルダ直下に普通に置かれる。スキーマの正本は `src-tauri/src/db.rs` の `migrate()`。

### カードの種類（`virtual_bodies.kind`）

- `file` — ファイルカード（実身／仮身）。フローでは**中身がそのまま入力**になる。
- `filter` — 処理カード。`filter_ref` に FilterSpec（JSON）を持つ。正本＝`src-tauri/src/flow.rs`。
- `note` — コメント付箋。**定数カード**でもある（§3-5）。
- `url` / `folder` / `project` / `op` / `launcher` — 今回の用途では通常使わない。

実身（コミット済みファイルカード）は `committed_path` と `origin_path` の**両方**を実ファイルに
向け、`committed_mtime` も入れる（`objects.rs` の `import_file` と同じ形にする。ここを外すと
編集検知や「仮身に戻す」のガードが狂う）。

### 矢印（`relations`）

- 実行の矢印は `kind='flow'`。
- **集約カードへの入力の並び順は `created_at` 昇順**。挿す順序が意味を持つ（§3-3）。

## 3. 落とし穴（実測で踏んだもの。ここが本体）

### 3-1. AI カードは入力ごとにファンアウトする ★最重要

`builtin:"ai"` の transform モードは**集約ノードではない**。入力を N 本繋ぐと、
**N 回別々に実行**され、出力も N 個できる。「議題と参考資料をまとめて読ませる」つもりの
配線が、「議題だけで1回」「資料だけで1回」になる。

複数の材料を1回で読ませたいときは、**必ず前に `text_concat`（束）カードを挟む**。

```
資料A ─┐
資料B ─┼→ [text_concat] → [AI]        ← 正しい
資料C ─┘
```

なお、複数入力を「資料」として文脈注入する `collect_context` は
**chat モード専用**（`ai.rs`）で、transform では使われない。

**副次効果**: 束カードは邪魔者ではなく、**「その判断が何を材料にしたか」の記録**になる。
キャンバス上で束を開けば、AI が実際に読んだものがそのまま見られる。

**例外＝役割ポート（v1.8）**: `role:"system"` を付けた矢印だけは**入力に数えない**ので、
束を挟まずに直結してよい（§3-9）。

### 3-9. 役割ポート — システムプロンプトを付箋から渡す（v1.8）

矢印に `attrs = {"role":"system"}` を付けると、上流の中身が
**AI カードのシステムプロンプト**として渡される（カード自身の `system` を上書き）。

```
  ┌──────────────┐
  │ 役割：批判担当 │─── 役割 ───┐
  │ 弱点とリスク… │            ▼
  └──────────────┘      ┌────────────┐
      （付箋）  審査票 ─▶│  AIカード  │─▶
                         └────────────┘
```

- 役割つきの矢印は**通常入力に数えない**＝ファンアウトを起こさない。束を挟まなくてよい。
- `when` / `carry` は適用されない（役割は条件分岐の対象ではなく直結の配線）。
- AI カード以外に繋いでも効かない（実行レポートに「AI カードにだけ効きます」と出る）。
- 1枚の AI カードに役割の矢印は1本まで。

**なぜ使うか**: AI カードの一番重要な中身＝役割が、これまで JSON ダイアログの中に隠れていた。
役割を付箋にすると、**誰がどんな担当なのかがキャンバスから読めて、その場で書き換えられる**。
合議のような多視点グラフでは、これがあるかないかで読みやすさが決定的に変わる。

### 3-10. 記録カード（`builtin:"tap"`）— 途中を残す（v1.8）

§1 のとおり、**中間カードの出力はファイルにならない**。1周流したあとのグラフには
構造だけが残り、中身は消える。記録カードを矢印の途中に置くと、データはそのまま
下流へ通しながら、通った中身を**固定名で上書き保存**してカードにする。

- 名前は `prefix`（未指定ならカードのラベル）。出力先は `out_dir` があればそこ、無ければ直下。
- 素通しなので入力は何本でもよく、ファンアウトしない。入力2本目以降は `_2`, `_3` が付く。
- 2回目以降は同じカードの中身を差し替える（カードは増えない）。

エージェントの仕事を人が検証できるようにするための道具なので、
**判断が切り替わる場所（判定・反証・確定の前後）には置いておくとよい**。

反復カードの中に置いた記録カードは、**周ごとに `_1` `_2` … が付く**（3-11）。
固定名のままだと各周が次の周に上書きされて消えるため。

### 3-11. 反復カード（`builtin:"loop"`）— 練り直しを描く（v1.8）

§1 の pull 評価は DAG が前提で、矢印の輪はエラーになる。つまりこの記法では
**「直してもう一度」がそもそも言えなかった**。反復カードは、上流のサブグラフを
条件が満たされるまで**引き直す**ことでこれを可能にする。

```
   お題（付箋）──┐
                  ▼
            ┌──────────┐    ┌────────┐    ┌──────┐    ┌────────┐
            │   束     │───▶│ AI推敲 │───▶│ 記録 │───▶│  反復  │──▶ 結論
            └──────────┘    └────────┘    └──────┘    └────────┘
                  ▲                                        │
                  └──────── 役割＝前周の結果 ───────────────┘
```

- **戻り矢印**＝反復カードから上流のカードへ引き、`attrs = {"role":"previous"}` を付ける。
  実行時はそこを「1周前の出力」が流れる。**1周目だけは空**（no-data ではないので下流は止まらない）。
- **この矢印は評価で遡らない**。値は反復カードが実行文脈に置いたものを読むだけ。
  だから**絵は輪に見えても pull は DAG のまま**＝循環エラーにならず、pull 解決の中核にも触らない。
- 戻り矢印は**入力に数える**（材料だから）。AI カードへ直接戻すと資料と合わせて2本＝
  ファンアウトする（3-1）。**戻し先は束カードにする**のが定石。
- 止まり方は2つ: `max_rounds`（**ヒューズ・必須**。未指定3・上限50に丸める）と
  `until`＋`pattern`（その周の出力テキストに対する決定的な判定。
  `contains` / `not_contains` / `regex` / `not_regex` / `empty` / `not_empty`）。
- 反復カードの出力＝**最後の周の結果**。途中の周を読みたいなら中に記録カードを置く。

**なぜ「循環を許す」のではなくこの形か**: 実行経路が人に見えるグラフであることが TexoS の
理念（`V2.0課題.md §8-1`）で、pull 評価に分岐や循環を持ち込むと両方の枝を辿るなどの
破れが出る。反復を**1枚のカードの内部実装**に閉じ込めれば、グラフは DAG のままで
可視性・再現性が崩れない。停止判定もカード内部の制御であって「グラフの分岐」ではない。

### 3-12. 問い合わせカード（`builtin:"ask"`）— 途中で人に聞く（v1.8）

人が口を挟めるのは、これまで**前（付箋を書く）か後（出力を読む）だけ**だった。
問い合わせカードを置くと、実行の途中で人の判断を待てる。

**入る矢印は2種類**（ここが読み取れず実機で迷ったので明示する・2026-08-08）:

```
   下書き(AI) ──── ふつうの矢印（材料＝何について聞くか）────▶ ┌────────┐
                                                              │ 問い合わせ │──▶ 答え
   答えの付箋 ──── 役割＝答え（ここに書いたものが答え）──────▶ └────────┘
```

- 答えは **`role:"answer"` の矢印で繋いだ付箋**に書く。付箋の中身が答え。
  **付箋は自分で用意して先に繋いでおける**（そのほうが面から読める。用意していなければ
  最初の実行で自動生成される）。用意する付箋は**空か `>` 行だけ**にすること
  ——素の行を書くとそれが答えになる。
- **答えが空のあいだは no-data**＝そこから先へ進まない（エラーではない）。
  人が書いて ▶ を押し直すと通る。
- 付箋がまだ無ければ、**最初の実行で自動的に作られて矢印まで引かれる**。
  中身は質問と、そのとき届いていた材料、そして**使い方の注釈**が **`>` の引用**で入っている
  （引用行は答えとして読まない＝注釈を書いても「答えたこと」にならないので、
  案内は付箋に置いたまま残る）。
- 出力は**答えの文字列だけ**。材料も下流へ渡したいなら連結カードで束ねる。
- 通常入力は「質問の文脈」。無くてもよい（入力0でもエラーにしない）。

**注意（案B の性質）★**: 問い合わせカードは、**既定では答えが書いてあっても上流を評価する**。
つまり再実行のたびに上流の AI も走り直し、**人が読んだ案とは別の文面が下流へ行く**。

**対策①＝スイッチを入れる（v1.8.1・こちらが簡単）**: spec に `"skip_upstream": "on"`
（設定フォーム「答えが入ったら」→「上流を動かさない（聞いたときのまま）」）。
答えが入っているあいだは**上流を1枚も評価せず**答えだけを流す（AI も呼ばれない）。
答えを消せばまた上流から動く。`texos_flow.py` なら `ask(..., skip_upstream=True)`。

```python
ask("方針を聞く", question="どちらで進めますか", skip_upstream=True)
```

- **AI の出力について人に聞くフローでは、原則こちらを付ける。** 付けないと2パス目に
  原案が作り直され、人が読んで判断した案と別物が下流へ行く。
- 逆に「毎回いまの上流を見たうえで答えだけ差し替えたい」なら付けない（既定のまま）。
- 例 → `scripts/build_sample_human_decision.py`（課題に人の判断を挟む・2パス）。

**対策②＝答えたときの案を実身で固定する**（実機で踏んだ・2026-08-08）。
スイッチが無かった頃の配線レシピ。**人が書き出したファイルを手で直したい**ときは
いまでもこちらが要る（スイッチは上流を止めるだけで、材料を編集可能にはしない）:

```
  下書き(AI) ──▶ 記録 ──▶ [下書き控え.md]          ← 記録が作る実身カード
       │                        │
       └──▶ 問い合わせ ──┐      └──▶ 束（1本目）    ← ここを繋ぐ
                          └────────▶ 束（2本目）
```

- **束に繋ぐのは記録カードではなく、記録が作った実身カードのほう**。
  記録カードの矢印は「その実行で通った中身」を流すが、実身カードは**ファイルの今**を読む。
  だから前回の実行で書き出された案がそのまま材料になり、**人が手で直した編集も効く**。
- 逆に言うと、**記録カードが書き出したファイルを編集しても、記録カードの矢印には反映されない**
  （記録は書き出し専用で読み返さない。しかも次の実行で上書きされる）。
- 矢印を引き直したら**束を右クリック →「入力の順序 ...」**で並べ直すこと。
  順番は繋いだ順（`created_at`）なので、後から引いた矢印は最後尾になる（§3-3）。

### 3-2. 集約ノードは限られている

- 内蔵: `text_concat` / `text_diff` / `text_paste` の3つだけ（`flow.rs: builtin_is_aggregate`）。
- 外部コマンド: `cmd` に `{in*}` か `{in2}` 以降があれば集約、`{in}`/`{in1}` だけならファンアウト。
- それ以外（AI・t2i 等）は全部ファンアウト側。

### 3-3. 集約の入力順は「矢印を作った順」

`relations.created_at` 昇順。**先に繋いだものが1本目**。
束の1本目に「元の問い」「前提」を置くと、下流が文脈を見失いにくい（§4-3）。

### 3-4. `prefix` と `seq` で出力名が決まる

- `prefix` あり・`seq` なし → **`prefix.拡張子` で固定名・毎回上書き**。反復実行に向く。
- `prefix` あり・`seq` あり → `prefix1.ext`, `prefix2.ext` … と連番。
- `prefix` なし → `入力名_フィルタ名.ext`。
- 繰り返すが、**効くのは実行した終端カードの `prefix` だけ**。

### 3-5. 付箋は「定数カード」— パラメータの置き場に最適

`kind='note'` をフローに繋ぐと、本文が `text/plain` として流れる（`flow_run.rs`）。
つまり**設定値・前提・重み付けを付箋に書いて繋げば、キャンバス上でダブルクリックして
書き換えるだけで挙動が変わる**。JSON を編集させる必要がない。

人間に見せたい説明の付箋（繋がない）と、パラメータの付箋（繋ぐ）が同じ見た目で
共存する点は、利点でもあり混乱の元でもある。**繋ぐ付箋は見出しを「〜（ここを書き換える）」等に
して見分けをつける**こと。

### 3-6. 制限時間は「未指定＝無制限」

`timeout_secs` は未指定または `0` で無制限（`flow.rs: gen_timeout`）。
ローカル LLM は分単位かかるので、AI カードでは**指定しない**のが正解。

### 3-7. 型チェックで黙って飛ばされる

矢印は `accept_mime` で検査される。AI カードは `text/*`。
合わない入力は**エラーにならず「スキップ」**され、結果だけが静かに変わる。
テキスト系に統一するか、前段に変換フィルタを置く。

### 3-8. TexoS が開いている間に DB を書かない

外から `.texos/texos.db` に書いても、起動中の TexoS は自分の接続を持っているので
**UI には反映されない**。プロジェクトを開き直す必要がある。
**組み立ては TexoS を終了した状態で行う**こと。

## 4. 多視点・多段判断を組むときの設計則

実際に「AI 合議」「設計審査」を組んで、通しで走らせて分かったこと。

### 4-1. 並行（横）は「別コンテキスト」でなければ意味がない

1つのプロンプトで「4つの視点で考えて」と頼むと、4つの意見は**同じ文脈の中で
互いに条件づけられて生成される**ので、必ず整合の取れた穏当な話に収束する。
独立した反対意見を出すには、**別々のカード＝別々の呼び出し**にするしかない。
これはモデルの賢さではなく配線の問題であり、TexoS でやる意味の中心にある。

### 4-2. 垂直（縦）は「答えの上でもう一段考える」

横＝同じ問いを別の基準で切る。縦＝**出てきた答えそのものを次の段の入力にする**。
効いた縦の段は2種類:

- **前段の縦**: 問いそのものを立て直す（前提・対象・重み付けを適用した問いに書き換える）。
- **後段の縦**: 判定 → その判定を疑う → 確定。

### 4-3. 枠は「持ち回る」— 離れると溶ける ★

前提（対象ユーザー・重み付け）を固定する段と、それを消費する段が離れるほど、
途中で枠が溶ける。実測では、最終段が前提を見失って
「ターゲット層が未決定である」と言い出した（前提で確定済みなのに）。

**対策: 束カードで枠を毎回一緒に運ぶ。** 下流の束の1本目に、常に前提（審査票）を入れる。

### 4-4. 迎合対策を入れると、反対側へ迎合する ★

意図的にバイアスを入れて「迎合していないか」を検査する段を足したところ、
最終段が**反証を全件「認めた」**で処理した。バイアス迎合を潰したら反証迎合になっただけ。

**対策: 中間段の処理を2値にしない。** 「認めた／退けた」ではなく
**「認めた（結論を変える）／認めた（条件に反映）／退けた」**の3値にし、
さらに「全件認容ならそれは迎合の疑いがある、と自己申告せよ」と書く。

### 4-5. 確信度は理由を要求しないと演出になる

小型モデルは平然と「確信度: 高」と書く。
**「確信度と、その確信度になった理由を一文で。理由の無い確信度は書かない」**と指定すると、
急に中身のある不確実性の申告になる。

### 4-6. 実測の目安

Ollama `gemma4:latest`（8B）で AI カード1枚あたり **13〜23秒**。
7段構成のフルパスで **約120秒**（モデルロード済み）。初回はロードに +90秒。
重い判断のときだけ、特定の1枚（反証など）を大きいモデルにすると、
入れ替えが1回で済んで効率がよい。

## 5. 組み立て方 — `scripts/texos_flow.py`

生 SQL を書かない。ビルダーを使う。**規約違反は `save()` で例外になる。**

```python
import sys; sys.path.insert(0, r"<repo>\scripts")
from texos_flow import Project

p = Project(r"F:\...\新しいプロジェクト", model="gemma4:latest")

議題   = p.file("議題.md", "# 議題\n...", 0, 300, memo="ここを書き換える")
重み   = p.note("重み付け（ここを書き換える）\n...", 0, 520)
役割   = p.note("役割：批判担当\n弱点とリスクだけを書く…", 400, 60)
束     = p.cat("束 材料", 400, 400, prefix="05_材料")
判定   = p.ai("判定", 700, 400, system="", temperature=0.2, prefix="判定")
記録   = p.tap("記録：判定", 1000, 400, prefix="途中_判定")

p.flow(議題, 束); p.flow(重み, 束)      # ← 繋いだ順 = 束の中の順
p.flow(束, 判定)
p.flow(役割, 判定, role="system")       # ← 役割ポート（入力に数えない）
p.flow(判定, 記録)
p.shape(380, 340, 620, 220, "束ねてから渡す")
p.view()
p.save()
```

`save()` は検証したうえで、終端カードと**実行すると出来るファイル名**を印字する。

主な API: `file()` `note()` `ai()` `cat()` `tap()` `ask()` `loop()` `builtin()`
`flow(…, role=)` `shape()` `view()` `save()`。

問い合わせ（3-12）は `p.ask(...)` と `p.flow(付箋, 問い合わせ, role="answer")`。
答え矢印を付箋以外から引いたり、相手が問い合わせカードでなければ例外になる
（間違えると答えたつもりでいつまでも止まったままになる）。実物は `scripts/build_ask_demo.py`。

反復（3-11）を組むときは、戻り矢印の**戻し先を束にする**（AI へ直接戻すとファンアウトする）:

```python
束   = p.cat("束（お題＋前周）", 520, 60, prefix="材料")
推敲 = p.ai("推敲", 520, 240, system="", prefix="案")
記録 = p.tap("各周の記録", 520, 420, prefix="各周")     # 反復の中なので 各周_1, 各周_2 …
反復 = p.loop("反復", 520, 600, max_rounds=3, until_contains="合格")

p.flow(お題, 束)                        # 1本目＝毎周変わらない前提（枠は持ち回る・§4-3）
p.flow(反復, 束, role="previous")       # 2本目＝前周の結果（1周目は空）
p.flow(束, 推敲); p.flow(推敲, 記録); p.flow(記録, 反復)
```

ビルダーは戻り矢印を**循環として数えない**（評価が遡らないため）が、
反復カード以外から `role="previous"` を引いたら例外にする。
戻り矢印が1本も無い反復カードは警告（同じ処理を繰り返すだけになるため）。
実物は `scripts/build_loop_demo.py`（`カード実験_反復` を組む手本）。

## 6. 納品前に必ずやること

**組んだだけで終わりにしない。1周走らせて、出力を読むこと。**

`§4-3`（枠が溶ける）も `§4-4`（反証迎合）も、グラフを眺めていても分からず、
**実際に流して出力を読んで初めて分かった**。プロンプト設計の欠陥は静的には見えない。

- ローカル Ollama が動いていれば、TexoS を起動しなくても pull 評価は再現できる
  （`file`/`note` を読み、`text_concat` を連結し、AI カードは `/api/chat` に投げる）。
- 出力一式は `試走結果_YYYY-MM-DD/` のような**サブフォルダ**に置く。
  プロジェクト直下に置くと、TexoS の「新規カードを登録」の対象になって紛らわしい。

## 7. この文書の位置づけと、その先

現在の形（規約 + Python ビルダー）は**足場**であって最終形ではない。
本来あるべきは、`docs/共有とモジュール設計.md §2` の
**フローモジュール＝名前付きの再利用可能な部分グラフ**を、宣言的なファイル
（モジュール JSON）として TexoS 自身が読み書きすることである。そうなれば:

- **人間**は「モジュールを読み込む」だけでよい（カードを並べる必要がない）。
- **エージェント**は SQLite にもスキーマにも触れず、宣言だけを書けばよい。
  §3 の落とし穴の大半（3-1〜3-4, 3-8）が**そもそも触れない領域**に隠れる。
- 配布物（`SampleProject.zip`）に「仕組み」を同梱できる。

つまり **§3 が短くなるほど、TexoS の設計は正しい方向に進んでいる**。
この文書の落とし穴の項目数は、モジュール機構の未整備度をそのまま測っている。

> **実際に減った例（v1.8）**: §3-9 役割ポートと §3-10 記録カードは、落とし穴として
> 書かれていたものを**機能で消した**追加である。役割ポートは 3-1（ファンアウト回避のため
> 束を挟む）の一部を不要にし、記録カードは 3-4（中間出力はファイルにならない）の
> 痛みを直接埋める。§3 に項目が増えているように見えるが、中身は「守るべき制約」から
> 「使える道具」へ移っている。この移し替えを続けるのが正しい進み方。
