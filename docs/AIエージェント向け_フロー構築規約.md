# TexoS フロー構築 規約（AI エージェント依頼用 指示書）

> **これは何か**: TexoS のキャンバス上に**カードと矢印でできた仕組み（フロー）を組み立てる**
> ための規約。「TexoS で○○する仕組みを作って」と AI に依頼するとき、**この文書をそのまま添付**する。
> 設計（どんなカードを何枚、どう繋ぐか）は自由。ただし**実行モデルと配線規約にだけは必ず従うこと**。
>
> 姉妹編＝`docs/カード化プログラム作成規約.md`（あちらは「1枚のカードの中身」、こちらは「カードの並べ方」）。
> 足場＝`scripts/texos_flow.py`（このビルダーを使えば規約違反は例外で弾かれる）と
> `scripts/texos_dryrun.py`（TexoS を起動せずに試走して、納品前に出力を読む）。
> 初版 2026-08-08。実例＝`F:\yoshi\Documents\TexoS\AI合議判断` / `…\AI設計審査`。

## 0. なぜこの文書が要るか

TexoS の実行モデルは、キャンバスを見ただけでは分からない。実際に組んでみると、
**ソースを読まないと踏み抜く罠が複数ある**（§3）。ここを外すと、動くには動くが
意図と違うものができる — 例えば AI カードに資料を2枚繋ぐと、まとめて読むのではなく
**AI が2回別々に走る**。

だから、この規約の目的は「TexoS の使い方」ではなく、
**エージェントが1周で正しく組み上げるための最小の契約**を渡すことにある。

### 0-1. 受け取ったエージェントが最初にやること（4項目）

初めての環境では、この順で**確認してから**組む。ここを飛ばすと、
「組めたが動かない」フローを納品することになる。

1. **足場があるか** — この文書と**2つのスクリプトで1組**。手元に無ければ人に貰う。
   - `texos_flow.py` … 組む（§5）。**生 SQL でカードを作ろうとしないこと**。
     置き場所はどこでもよく、`sys.path` に足して import する。
   - `texos_dryrun.py` … 組んだものを TexoS 無しで1周流す（§6）。
2. **どこに作るか** — いま開いているプロジェクトは §2-0 で分かる。
   ただし**そこへ直接足さない**。新しいフォルダに1つのプロジェクトとして組み、
   親には入口を1枚貼る（§5-2）。フォルダは無ければ作られる。
3. **AI カードを使うなら、モデルを実機で確認する**（§2-1）。
   マニュアルの例のモデル名を写して済ませない。
4. **組んだら1周流して、出来たファイルを読む**（§6）。
   終端が完走しても中身が欠けることがある（§3-14）。

### 0-2. 手本がある — 事典とレシピ集

**組む前にこの2つを見ること。** どちらも TexoS のプロジェクト（＝SQLite）なので、
人は開いて読め、エージェントは DB を読めばカードの設定（`filter_ref` の JSON）が
そのまま手に入る。**ソースを読みに行く必要はない。**

- **カードカタログ** `…\TexoS\カードカタログ`
  カードの種類を1枚ずつ「押せる標本」にしたもの。サンプル入力の付箋が繋いであり、
  ▶ を押せば挙動が見られる。同じ内容の一覧が **`カード事典.md`** に入っている
  （エージェントはまずこれを読む）。分類は テキスト／集約／生成／記法／口／自動発行／
  情報収集／画像／OS機能／外部。
  生成元は `scripts/build_card_catalog.py` — **UI のスキーマ表から機械生成**しているので、
  カードが増えたら流し直せば追いつく（手書きの事典は次のリリースで嘘になる）。

  後半に **データの見本**が26形式ぶん入っている（画像6・音4・動画2・文書6・表と構造5・
  3D と書庫）。各カードのメモに **MIME ／ カードの上で見えるか ／ どのカードに繋がるか**
  が書いてある。**繋ぐ前にここを見ること** —— 型が合わない入力は
  エラーにならず黙って飛ばされる（§3-7）。特に間違えやすいのは:
  - **PDF・docx・xlsx は `text/*` ではない。** AI に読ませたいなら pandoc で変換してから。
  - **`.xml` は `application/xml`。** 面の上ではテキストとして開けて編集もできるのに、
    **`text/*` のカードには通らない**（UI の判定と矢印の判定が別規則）。要注意。
  - `.csv` `.tsv` `.json` は `text/*` のカードが受ける（json は特例扱い）。

- **レシピ集** `…\TexoS\レシピ集`
  目的別の実例18本（AIに聞く／答えを Word に／AIにコードを書かせて実行／多視点AI／
  人の判断を挟む／反復／Web要約／フィード絞り込み／文字起こし／読み上げ／
  プロンプト自動生成＋画像生成／画像変換／画像→3D／音の切り出し／動画→GIF／
  テキスト集計／ランチャー／文字コード変換）。
  外部プログラムの引数は**実際に動いていたものをそのまま写してある**。
  生成元は `scripts/build_recipe_book.py`。

**やりたいことに近いレシピがあるなら、そこから始めるのが速い。**
枠（図形）ひとつが1レシピで、左の付箋に「何ができるか／要るもの／出典」が書いてある。

## 1. 実行モデル — 終端から遡る（pull 評価）

TexoS のフローは**押す（push）のではなく引く（pull）**。

- ユーザーが押すのは**終端カードの ▶ 1つだけ**。
- そこから矢印を逆に遡って上流を再帰的に評価し、必要なものだけを実行する。
- 途中のカードの出力は**メモリ上のペイロード**として下流へ渡るだけで、**ファイルにはならない**。
- **ファイルになるのは、そのとき実行した終端カードの出力だけ。**

この帰結が2つ:

1. **中間カードを個別に ▶ することもできる。** そのカードが終端になり、そこまでの
   上流だけが走って、そのカードの出力がファイルになる。
   → 「全部通す」と「途中だけ見る」が同じグラフで両立する。これは設計上の武器。
2. **出力ファイル名は、終端カードの `prefix` だけが決める。** 中間カードの
   `prefix` は、そのカードを単独実行したときにだけ効く。

## 2. データモデル（最小限）

プロジェクト＝**フォルダ**。その中に `.texos/texos.db`（SQLite）と `.texos/cas/`。

### 2-0. どのプロジェクトに組むか — 人に聞かなくていい

「いま開いているプロジェクト」は設定ファイルから分かる。**人にパスを尋ねる必要はない。**

- Windows: `%APPDATA%\com.yoshi.texos\config.json`
- macOS: `~/Library/Application Support/com.yoshi.texos/config.json`
- Linux: `~/.config/com.yoshi.texos/config.json`

この JSON の `"last"` が最後に開いたプロジェクト（`recent[0]` も同じ）。
ビルダーなら `texos_flow.current_project()` が返す。

ただし**そこへ直接カードを流し込んではいけない**。既に人が並べたカードがあり、
座標がぶつかるうえ、同じスクリプトを2回流すと二重になる。正しい形は §5-2。
実ファイルはフォルダ直下に普通に置かれる。スキーマの正本は `src-tauri/src/db.rs` の `migrate()`。

### 2-1. AI カードのモデルは、実機を見てから決める ★

**マニュアルに書いてあるモデル名をそのまま写してはいけない。** 例に出てくる
`gemma4:latest` はこの文書を書いた環境の話で、相手の PC に入っている保証はない。
`model` が無い／存在しないモデルを書いたフローは、組めても実行時に落ちる。

手順はこれだけ:

1. **Ollama（既定・`provider:"ollama"`、エンドポイント既定 `http://localhost:11434`）**
   - `ollama list`、または `curl http://localhost:11434/api/tags`
2. **LM Studio / OpenAI 準拠（`provider:"lmstudio"`、既定 `http://localhost:1234/v1`）**
   - `curl http://localhost:1234/v1/models`
3. どちらも応答しなければ **LLM が動いていない**。勝手に決め打ちせず、
   「どのモデルを使いますか（Ollama なら `ollama pull <名前>` が要ります）」と**人に1回だけ聞く**。
   聞けない状況なら、フローは組んだうえで**モデル名を書いた付箋を添えて未確定だと明示する**。

複数あるときの選び方は §4-6 — 基本は軽いモデルを全体に使い、
**重い判断をする1枚だけ**大きいモデルにする（入れ替えが1回で済む）。

### 2-2. この規約そのものを AI に食わせるとき（自己構築）★

TexoS の中の AI カードにこの文書を渡して、**フローを組む Python を書かせる**ことができる
（実物＝`scripts/build_self_build.py` が組む「AI自己構築」プロジェクト）。
2026-08-26 に実機で通したときの数字と、そこで要る設定:

- **文書の大きさ** — 42KB ≒ **約 10.9k トークン**（Ollama の `prompt_eval_count` 実測）。
- **コンテキスト長は既定でよかった** — Ollama 0.33 は載るだけ自動で広げる。
  実測 `ollama ps` の CONTEXT は **32768**（27B・Q4_K_M・RTX3090 で 100% GPU）。
  つまり規約1万＋依頼＋生成2千で収まる。**ただし TexoS の AI カードは `num_ctx` を
  送っていない**（`flow.rs` は `temperature` だけ）ので、コンテキストは
  **Ollama 側の既定に完全に依存する**。小さいモデル／VRAM が足りない環境では
  黙って詰められる。疑ったら `ollama ps` の CONTEXT 欄を見ること。
- **thinking モデルでよい** — Ollama は思考を `message.thinking` に分けて返し、
  TexoS が読む `message.content` は綺麗なまま（qwen3.8 で確認）。
  v1.8.6 からは AI カードに `think`（`"on"` / `"low"` / `"medium"` / `"high"`）を書けば
  こちらから思考を要求できる。対話カードは思考を折りたたみで表示するだけで、
  **会話履歴にも MDログにも残さない**（次ターンへも送らない）。変換カードは思考を出力から
  必ず除去する。`think` を書かないモデル任せの場合でも、本文に混ざった
  `<think>…</think>` は常に取り除かれる。
- **GPU の使い方** — v1.8.6 で `gpu` を追加（`"max"`＝全層を GPU へ強制／`"cpu"`＝GPU を
  使わない）。**既定は書かない**のが正解で、そのとき Ollama が VRAM に載る層だけ GPU に
  置く。VRAM 量を理由に CPU へ落とす既定は廃止した（少 VRAM でも GPU の方が速い）。
- **役割（system）に置くべきもの** — 規約は1万トークンあり、真ん中の決まりは薄れる。
  効かせたい約束（出力は ```python 1ブロックだけ・骨格・使ってよい API・出力先）は
  **短く役割の付箋に書く**（§3-9）。規約は資料として束の1本目に置く。
- **実測** — 規約 10.9k tok を読んで 2.2k tok のスクリプトを書くのに **約55秒**。

**生成した Python をそのまま流して実行させないこと。** 「案を作る」終端と
「実行する」終端の**あいだに実身カードを1枚挟む**（§3-12 対策②）。一本の矢印で繋ぐと、
実行の ▶ が上流の AI を走らせ直し、**人が読んだ案とは別のスクリプトが走る**。

### カードの種類（`virtual_bodies.kind`）

- `file` — ファイルカード（実身／仮身）。フローでは**中身がそのまま入力**になる。
- `filter` — 処理カード。`filter_ref` に FilterSpec（JSON）を持つ。正本＝`src-tauri/src/flow.rs`。
- `note` — コメント付箋。**定数カード**でもある（§3-5）。
- `op` — 素通しの口。`{"op":"in"}`＝IN（入口）、`{"op":"out"}`＝OUT（出口・**▶を押せる終端になれる**）。
  `real_id` は `op:empty`、MIME は `application/vnd.texos.op`。
  トリガ/タイマ/ウォッチャも `op` だが、あちらは pull ではなく**リクエスト（発行）レーン**で、
  フローの評価には出てこない。
- `url` / `folder` / `project` / `launcher` — 今回の用途では通常使わない
  （`project` だけは §5-2 で使う）。

実身（コミット済みファイルカード）は `committed_path` と `origin_path` の**両方**を実ファイルに
向け、`committed_mtime` も入れる（`objects.rs` の `import_file` と同じ形にする。ここを外すと
編集検知や「仮身に戻す」のガードが狂う）。

### 矢印（`relations`）

- 実行の矢印は `kind='flow'`。
- **集約カードへの入力の並び順は `created_at` 昇順**。挿す順序が意味を持つ（§3-3）。
- **▶ を押すと、終端カードから出来た出力カードへ `flow` の矢印が生える。**
  つまり「出ていく矢印が無い＝終端」は、**1回でも流したあとのプロジェクトでは成り立たない**。
  終端を探すなら「下流に処理カード（`filter`/`op`）があるか」で見ること（2026-08-21 実機）。

## 3. 落とし穴（実測で踏んだもの。ここが本体）

### 3-1. AI カードは入力ごとにファンアウトする ★最重要

`builtin:"ai"` の transform モードは**集約ノードではない**。入力を N 本繋ぐと、
**N 回別々に実行**され、出力も N 個できる。「議題と参考資料をまとめて読ませる」つもりの
配線が、「議題だけで1回」「資料だけで1回」になる。

複数の材料を1回で読ませたいときは、**必ず前に `text_concat`（束）カードを挟む**。

```
資料A ─┐
資料B ─┼→ [text_concat] → [AI]        ← 正しい
資料C ─┘
```

なお、複数入力を「資料」として文脈注入する `collect_context` は
**chat モード専用**（`ai.rs`）で、transform では使われない。

**副次効果**: 束カードは邪魔者ではなく、**「その判断が何を材料にしたか」の記録**になる。
キャンバス上で束を開けば、AI が実際に読んだものがそのまま見られる。

**例外＝役割ポート（v1.8）**: `role:"system"` を付けた矢印だけは**入力に数えない**ので、
束を挟まずに直結してよい（§3-9）。

### 3-9. 役割ポート — システムプロンプトを付箋から渡す（v1.8）

矢印に `attrs = {"role":"system"}` を付けると、上流の中身が
**AI カードのシステムプロンプト**として渡される（カード自身の `system` を上書き）。

```
  ┌──────────────┐
  │ 役割：批判担当 │─── 役割 ───┐
  │ 弱点とリスク… │            ▼
  └──────────────┘      ┌────────────┐
      （付箋）  審査票 ─▶│  AIカード  │─▶
                         └────────────┘
```

- 役割つきの矢印は**通常入力に数えない**＝ファンアウトを起こさない。束を挟まなくてよい。
- `when` / `carry` は適用されない（役割は条件分岐の対象ではなく直結の配線）。
- AI カード以外に繋いでも効かない（実行レポートに「AI カードにだけ効きます」と出る）。
- 1枚の AI カードに役割の矢印は1本まで。

**なぜ使うか**: AI カードの一番重要な中身＝役割が、これまで JSON ダイアログの中に隠れていた。
役割を付箋にすると、**誰がどんな担当なのかがキャンバスから読めて、その場で書き換えられる**。
合議のような多視点グラフでは、これがあるかないかで読みやすさが決定的に変わる。

### 3-10. 記録カード（`builtin:"tap"`）— 途中を残す（v1.8）

§1 のとおり、**中間カードの出力はファイルにならない**。1周流したあとのグラフには
構造だけが残り、中身は消える。記録カードを矢印の途中に置くと、データはそのまま
下流へ通しながら、通った中身を**固定名で上書き保存**してカードにする。

- 名前は `prefix`（未指定ならカードのラベル）。出力先は `out_dir` があればそこ、無ければ直下。
  **`out_dir` に絶対パスを書かないこと**（v1.8.3〜）。フォルダ欄は「空欄＝プロジェクト
  フォルダ／相対＝プロジェクト基準／絶対＝そのまま」で解決される。相対で書けば
  プロジェクトごと移動・配布しても壊れない（ウォッチャの `path`、「新規カードを登録」の
  `path` も同じ規約）。絶対パスは「本当にプロジェクトの外を指したいとき」だけ。
- 素通しなので入力は何本でもよく、ファンアウトしない。入力2本目以降は `_2`, `_3` が付く。
- 2回目以降は同じカードの中身を差し替える（カードは増えない）。

エージェントの仕事を人が検証できるようにするための道具なので、
**判断が切り替わる場所（判定・反証・確定の前後）には置いておくとよい**。

反復カードの中に置いた記録カードは、**周ごとに `_1` `_2` … が付く**（3-11）。
固定名のままだと各周が次の周に上書きされて消えるため。

### 3-11. 反復カード（`builtin:"loop"`）— 練り直しを描く（v1.8）

§1 の pull 評価は DAG が前提で、矢印の輪はエラーになる。つまりこの記法では
**「直してもう一度」がそもそも言えなかった**。反復カードは、上流のサブグラフを
条件が満たされるまで**引き直す**ことでこれを可能にする。

```
   お題（付箋）──┐
                  ▼
            ┌──────────┐    ┌────────┐    ┌──────┐    ┌────────┐
            │   束     │───▶│ AI推敲 │───▶│ 記録 │───▶│  反復  │──▶ 結論
            └──────────┘    └────────┘    └──────┘    └────────┘
                  ▲                                        │
                  └──────── 役割＝前周の結果 ───────────────┘
```

- **戻り矢印**＝反復カードから上流のカードへ引き、`attrs = {"role":"previous"}` を付ける。
  実行時はそこを「1周前の出力」が流れる。**1周目だけは空**（no-data ではないので下流は止まらない）。
- **この矢印は評価で遡らない**。値は反復カードが実行文脈に置いたものを読むだけ。
  だから**絵は輪に見えても pull は DAG のまま**＝循環エラーにならず、pull 解決の中核にも触らない。
- 戻り矢印は**入力に数える**（材料だから）。AI カードへ直接戻すと資料と合わせて2本＝
  ファンアウトする（3-1）。**戻し先は束カードにする**のが定石。
- 止まり方は2つ: `max_rounds`（**ヒューズ・必須**。未指定3・上限50に丸める）と
  `until`＋`pattern`（その周の出力テキストに対する決定的な判定。
  `contains` / `not_contains` / `regex` / `not_regex` / `empty` / `not_empty`）。
- 反復カードの出力＝**最後の周の結果**。途中の周を読みたいなら中に記録カードを置く。

ビルダーでは停止条件は `until_contains=` の1語で書く（spec の `until`/`pattern` を束ねたもの）。
**戻し先は束にする** —— AI へ直接戻すと資料と合わせて2本＝ファンアウトする:

```python
束   = p.cat("束（お題＋前周）", 520, 60, prefix="材料")
推敲 = p.ai("推敲", 520, 240, prefix="案")
記録 = p.tap("各周の記録", 520, 420, prefix="各周")     # 反復の中なので 各周_1, 各周_2 …
反復 = p.loop("反復", 520, 600, max_rounds=3, until_contains="合格")

p.flow(お題, 束)                        # 1本目＝毎周変わらない前提（§4-3）
p.flow(反復, 束, role="previous")       # 2本目＝前周の結果（1周目は空）
p.flow(束, 推敲); p.flow(推敲, 記録); p.flow(記録, 反復)
```

**なぜ「循環を許す」のではなくこの形か**: 実行経路が人に見えるグラフであることが TexoS の
理念（`V2.0課題.md §8-1`）で、pull 評価に分岐や循環を持ち込むと両方の枝を辿るなどの
破れが出る。反復を**1枚のカードの内部実装**に閉じ込めれば、グラフは DAG のままで
可視性・再現性が崩れない。停止判定もカード内部の制御であって「グラフの分岐」ではない。

### 3-12. 問い合わせカード（`builtin:"ask"`）— 途中で人に聞く（v1.8）

人が口を挟めるのは、これまで**前（付箋を書く）か後（出力を読む）だけ**だった。
問い合わせカードを置くと、実行の途中で人の判断を待てる。

**入る矢印は2種類**（ここが読み取れず実機で迷ったので明示する・2026-08-08）:

```
   下書き(AI) ──── ふつうの矢印（材料＝何について聞くか）────▶ ┌────────┐
                                                              │ 問い合わせ │──▶ 答え
   答えの付箋 ──── 役割＝答え（ここに書いたものが答え）──────▶ └────────┘
```

- 答えは **`role:"answer"` の矢印で繋いだ付箋**に書く。付箋の中身が答え。
  **付箋は自分で用意して先に繋いでおける**（そのほうが面から読める。用意していなければ
  最初の実行で自動生成される）。用意する付箋は**空か `>` 行だけ**にすること
  ——素の行を書くとそれが答えになる。
- **答えが空のあいだは no-data**＝そこから先へ進まない（エラーではない）。
  人が書いて ▶ を押し直すと通る。
- 付箋がまだ無ければ、**最初の実行で自動的に作られて矢印まで引かれる**。
  中身は質問と、そのとき届いていた材料、そして**使い方の注釈**が **`>` の引用**で入っている
  （引用行は答えとして読まない＝注釈を書いても「答えたこと」にならないので、
  案内は付箋に置いたまま残る）。
- **先に用意した付箋にも、実行のたびに材料が入る**（v1.8.4）。だから
  「判断するために別のカードを開きに行く」必要はない —— 答えを書く付箋の中に、
  そのとき何が届いていたかが引用で載る。人が書いた案内は消えない（目印より下は人の領分）。
  引用は 40 行／1200 字までの抜粋なので、全文を読みたいときは記録カードの実身を開く。
- 出力は**答えの文字列だけ**。材料も下流へ渡したいなら連結カードで束ねる。
- 通常入力は「質問の文脈」。無くてもよい（入力0でもエラーにしない）。

**注意（案B の性質）★**: 問い合わせカードは、**既定では答えが書いてあっても上流を評価する**。
つまり再実行のたびに上流の AI も走り直し、**人が読んだ案とは別の文面が下流へ行く**。

**対策①＝スイッチを入れる（v1.8.1・こちらが簡単）**: spec に `"skip_upstream": "on"`
（設定フォーム「答えが入ったら」→「上流を動かさない（聞いたときのまま）」）。
答えが入っているあいだは**上流を1枚も評価せず**答えだけを流す（AI も呼ばれない）。
答えを消せばまた上流から動く。`texos_flow.py` なら `ask(..., skip_upstream=True)`。

```python
ask("方針を聞く", question="どちらで進めますか", skip_upstream=True)
```

- **AI の出力について人に聞くフローでは、原則こちらを付ける。** 付けないと2パス目に
  原案が作り直され、人が読んで判断した案と別物が下流へ行く。
- 逆に「毎回いまの上流を見たうえで答えだけ差し替えたい」なら付けない（既定のまま）。
- 例 → `scripts/build_sample_human_decision.py`（課題に人の判断を挟む・2パス）。

**ただし `skip_upstream` が止めるのは「その問い合わせを通る経路」だけ** ★（2026-08-27 実機）。
問い合わせを**迂回して**上流へ届く矢印が1本でもあれば、そこから AI は走り直す。
実測では「記録 → 問い合わせ」と「記録 → 束」を並べた配線で、2パス目に原案が作り直され、
**人が読んだ案とは別物が束へ入った**（スイッチは効いているのに、である）。
人が読んだそのものを下流へ渡したいなら、**束へは記録カードではなく実身のほうを繋ぐ**
（対策②）。ビルダーでは実身を先に置いておけばよい:

```python
控え = p.file("企画案_控え.md", "", 500, 560)      # 記録の prefix と同じ名前にする
記録 = p.tap("記録：企画案", 500, 400, prefix="企画案_控え")
p.flow(記録, 問い合わせ)
p.flow(控え, 束)                                   # ← 束へは実身（ファイルの今を読む）
```

記録は同じパスの実身を見つけると**中身だけ差し替える**ので、カードは増えない。

**問い合わせの出力は「答えの文字列」だけ。判断した当のものは別に渡すこと** ★（2026-08-27 実機）。
`skip_upstream` を付けると上流が動かないので安心してしまうが、**下流には「採用」の3文字しか
届かない**。実測では、人が承認した企画案が最終文書を書く AI に1文字も渡っておらず、
その AI は**お題からゼロで書き直していた**（毎回まったく別の製品になった）。
束のラベルが「お題＋企画案＋判断」でも、矢印を引いていなければ入らない。

```
  記録：企画案 ──▶ [企画案.md] ─┬─▶ 問い合わせ ──┐
                                │                ▼
                                └───────────▶ [束] ──▶ 最終文書
                                  ↑ 承認した当のものも束へ入れる
```

**下流が AI なら、なおさら渡す。** 「採用」だけを見た AI は、承認された内容を知らないまま
それらしい文書を作る —— 人は自分が読んでいないものに判子を押したことになる。

#### 2パスで描く（推奨の形・v1.8.4）★

人の判断は本質的に2パスなので、**押す場所を2つに分けて描く**のがいちばん読みやすい。
継ぎ目は**空の実身を先に置くこと**で作る（記録カードが同じ名前で埋める・§3-10）。

```python
案   = p.file("企画案.md", "", 300, 560)          # ← 空で先に置く。記録の prefix と同じ名前
記録 = p.tap("記録：企画案", 300, 380, prefix="企画案")
判断 = p.ask("判断", 620, 380, question="採用 / やり直し のどちらで進めますか")

p.flow(企画, 記録)                                 # ①原案を作る  … ここを押す
p.flow(案, 判断); p.flow(答え, 判断, role="answer")
p.flow(案, 束); p.flow(判断, 束); p.flow(束, 最終)   # ②判断して仕上げる … ここを押す
```

- **判断と束が受けるのは実身のほう**（`記録` カードではない）。実身は葉なので、
  ②を押しても**上流の AI は1枚も走らない** —— つまり **`skip_upstream` は要らない**。
  スイッチは「材料が実身でない配線」のためのもので、この形では出番がない。
- そして外しておくと得がある: **②を先に押しても静かに止まる**。実身がまだ空だからで、
  「材料がまだありません」と出て no-data になる（答えが書いてあっても止まる）。
  スイッチを入れると上流を見ないので、この保険は効かない。
- 押す場所を明示したければ、それぞれに**トリガ**を添える
  （`p.op(..., kind="trigger")` → 実行したいカードへ矢印。発行レーンなので pull には出ない）。

**対策②＝答えたときの案を実身で固定する**（実機で踏んだ・2026-08-08）。
スイッチが無かった頃の配線レシピ。**人が書き出したファイルを手で直したい**ときは
いまでもこちらが要る（スイッチは上流を止めるだけで、材料を編集可能にはしない）:

```
  下書き(AI) ──▶ 記録 ──▶ [下書き控え.md]          ← 記録が作る実身カード
       │                        │
       └──▶ 問い合わせ ──┐      └──▶ 束（1本目）    ← ここを繋ぐ
                          └────────▶ 束（2本目）
```

- **束に繋ぐのは記録カードではなく、記録が作った実身カードのほう**。
  記録カードの矢印は「その実行で通った中身」を流すが、実身カードは**ファイルの今**を読む。
  だから前回の実行で書き出された案がそのまま材料になり、**人が手で直した編集も効く**。
- 逆に言うと、**記録カードが書き出したファイルを編集しても、記録カードの矢印には反映されない**
  （記録は書き出し専用で読み返さない。しかも次の実行で上書きされる）。
- 矢印を引き直したら**束を右クリック →「入力の順序 ...」**で並べ直すこと。
  順番は繋いだ順（`created_at`）なので、後から引いた矢印は最後尾になる（§3-3）。

### 3-2. 集約ノードは限られている

- 内蔵: `text_concat` / `text_diff` / `text_paste` の3つだけ（`flow.rs: builtin_is_aggregate`）。
- 外部コマンド: `cmd` に `{in*}` か `{in2}` 以降があれば集約、`{in}`/`{in1}` だけならファンアウト。
- それ以外（AI・t2i 等）は全部ファンアウト側。

### 3-3. 集約の入力順は「矢印を作った順」

`relations.created_at` 昇順。**先に繋いだものが1本目**。
束の1本目に「元の問い」「前提」を置くと、下流が文脈を見失いにくい（§4-3）。

### 3-4. `prefix` と `seq` で出力名が決まる

- `prefix` あり・`seq` なし → **`prefix.拡張子` で固定名・毎回上書き**。反復実行に向く。
- `prefix` あり・`seq` あり → `prefix1.ext`, `prefix2.ext` … と連番。
- `prefix` なし → `入力名_フィルタ名.ext`。
- 繰り返すが、**効くのは実行した終端カードの `prefix` だけ**。

### 3-5. 付箋は「定数カード」— パラメータの置き場に最適

`kind='note'` をフローに繋ぐと、本文が `text/plain` として流れる（`flow_run.rs`）。
つまり**設定値・前提・重み付けを付箋に書いて繋げば、キャンバス上でダブルクリックして
書き換えるだけで挙動が変わる**。JSON を編集させる必要がない。

人間に見せたい説明の付箋（繋がない）と、パラメータの付箋（繋ぐ）が同じ見た目で
共存する点は、利点でもあり混乱の元でもある。**繋ぐ付箋は見出しを「〜（ここを書き換える）」等に
して見分けをつける**こと。

### 3-6. 制限時間は「未指定＝無制限」

`timeout_secs` は未指定または `0` で無制限（`flow.rs: gen_timeout`）。
ローカル LLM は分単位かかるので、AI カードでは**指定しない**のが正解。

### 3-7. 型チェックで黙って飛ばされる

矢印は `accept_mime` で検査される。AI カードは `text/*`。
合わない入力は**エラーにならず「スキップ」**され、結果だけが静かに変わる。
テキスト系に統一するか、前段に変換フィルタを置く。

**MIME は拡張子だけで決まる**（`util.rs: mime_for_ext`）。**この表に無い拡張子は
`application/octet-stream`** になり、`text/*` のカードに黙って読み飛ばされる。
2026-08-21 の実機で `.java` がこれに当たり、`md_codeblock` が切り出したソースが
下流で消えた（v1.8.2 で java/kt/go/rb/sh/ps1/bat/sql/lua/cs/swift 等を追加して解消）。
ソースコードや見慣れない拡張子を流すときは、まず `mime_for_ext` に載っているか見ること。

**AI に書かせたソースをコンパイラ／インタプリタへ渡すなら、あいだに `md_codeblock` を挟む** ★
（2026-08-27 実機）。**AI カードの出力は必ず `.md`** で、しかも囲い（```c …）が付く。
そのまま `gcc.exe` に渡すと `file not recognized: File format not recognized` で落ちる。
`md_codeblock` は囲いを剥がすだけでなく **拡張子を言語のものに変える**（`lang="c"` →
`.c`）ので、この1枚が MIME と囲いの両方を同時に片付ける。`output_ext` で明示してもよい。

```
[課題] ─▶ [AI] ─▶ [md_codeblock lang="c"] ─▶ [gcc.exe] ─▶ 実行結果
                        ↑ここが要る（.md のままだと下流が受け取れない）
```

役割の付箋に「``` は使わないで」と書いて済ませようとしないこと —— 囲いは出るし、
出なかったとしても**拡張子は `.md` のまま**なので、どちらにせよ通らない。

ビルダーでの書き方（`builtin()` は**内蔵フィルタ名を `name=` で渡す**。第1引数はカードのラベル）:

```python
ソース = p.builtin("ソース取り出し", 650, 300, name="md_codeblock", lang="c")
実行   = p.program("コンパイル＆実行", 950, 300, name="gcc.exe", output_ext="txt",
                   prefix="実行結果",
                   cmd='"{in}" -o "{out_noext}.exe" && "{out_noext}.exe" > "{out}"')
```

### 3-8. TexoS が開いている間に DB を書かない

外から `.texos/texos.db` に書いても、起動中の TexoS は自分の接続を持っているので
**UI には反映されない**。プロジェクトを開き直す必要がある。
**組み立ては TexoS を終了した状態で行う**こと。

**起動中の TexoS をそのまま触りたいなら MCP 接続を使う**（v1.11・`docs/MCP接続.md`）。
TexoS の「表示・設定」で受け付けをオンにすると、エージェントは MCP 経由で
**いま開いているプロジェクト**のカード作成・配線・実行・結果取得ができ、その場で面に出る
（DB へ外から書くのではなく、TexoS 自身が UI と同じ処理で書く）。

`texos_flow.py` の `save(reset=True)` は、開いたままだと DB ファイルを消せないので
**中身を空にして組み直し、「開き直してください」と印字する**（黙って古いカードを
残さないようにした・2026-08-21）。

**例外: 実行カードの中から書いたものは、その場で面に出る** ★（2026-09-06 実機）。
TexoS は ▶ の実行が終わると**面を丸ごと読み直す**（`App.tsx` の `run_flow` 後の
`refresh()`）。だから外部プログラムカードが実行中に親の DB へ書いたカードは、
同じ実行の中で拾われる —— 開き直さなくてよい。

これを使うと、**生成したプロジェクトへの入口カードを自動で置ける**。張る仕事は
**踏み台の側に置く**こと —— 案を書く AI に `link_into` を教えると、親のプロジェクトへ
勝手に書き始める。禁止は禁止のまま、安全な場所でだけ張る。

なお**生成先がサブフォルダなら、そもそも §3-8 に触れない**（別プロジェクト＝別 DB で、
TexoS はそれを開いていない）。再起動が要るのはホストのフロー自体を組み直すときだけ。

### 3-15. 「入力する」と言われたら、入口を作り分ける ★

依頼文の「○○を入力すると」は、たいてい**人がその場で書き換えられる場所**を求めている。
TexoS には口が3種類あり、取り違えると「入口はあるのに何も書けないフロー」になる。

- **付箋（`note`）** — 人がダブルクリックして書き換える定数（§3-5）。
  **短い課題・お題・パラメータはこれ**。既定で選ぶべき入口。
- **実身（`file`）** — 中身が長い／別のアプリで編集したい／履歴を残したいとき。
  ファイルとして直下に置かれ、外のエディタでも直せる。
- **IN カード（`{"op":"in"}`）** — **中身を持てない**。素通しの札で、
  「ここが差し替え可能な口です」と示すためのもの。モジュールとして外から
  別の流れを繋ぎ替える前提のときだけ使う。

つまり「課題を入力する」の実装は、**付箋（または実身）を置く**のが本体で、
IN カードはその手前に**添える**もの。IN だけ置くと入れる中身が無い。

**画像・音・PDF のようなバイナリは付箋に書けない。入口は `p.drop(...)`**（ドロップポイント）★
（2026-08-27 実機）。「中身は人があとで置く」ときに、空の実身カードで代用しないこと ——
空ファイルは**壊れたファイル**であって、下流は実行時に落ちる（空の `.png` に対して
`magick.exe: improper image header` が出た）。ドロップポイントは**投入されるまでスキップ**
されるので、フローは組んだ状態のまま置いておける。
フォルダに置かれたものを自動で拾いたいなら、ドロップポイントではなく
**ウォッチャ**（`p.op(..., kind="watch", path="受信箱")`・発行レーンなので矢印では繋がない）。

```
  [課題（ここを書き換える）付箋] ──▶ [IN] ──▶ [AI①] ──▶ [AI②] ──▶ [OUT]
                                     ↑口を明示            ↑▶を押すのはここ
```

**IN は終端になれない**（▶ を押せない）。出口には OUT か普通のフィルタカードを置く。
OUT は押せる終端で、結果カードが OUT の横に生まれる。

**OUT を終端にするときの出力名に注意。** `prefix` の無い終端の名前は
`入力名_終端カードのラベル.拡張子`（`flow_run.rs`）。だから OUT のラベルを
「要約（ここの ▶ を押す）」のようにすると、ファイル名が
`要約_要約（ここの ▶ を押す）.md` になる。**案内文はラベルではなくメモか説明の付箋に置き、
OUT には短い名前を付ける**こと。OUT の spec に `prefix` を書けば名前を決められる
（UI のフォームには出ないが、終端の命名はこの値を読む）。
ビルダーでは `p.op_in(...)` / `p.op_out(..., prefix="要約")`。IN を終端にすると `save()` が例外にする。

### 3-13. 外部プログラムの名前は拡張子まで書く（Windows）★

`flow.rs: resolve_program` は「指定パス → `.texos/filters` → PATH」の順に探すが、
**PATH の各フォルダに `name` をそのまま繋いで `is_file()` を見るだけ**で、`.exe` を補わない。

- ✗ `"name": "python"` … 解決できず「プログラムが見つかりません」
- ✓ `"name": "python.exe"` / `"gcc.exe"` / `"javac.exe"` / `"ffmpeg.exe"` / `"pandoc.exe"`

**`name` と `cmd` は別物。`cmd` に書くのは引数だけ** ★（2026-08-27 実機）。
`cmd` の先頭にもう一度プログラム名を書くと `"…\python.exe" python.exe -c …` になり、
**エラーにならず 0 バイトの出力が静かに出来る**（§3-14）。

- ✗ `p.program(..., name="python.exe", cmd='python.exe -c "..." > "{out}"')`
- ✓ `p.program(..., name="python.exe", cmd='-c "..." > "{out}"')`
- 2026-10-23 から `validate()` が**エラーで弾く**（コンストラクタの AI＝Strata も `gcc.exe {in} -o {out}` と書いた）。

**`{out}` に書かないと、結果は1枚も出来ない** ★（2026-09-06 実機）。
コマンドの標準出力は捨てられる。結果をカードにしたいなら **`> "{out}"` を必ず書く**。
書かないと「出力を作らない自己完結コマンド」とみなされ、**エラーにならず出力カードが
0枚**になる（§3-14 の静かな失敗）。試走では `0バイト ×0` と出る。

- ✗ `p.program(..., name="python.exe", cmd='"{in}"')` … 実行はされるが結果が消える
- ✓ `p.program(..., name="python.exe", cmd='"{in}" > "{out}"')`
- `{out}` を省いてよいのは、読み上げ・カメラ起動のように**出力が無いのが正しい**ときだけ

**`{in}` は入力ファイルの「パス」であって「中身」ではない** ★（2026-08-27 実機）。
付箋に書いた URL や語句を**引数として**渡すことはできない —— 渡るのは
一時ファイルのパスで、`curl.exe -s -L "{in}"` はそのパスを URL として叩き、
**0 バイトを返す**。中身を読むのはプログラムの仕事:

**Windows に `awk` / `sed` / `sh` / `grep` は無い** ★（2026-08-27 実機・3モデルとも踏んだ）。
テキスト処理でこれらを呼ぼうとして「プログラムが見つかりません」で落ちるのが、
外部プログラム関連で一番多い失敗だった。**内蔵カードで済むなら内蔵を使うこと**:

```
text_grep（行の抽出）  text_replace（置換）   text_sort（並べ替え・重複除去）
text_head / text_tail（先頭・末尾）          text_cut（列の取り出し）
text_count（数える）   text_convert（文字コード）  text_concat / text_diff / text_paste（集約）
md_codeblock（コードブロックの取り出し）      img_resize / img_convert（画像）
```

**生成・取得も内蔵カードがある。外部プログラムを発明しないこと** ★（2026-08-27 実機）。
未見の依頼で `whisper.exe` や `image_generator.exe` を呼びに行って落ちた —— どちらも
存在しないプログラムで、しかも**片方は内蔵カードで出来る**:

```
ai（文章の生成・変換）      t2i（文章 → 画像）      t23d（画像 → 3Dモデル）
speak（読み上げ）           web_fetch（URL → 本文）  web_feed（RSS）
web_capture（ページの画像）  img_resize / img_convert（画像の加工）
web_search（検索語 → 結果一覧）
```

- ✓ キーワードで Web を調べるのは内蔵の `p.builtin("Web検索", x, y, name="web_search")`
  （**入力の空でない1行が1検索語**。上限 `max_queries` 既定3。AI に検索語を出させるなら
  役割に「検索語だけを1行に1つ・最大3行・説明は書かない」と書く。結果0件は no-data）。
  検索エンジン（SearXNG）は人が「Web検索エンジンの管理」で一度導入しておく必要がある

内蔵に無い処理は `python.exe` に `-c` で書かせる（Windows に必ずある道具はこれ）。
**それでも足りないときだけ外部プログラムを使い、依頼にその名前が書いてなければ
「この道具が要ります」と付箋に明記する**。入っている保証のないプログラム名
（`whisper.exe`・`ffmpeg.exe`・`pandoc.exe` 等）を黙って呼ぶと、実行するまで誰も気づかない。

- ✗ `p.program(..., name="curl.exe", cmd='-s -L "{in}" > "{out}"')`
- ✓ URL から本文を取るのは内蔵の `p.builtin("ページ取得", x, y, name="web_fetch")`
  （**入力の1行目を URL として読む**。付箋に URL を書いて繋げばよい）
- ✓ どうしても外部プログラムに中身を渡すなら、`-c` のスクリプト側で
  `open(パス).read()` する（`{in}` をパスとして受けて自分で開く）

人が設定ダイアログから作るときは存在チェックがその場で出るので気づくが、
**エージェントが書いた定義は実行するまで誰も気づかない**。ここは必ず拡張子まで書く。

コンパイルと実行のように2段必要なものは、`&&` で繋いで**1枚のカード**にしてよい
（Windows では `cmd /C "..."` に丸ごと渡されるので `&&` も `>` も効く）。
中間生成物は `{out_noext}` を借りると一時フォルダ側に落ち、プロジェクトが散らからない:

```json
{"name": "gcc.exe", "type": "command", "output_ext": "txt",
 "cmd": "\"{in}\" -o \"{out_noext}.exe\" && \"{out_noext}.exe\" > \"{out}\""}
```

### 3-14. 途中のカードが失敗しても、終端は止まらない ★

上流の1枚が失敗しても、**pull は他の枝を評価し続け、終端カードは完走する**。
集約カードはその入力が無かったものとして詰めるので、
**出来上がるファイルは「一部が欠けたまま」で、見た目は正常**になる。

- 気づく手立ては2つ。①実行後のダイアログの「エラー:」欄（`FlowReport.errors`）。
  ②各カードの `last_run`（`ok:false` とコマンドの stderr がそのまま入る）。
- **エージェントは「終端が動いた」で完了と判断してはいけない。**
  出来たファイルを開いて、期待した節がすべて揃っているか数えること。

実測（2026-08-21）: 3言語のうち C だけコンパイルに失敗したが、まとめカードは `ok:true` で
完走し、C の実行結果だけが抜けた md ができた。欠けに気づいたのは**出力を読んだから**で、
グラフを見ても実行が成功したかは分からない（§6 と同じ話）。

## 4. 多視点・多段判断を組むときの設計則

実際に「AI 合議」「設計審査」を組んで、通しで走らせて分かったこと。

### 4-1. 並行（横）は「別コンテキスト」でなければ意味がない

1つのプロンプトで「4つの視点で考えて」と頼むと、4つの意見は**同じ文脈の中で
互いに条件づけられて生成される**ので、必ず整合の取れた穏当な話に収束する。
独立した反対意見を出すには、**別々のカード＝別々の呼び出し**にするしかない。
これはモデルの賢さではなく配線の問題であり、TexoS でやる意味の中心にある。

### 4-2. 垂直（縦）は「答えの上でもう一段考える」

横＝同じ問いを別の基準で切る。縦＝**出てきた答えそのものを次の段の入力にする**。
効いた縦の段は2種類:

- **前段の縦**: 問いそのものを立て直す（前提・対象・重み付けを適用した問いに書き換える）。
- **後段の縦**: 判定 → その判定を疑う → 確定。

### 4-3. 枠は「持ち回る」— 離れると溶ける ★

前提（対象ユーザー・重み付け）を固定する段と、それを消費する段が離れるほど、
途中で枠が溶ける。実測では、最終段が前提を見失って
「ターゲット層が未決定である」と言い出した（前提で確定済みなのに）。

**対策: 束カードで枠を毎回一緒に運ぶ。** 下流の束の1本目に、常に前提（審査票）を入れる。

### 4-4. 迎合対策を入れると、反対側へ迎合する ★

意図的にバイアスを入れて「迎合していないか」を検査する段を足したところ、
最終段が**反証を全件「認めた」**で処理した。バイアス迎合を潰したら反証迎合になっただけ。

**対策: 中間段の処理を2値にしない。** 「認めた／退けた」ではなく
**「認めた（結論を変える）／認めた（条件に反映）／退けた」**の3値にし、
さらに「全件認容ならそれは迎合の疑いがある、と自己申告せよ」と書く。

### 4-5. 確信度は理由を要求しないと演出になる

小型モデルは平然と「確信度: 高」と書く。
**「確信度と、その確信度になった理由を一文で。理由の無い確信度は書かない」**と指定すると、
急に中身のある不確実性の申告になる。

### 4-6. 実測の目安

Ollama `gemma4:latest`（8B）で AI カード1枚あたり **13〜23秒**。
7段構成のフルパスで **約120秒**（モデルロード済み）。初回はロードに +90秒。
重い判断のときだけ、特定の1枚（反証など）を大きいモデルにすると、
入れ替えが1回で済んで効率がよい。

## 5. 組み立て方 — `scripts/texos_flow.py`

生 SQL を書かない。ビルダーを使う。**規約違反は `save()` で例外になる。**

```python
import sys; sys.path.insert(0, r"<repo>\scripts")
from texos_flow import Project

p = Project(r"F:\...\新しいプロジェクト", model="gemma4:latest")

議題   = p.file("議題.md", "# 議題\n...", 0, 300, memo="ここを書き換える")
重み   = p.note("重み付け（ここを書き換える）\n...", 0, 520)
役割   = p.note("役割：批判担当\n弱点とリスクだけを書く…", 400, 60)
束     = p.cat("束 材料", 400, 400, prefix="05_材料")
判定   = p.ai("判定", 700, 400, system="", temperature=0.2, prefix="判定")
記録   = p.tap("記録：判定", 1000, 400, prefix="途中_判定")

p.flow(議題, 束); p.flow(重み, 束)      # ← 繋いだ順 = 束の中の順
p.flow(束, 判定)
p.flow(役割, 判定, role="system")       # ← 役割ポート（入力に数えない）
p.flow(判定, 記録)
p.shape(380, 340, 620, 220, "束ねてから渡す")
p.view()
p.save()
```

`save()` は検証したうえで、終端カードと**実行すると出来るファイル名**を印字する。

**使える API はこれで全部**: `file()` `copy_file()` `note()` `drop()` `ai()` `cat()` `tap()`
`ask()` `loop()` `builtin()` `program()` `launcher()` `bundle()` `op_in()` `op_out()`
`flow(…, role=)` `shape()` `view()` `save()`。ここに無いものは発明しないこと。

発行側（トリガ/タイマ/ウォッチャ/音声）は `op(…, kind=)` と **`request(op, 先, say=)`**（リクエスト矢印）で
繋ぐ — `flow()` で繋ぐと例外。音声カードは `voice(…, mode="command"|"dictation", say_out=)`。
フローの入力には say_out の実身（`file("音声/発話.txt", "", …)`）を使う。手本＝`scripts/build_voice_demo.py`
（v1.10・`docs/V1.10_音声反射カード計画.md`）。

`ai()` の `system=` は**省略できる**（既定は空）。役割を付箋にして
`flow(付箋, ai, role="system")` で渡すのが基本形で、そのとき system は書かなくてよい。
ただし**役割の矢印も system も無い AI カードは指示ゼロ**なので `save()` が警告する。

### 5-2. 成果物は「別プロジェクト＋親に入口を1枚」で渡す ★

依頼は普通「いま開いているプロジェクトに作って」と来るが、
**そこへカードを直接足すのは避ける**（既存のカードと座標がぶつかる／二重生成の元／
1つの面に無関係な仕組みが混ざって読めなくなる）。

代わりに、**仕組みは新しいフォルダに1つのプロジェクトとして組み、
親の面にはそのプロジェクトカード（入口）を1枚だけ置く**。人はダブルクリックで中に入れる。

> **例外＝TexoS 内のコンストラクタカード（v1.12・`builtin:"construct"`）。** TexoS 自身が並べるので
> 「外から書いても面に出ない」は起きず、座標は全カードの下端の下に枠で囲んで置き（ぶつからない）、
> 流すたびに新しい枠になる（消すのは UNDO 1回）。設計図の検査はこのビルダーの `validate()` をそのまま使う
> （`python/texos_plan.py`）。外のエージェントが組むときは、これまでどおり別プロジェクトに作ること。

```python
p = Project(r"F:\...\親\カード実験_多言語実行")
...
p.save()
p.link_into()                 # 親＝いま開いているプロジェクト（current_project）
p.link_into(r"F:\...\親")     # 親を明示することもできる
```

`link_into()` は親の DB に `kind='project'` のカードを1枚足すだけ
（`real_id` は `project:<パスのSHA-256>`・`project_ref` は絶対パス）。
既に同じ先へのリンクがあれば何もしない。空いている座標を自分で選ぶ。
**親を TexoS で開いたままなら、開き直すまで面には出ない**（§3-8）。

主な API: `file()` `copy_file()` `note()` `ai()` `cat()` `tap()` `ask()` `loop()`
`builtin()` `program()` `launcher()` `bundle()` `flow(…, role=)` `shape()` `view()`
`save()` `link_into()`。モジュール関数 `current_project()`。

問い合わせ（3-12）は `p.ask(...)` と `p.flow(付箋, 問い合わせ, role="answer")`。
答え矢印を付箋以外から引いたり、相手が問い合わせカードでなければ例外になる
（間違えると答えたつもりでいつまでも止まったままになる）。実物は `scripts/build_ask_demo.py`。

反復（3-11）を組むときは、戻り矢印の**戻し先を束にする**（AI へ直接戻すとファンアウトする）:

```python
束   = p.cat("束（お題＋前周）", 520, 60, prefix="材料")
推敲 = p.ai("推敲", 520, 240, system="", prefix="案")
記録 = p.tap("各周の記録", 520, 420, prefix="各周")     # 反復の中なので 各周_1, 各周_2 …
反復 = p.loop("反復", 520, 600, max_rounds=3, until_contains="合格")

p.flow(お題, 束)                        # 1本目＝毎周変わらない前提（枠は持ち回る・§4-3）
p.flow(反復, 束, role="previous")       # 2本目＝前周の結果（1周目は空）
p.flow(束, 推敲); p.flow(推敲, 記録); p.flow(記録, 反復)
```

ビルダーは戻り矢印を**循環として数えない**（評価が遡らないため）が、
反復カード以外から `role="previous"` を引いたら例外にする。
戻り矢印が1本も無い反復カードは警告（同じ処理を繰り返すだけになるため）。
実物は `scripts/build_loop_demo.py`（`カード実験_反復` を組む手本）。

## 6. 納品前に必ずやること

**組んだだけで終わりにしない。1周走らせて、出力を読むこと。**

`§4-3`（枠が溶ける）も `§4-4`（反証迎合）も、グラフを眺めていても分からず、
**実際に流して出力を読んで初めて分かった**。プロンプト設計の欠陥は静的には見えない。

**道具がある。`scripts/texos_dryrun.py`** — TexoS を起動せずに1周流す（試走）。
DB は読むだけ、出力は `試走結果_YYYY-MM-DD/` に置くので、プロジェクトを汚さない。

```bash
python scripts/texos_dryrun.py <プロジェクトのフォルダ>            # 終端を全部流す
python scripts/texos_dryrun.py <フォルダ> --list                  # 終端の一覧だけ
python scripts/texos_dryrun.py <フォルダ> --card "まとめ"          # 1つだけ
```

- pull の骨（終端から遡る／入力順は接続順／役割ポートは入力に数えない／型違いは黙って
  飛ばす／集約以外はファンアウト／`prefix` は stem ごと差し替え／終端の命名規則）を
  `flow_run.rs` から写してある。実測では**本物の TexoS が出したファイルとバイト単位で一致**した
  （`カード実験_多言語実行`・2026-08-21）。
- 再現しないもの: 問い合わせ(ask)・反復(loop)・t2i・t23d・web_* ・speak。
  当たったらその場で止まり、名前を告げる。そこは TexoS の ▶ で確かめる。
- **これは本体ではない。** ここで通っても TexoS で通る保証はない。
  逆に**ここで止まったものは、ほぼ確実に直す価値がある**。
- 出力一式は `試走結果_YYYY-MM-DD/` のような**サブフォルダ**に置く。
  プロジェクト直下に置くと、TexoS の「新規カードを登録」の対象になって紛らわしい。
- **出来たファイルを開いて、期待した節が全部あるか数える**。終端が完走しても
  途中が失敗していれば静かに欠ける（§3-14）。

**手本**: `scripts/build_polyglot_demo.py`
（「フィボナッチ数列を C / Java / Python で書いて、ソースと実行結果を並べて見せて」という
依頼をそのまま形にしたもの）。この1本を実際に流したことで、§3-7 の MIME 欠落・
§3-13 の `.exe`・§3-14 の部分出力・`save(reset=)` の握りつぶしが**まとめて出た**。
新しい種類のフローを初めて組むときは、必ず小さいものを1本通してから納品すること。

## 7. この文書の位置づけと、その先

現在の形（規約 + Python ビルダー）は**足場**であって最終形ではない。
本来あるべきは、`docs/共有とモジュール設計.md §2` の
**フローモジュール＝名前付きの再利用可能な部分グラフ**を、宣言的なファイル
（モジュール JSON）として TexoS 自身が読み書きすることである。そうなれば:

- **人間**は「モジュールを読み込む」だけでよい（カードを並べる必要がない）。
- **エージェント**は SQLite にもスキーマにも触れず、宣言だけを書けばよい。
  §3 の落とし穴の大半（3-1〜3-4, 3-8）が**そもそも触れない領域**に隠れる。
- 配布物（`SampleProject.zip`）に「仕組み」を同梱できる。

つまり **§3 が短くなるほど、TexoS の設計は正しい方向に進んでいる**。
この文書の落とし穴の項目数は、モジュール機構の未整備度をそのまま測っている。

> **実際に減った例（v1.8）**: §3-9 役割ポートと §3-10 記録カードは、落とし穴として
> 書かれていたものを**機能で消した**追加である。役割ポートは 3-1（ファンアウト回避のため
> 束を挟む）の一部を不要にし、記録カードは 3-4（中間出力はファイルにならない）の
> 痛みを直接埋める。§3 に項目が増えているように見えるが、中身は「守るべき制約」から
> 「使える道具」へ移っている。この移し替えを続けるのが正しい進み方。
