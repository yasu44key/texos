# 生成カード群企画 — t2x ファミリー（3D・動画・音源）（2026-07-11）

[標準フィルタ充実検討.md](標準フィルタ充実検討.md) の続き。あちらで「t2i は別格の専用機構」と
位置づけたが、将来は 3Dオブジェクト作成・動画作成・音源作成もディフュージョンモデルの仲間として
考えられる。この「別格」を1回きりの例外にせず、**生成カード群（t2x ファミリー）という正式カテゴリ**
として企画する記録。

---

## 1. 位置づけ — 4層モデルの外にある「G層」

標準フィルタの4層（L1ビルトイン〜L4ユーザー用意）はどれも「小さい・決定的・即時」が前提。
生成系はそのどれとも違う:

- GPU/VRAM を占有する・モデルのダウンロード管理が要る・生成に数秒〜数分かかる
- 中断（cancel）と進捗が要る・常駐させないと毎回のロード待ちが致命的

これを **G層（生成デーモン系）** と呼び、分類手順（標準フィルタ検討 §2.5）に第0問として足す:
「**GPUで動く生成モデルか？ → G層**（以降の4層判定はしない）」。

### 既存2形式の棚卸し

| | builtin | 常駐 | 方式 |
|---|---|---|---|
| AIチャット/変換 | `ai` | Ollama（外部OSS） | **乗る** — 定番の常駐サーバーが既にあるので自前で持たない |
| Text-To-Image | `t2i` | t2i_server.py（自前） | **作る** — 画像生成に Ollama 相当の定番常駐サーバーが無かったので最小デーモンを自作 |

→ G層の選定原則もここから出る: **「Ollama 相当の定番常駐サーバーがあるなら乗る。無ければ
t2i_server 型の最小デーモンを自作する」**（理念「OSSに乗る・全部自前で持たない」の生成版）。
ComfyUI に乗る道もあるが、巨大・ノードUI思想が TexoS と競合・API が不安定なので、
「diffusers 直叩きの最小デーモン」が TexoS 流。

## 2. 将来カテゴリと builtin 名（t2x ファミリー）

| builtin 案 | カテゴリ | 入力 | 出力 | 既存カードとの連結 |
|---|---|---|---|---|
| `t2i`（既存） | 画像 | テキスト＋画像(img2img) | PNG | — |
| `t23d` | 3Dオブジェクト | **画像**（＋テキスト） | .glb | t2i の出力画像 → 3D 化が主経路 |
| `t2v` | 動画 | テキスト＋画像(img2vid) | mp4 | t2i の画像を初期フレームに。ffmpeg で後処理 |
| `t2a` | 音源（音楽・効果音） | テキスト | wav | whisper（音→文字）の逆方向。ffmpeg で変換・結合 |

- いずれも t2i と同じ**集約ノード**（プロンプト＋素材の複数入力）で、NodeKind を1つずつ足す形。
- 出力は普通の実身（.glb / .mp4 / .wav）なので、既存の外部アプリ起動・ffmpeg フィルタ・
  Blender 連携がそのまま効く。**カード連結で生成パイプラインが組めるのが TexoS の本領**:
  - 文 →(ai: プロンプト推敲)→ 画 →(t23d)→ 3D → Blender
  - 文 → 画 →(t2v)→ 動画 ＋ (t2a)→ BGM →(ffmpeg 集約)→ 音付き動画
- モデル候補（2026年初時点の知識。**着手時に要再調査** — この領域は半年で定番が入れ替わる）:
  - **3D**: TripoSR / Stable Fast 3D / Hunyuan3D-2 / TRELLIS。image→3D が主流・VRAM 6〜12GB と軽め。
  - **動画**: LTX-Video（軽量高速）/ Wan 2.x 小型版（Apache 2.0）/ SVD(img2vid)。VRAM 8GB〜・生成は分単位。
  - **音源**: Stable Audio Open（拡散・効果音/短尺）/ MusicGen（⚠️ CC-BY-NC）/ ACE-Step。VRAM 6GB 前後。
- ⚠️ モデルライセンスは商用可否がバラバラ。known（推奨一覧）に載せるときに必ず明記
  （t2i の「定番限定・POLICY」方式を踏襲）。

## 3. 共通基盤 —「生成デーモン規約」を切り出す

t2i_server.py で実証済みのプロトコルを **t2x 共通規約** として明文化し、新モダリティは
この規約を満たす別デーモンとして足す:

1. `GET /health` — ok / device / current_model / **version**（Rust 側定数と照合、古ければ再起動）
2. `GET /models` — available（手持ち）/ known（定番リスト）/ current
3. `POST /pull` — NDJSON 進捗ストリームでモデル取得
4. `POST /generate` — 生成本体（バイト列を返す）
5. `POST /cancel` — 次ステップ境界で中断（部分出力は Rust 側で破棄＝既存契約）
6. `--port` / `--home`（モデル置き場は共有 app-data 配下）・依存は最小（標準 http.server）
7. **毎生成リコンサイル**（モディファイアの差しっぱなしリーク防止）・定番限定＋手持ち診断（t2i_inspect 方式）

### デーモンの分け方 — モダリティごとに別プロセス・規約だけ共通

- **1デーモン多モダリティ（t2i_server を太らせる）はやらない**。torch/依存のバージョン衝突、
  VRAM 常駐の競合、SERVER_VERSION 更新の巻き添えが起きる。
- `t23d_server.py` / `t2v_server.py` / `t2a_server.py` と**プロセス・ポート・venv を分離**し、
  規約（上記1〜7）と Rust 側ハンドラを共通化する。Rust には `run_t2i` を一般化した
  `run_gen(kind, spec, inputs)` と、デーモン管理（起動・health照合・pull UI）の共通部を用意。
  `job.t2i_active` は `job.gen_active(kind)` に一般化（cancel の宛先デーモンを特定するため）。
- **GPU は資源として直列化**: v1.5 の並行実行・資源機構に「GPU 資源」を載せ、生成系ノードの
  同時実行を資源ロックで防ぐ（VRAM の取り合いでの共倒れ防止）。常駐モデルも
  「最後に使ったデーモンだけ VRAM 保持、他はアンロード」等の簡単な追い出し規則を検討。

## 4. 進め方

開発方針は「使いたい機能優先」なので順序は使いたい順でよいが、実装コスト・シナジーの目安:

| 順 | カテゴリ | 理由 |
|---|---|---|
| 1 | **3D（t23d）** | モデルが軽い・生成が速い・t2i の画像資産が入力に活きる・Blender との連携先が既にある |
| 2 | **音源（t2a）** | 軽め・whisper と対で「音の入出力」が揃う・動画企画の素材になる |
| 3 | **動画（t2v）** | 最重量（VRAM・生成時間・モデルの入れ替わりが激しい）。3D/音源で共通基盤を固めてから |

いずれも v2.0 系の企画（v1.5 熟成期間の粒ではない）。着手時の最初の作業は
「その時点の定番モデル再調査 → known リスト2〜3本の選定」から。

## 5. 論点（未決）

1. builtin 名の確定（`t23d` / `t2v` / `t2a` 案。i23d が実態に近い 3D をどう呼ぶか）。
2. 共通基盤の切り出し時期 — t23d 着手時に t2i からリファクタして規約を抽出するか、
   t2i はそのまま残して2本目から規約適用か（挙動不変を優先するなら後者）。
3. GPU 資源ロックの粒度 — 「生成中だけロック」か「モデル常駐中ずっとロック」か。
   複数デーモン常駐時の VRAM 追い出し規則。
4. 3D の表示 — 出力 .glb を TexoS 内でプレビューするか（サムネイル静止画を t23d が
   併産する手もある）、外部ビューア/Blender 任せにするか。
5. Python 環境 — 現状 t2i は開発 PC の system Python 前提。デーモンが増えると
  venv 分離・依存導入支援（L3 の Python 版）が要るか。配布構想との絡み。
