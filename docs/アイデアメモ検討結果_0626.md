## 0. 方針転換 ― 「AIモジュール路線」を背骨に据える

### 0.1 何が起きたか（事実の確認）
- NAS 上のプロジェクトフォルダを別 PC で開いて、そのまま動いた＝**可搬性が実証**された
  （プロジェクト＝自己完結フォルダ `<root>/.texos/{db,cas}` ＋実ファイルの設計が効いている）。
- v1.4.0〜v1.4.6 で **AI を「カード＝フィルタ」として組み込み**、自然言語→.md→コード抽出→
  gcc→.exe→実行までを「カードを矢印で繋ぐだけ」で通した（[[project_texos_ai_card]]）。
  AI は新種カードではなく `kind:'filter'` の `builtin:"ai"`＝**既存パイプラインの一部**。

### 0.2 ロードマップ上の「ズレ」
旧ロードマップ（`バージョンアップ計画.md` / `v1.4.0_計画.md`）は **「AI／MCP は UI と
システムが固まってから ＝ V2.0」** と書いている。しかし現実は v1.4 系で AI が主役級に
入った。**計画書が陳腐化している**。今回の方針転換はこのズレを正すもの。

### 0.3 新方針（ユーザー 2026-06-26）
> **「MCP で TexoS を外から制御する」より、「生成 AI を活用した自由な情報処理モジュール」を
> 増やす方が、このクリエイティブなツールの本来の姿。**

これを 3 本柱に分解する:

1. **有益な外部モジュールの取り込み** ― pandoc / ffmpeg / gcc は既に実証済み。これを
   「都度コマンドを書く」から **「カタログから取り込める部品」** へ引き上げる（§2-A）。
2. **ローカルでできることを増やす** ― クラウド非依存で完結する力。Ollama（AI）に続いて
   Whisper（音声→テキスト）、OCR、TTS など**ローカル AI/メディア処理**を足す（§1-1, §2-B）。
3. **AI-as-module を背骨に** ― AI は「TexoS を操作する外部エージェント（MCP）」ではなく、
   **パイプラインを流れるデータを変換するモジュール**。入口（何でも→テキスト）と出口
   （MD→何でも）を既存フィルタが埋め、AI 自身は「変換」と「対話」だけを担う。

### 0.4 MCP の位置づけ（格下げ・後送り）
- MCP（TexoS を外部 AI から制御する受け口）は **否定はしないが優先度を下げる**。
  理由: 「外からツールを操る」モデルは TexoS のキャンバス＝ビジュアルな情報処理という
  本質と方向が逆。まず**内側のモジュール群を太らせる**方が応用範囲が広がる。
- MCP を入れるとしても、それは **「TexoS のフィルタ／プロセスコントロールを MCP ツールとして
  外へ公開する」** 形（基盤が先・公開は後）。V2.0 課題として残置。

## 1. アイデアメモ0626 のブラッシュアップ（4項目）

### 1-① 音声テキスト化カード（Whisper）★方針の象徴
**メモ原文**: 「音声テキスト化カードを作る Whisper を呼ぶ（Whisper サーバーの立ち上げ）
first whisper が有利？」

**位置づけ**: 新方針 0.3 の②③をそのまま体現する第一弾。音声 → **[Whisper]** → テキスト →
**[AI カード]** → … と、**既存の AI-as-filter パイプラインの「入口」を一つ増やすだけ**。
新しいカード種別はいらない。

**実装方針 ― まず外部コマンドフィルタで（サーバー不要）**:
- ffmpeg/pandoc と同じ「ビルトイン外部コマンドフィルタのプリセット」として **whisper.cpp の
  CLI（`whisper-cli` / 旧 `main`）** を登録するのが最小・最速・最ローカル。
  例（コマンド型フィルタ）: `whisper-cli -m {model} -f {in} -otxt -of {out_noext}` 相当を
  TexoS の `{in}`/`{out}` テンプレートに合わせて。出力 .txt が**そのままテキスト実身**になる。
- 解決順は ffmpeg と同じ `.texos\filters → PATH`（`name="whisper-cli.exe"` 形式）。
  → **新規 Rust コードはほぼ不要**。`menuBuilder` のビルトインフィルタにプリセット追加が主。
- これで「外部モジュールの取り込み（①）＋ローカル完結（②）＋AI 入口（③）」が一度に立つ。

**「サーバー立ち上げ」「first whisper が有利？」への回答**:
- **Phase1 はサーバー不要**（CLI を都度起動。音声ファイル単位の変換は one-shot が素直で、
  Ollama のような常駐は要らない）。
- 「first whisper」＝おそらく **faster-whisper**（CTranslate2 実装、CPU でも速い）か
  **whisper.cpp** の取り違え。ローカル組み込み・依存の軽さ・サーバー化のしやすさで **whisper.cpp 推奨**
  （Python ランタイム不要の単一バイナリ＝可搬性と相性が良い。GGML モデルを `.texos\filters`
  の隣に置けば NAS 越しでも完結）。faster-whisper は精度/速度は魅力だが Python 環境を抱える。
- **サーバー化は Phase2 の選択肢**（whisper.cpp の `whisper-server`、または Speaches 等の
  OpenAI 準拠 ASR サーバー）。Ollama を `base_url` 差し替えで透過対応したのと同じ発想で、
  **OpenAI 準拠 `/v1/audio/transcriptions` を喋るサーバーなら AI カードと同じ流儀**で繋げる。
  ただし常駐管理コストが増えるので、CLI で不便を感じてから。
- **Ollama 連携の落とし穴の再確認**: モデル取り違えで「黙って無視」が起きる
  （[[project_texos_ai_card]] のビジョンモデルの件）。Whisper でも**モデルファイルの所在チェック**
  （ffmpeg 流の事前チェック）を入れ、未導入 PC には 1.4.6 の Ollama セットアップ案内と同型の
  ガイド（DL ページ誘導／モデル取得）を出すと親切。

**号**: v1.4.x（ビルトインフィルタ追加＝低リスク）。サーバー化は v1.5 以降の任意項目。

### 1-② 選択カードを他プロジェクトへエクスポート（すべて仮身に）
**メモ原文**: 「選択カードを他のプロジェクトにエクスポート、すべて仮身となる。
Pic Up , Drop Down の代替案」

**意義**: 長らく V2.0 課題だった**プロジェクト間データ共有**の、安価で安全な代替。
「移動」でも「コピー」でもなく **「向こうに仮身を置く（実体は元プロジェクトに残る）」** が要点。

**設計の核 ― どのレーンで参照するか**:
- TexoS の窓モデルには 2 レーンある: **内部レーン**（`window_of`＝同一プロジェクト内の
  カード ID 参照）と**外部レーン**（`origin_path`＝プロジェクト外の実ファイルを指す・1.3.9 以前の
  挙動で凍結）。**プロジェクトをまたぐ参照は内部レーンでは表せない**（ID はプロジェクトローカル）。
- したがって自然な実装は **「エクスポート＝元プロジェクトでコミット（実身化）して実ファイルを
  確定 → 先方プロジェクトに `origin_path` 仮身として登録」**。＝ **既存の外部レーンを再利用**。
  - 原則「エクスポート＝コミット」は `サブプロジェクト検討結果.md §7` で既に確立した方針と一致
    （TEMP 孤児を構造的に避ける）。
  - 先方では薄赤＝窓喪失（元を消す/動かすと切れる）が**正しく**機能する。再リンクも既存機能。
- **Pick Up/Drop On（OLE ドラッグ）の本実装は重い**ので、まずは**メニュー駆動**で:
  「選択 → 右クリック『他のプロジェクトへ送る…』→ 最近のプロジェクト一覧／フォルダ選択 →
  先方に仮身配置」。クリップボード持ち出し（CF_HDROP 済み）の**プロジェクト版**。

**論点（要決め）**:
- 先方に置いた仮身の**初期座標**（まとめて一角に／元の相対配置を保つか）。
- **双方向リンク**にするか（元側にも「○○へ送った」痕跡を残すか）。`open_origin_project` の
  資産（祖先 .texos を辿る）と組み合わせれば往復できる。
- フォルダ／サブプロジェクト／フィルタなど**非ファイルカードの扱い**（まずはファイル系のみ対象、で良い）。

**号**: v1.5 系（プロジェクト間ワークフローの第一歩。窓モデル外部レーンの再利用なので
中リスク）。クリップボード持ち出しの延長として v1.4.x に前倒しも可。

### 1-④ フィルタの強制終了の強化＋リダイレクト起動でのハングアップ
**メモ原文**: 「フィルタの強制終了の強化、外部プログラムのファイル名指定をリダイレクトで
呼び出したときハングアップする。」

**現状コード（`flow.rs`）の確認**:
- 既に **`stdin = Stdio::null()`**（標準入力待ちの古典的ストールは対策済み）、
  **`kill_tree` = `taskkill /F /T /PID`**（ツリー kill）、ポーリングループで **cancel（中断ボタン）/
  timeout/512MB 上限**を監視。基本の安全弁はある。
- にもかかわらずハングするということは、**ポーリングループや taskkill /T が前提とする
  「親子プロセス関係」が壊れるケース**が残っている、と読むのが妥当。仮説:
  1. **孫プロセスの再ペアレント／デタッチ**: `cmd /C` から起動された実体が独立し、
     `taskkill /T`（PID ツリー）から外れて生き残る。
  2. **リダイレクト経由の起動形態**: メモの「ファイル名指定をリダイレクトで呼び出した」＝
     `prog < file` / `prog > file` 形で、シェルの解釈やハンドル継承の都合でツリーが分断、
     または出力ファイルのハンドルを孫が握ったまま `child.wait()` が返らない。
  3. **break_flow（中断フラグ）がこの実行経路まで届いていない**ケース（集約実行/別経路）。

**強化方針（v1.5「Stop 常設・ハンドルを失わない」原則の前倒し適用）**:
- **Windows Job Object でツリーを束ねる**: 起動した `cmd` を Job Object に入れ
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` を設定。**ジョブを閉じれば子孫が再ペアレントしても
  確実に全滅**＝ `taskkill /T` の取りこぼし（仮説1）を根治。これがオートメーション設計メモ
  §1.35 の「危険なのはタイマー無しでなくハンドルを失うこと」の本筋の実装。
- **まず再現**: 「どの形のコマンドで」「どの外部プログラムで」ハングするかを 1 ケース特定する。
  リダイレクト形 vs 引数形、出力先が file vs パイプ、で切り分け（`external_stdio_redirection_runs`
  テストが通っているので、実機固有のプログラムの可能性が高い）。
- **中断の確実化**: cancel ポーリングを全実行経路（ファンアウト／集約／AI ／シェル）で共通化し、
  「実行中プロセス」一覧パネル＋Stop-all（設計メモ §1.35 モードC）を**前倒しで小さく入れる**。
- 既存のタイムアウトメッセージ（「標準入力待ちのフィルタ型を引数型で指定していないか」）は
  良いガイド。リダイレクト形のハング向けにも同種のヒントを足す。

**号**: バグ再現は即時調査。Job Object 化は v1.5 プロセスコントロールの基盤工事として位置づけ
（前倒しで v1.4.x に小さく入れる価値が高い＝暴走停止の信頼性はオートメーションの前提）。

## 2. 次のアイデア（新方針の発展）

### 2-A. モジュールカタログ（外部部品の「取り込み」を仕組み化）★方針①の本命
- 現在の「ビルトインフィルタ（ffmpeg/pandoc/gcc プリセット）」を、**追加・更新できる
  カタログ**へ昇格する。pandoc / ffmpeg / whisper.cpp / gcc / ImageMagick / yt-dlp /
  tesseract(OCR) / qpdf … を **1 クリックで取り込めるレシピ集**に。
- 各レシピ＝`{name, cmd テンプレート, in/out mime, 所在チェック, 未導入時の導入ガイド}`。
  **既存の `filter_library.json` / `launcher_library.json` の延長**で実装できる（新基盤不要）。
- 未導入 PC への対応は 1.4.6 の **Ollama セットアップ案内と同型**（winget があれば自動導入提案／
  無ければ DL ページ）。可搬性のため**ポータブル版バイナリを `.texos\filters` に同梱**する選択肢も。
- これが「**有益な外部モジュールの取り込み**」を抽象論でなく**操作**にする中核。

### 2-B. ローカル AI/メディア処理モジュール群（方針②）
AI-as-filter の入口/出口を増やす。すべて「新種カード不要・既存パイプラインに載る」:
- **OCR**（画像/PDF → テキスト）: tesseract を外部コマンドフィルタで。AI カードへの入口。
- **TTS**（テキスト → 音声）: Piper 等ローカル TTS。AI 出力 .md → 読み上げ .wav。Whisper の対。
- **翻訳／要約／分類**: **AI カードの system プロンプト・プリセット**で実現（新コード不要）。
  「フォルダ要約」「タグ付け」などはマルチコンテキスト注入（1.4.4 `collect_context`）の応用。
- **ローカル埋め込み＋簡易 RAG**（将来）: Ollama の embedding で「プロジェクト内検索カード」。
  AI カードに**プロジェクトの資料を自動で資料注入**する発展。Phase4（フォルダ一括）の延長。

### 2-C. パイプラインの保存・部品化（方針②③の地力）
- 組んだフロー（カード＋矢印の一群）を **「マイモジュール」として保存・再配置**。
  §1-② のエクスポートや図形スコープ（ビジュアルコマンド）と地続き。
- 「自己拡張ループ」（テキスト→コンパイル→フィルタ化、gcc 実証済み）を**カタログ登録まで
  自動化**＝ユーザーが作った部品がそのまま 2-A のカタログに載る。

### 2-D. AI 駆動のフロー組み立て（MCP の代わりに来るもの）
- 旧 V2.0 の「『画像処理をこうしたいからフローを並べて』が通る世界」は、**MCP（外部制御）
  ではなく「AI カードがフロー定義（JSON）を出力 → TexoS が配置」** で実現する方が方針に合う。
  ＝ AI は依然「データを変換するモジュール」のまま、出力先が「フローの設計図」になるだけ。
- これにより「AI が v1.5 の基盤を駆動する」を **MCP 抜きで**達成できる。MCP は対外公開用に温存。

## 3. ロードマップ改訂（提案）

| 旧（陳腐化） | 新（提案） |
|---|---|
| v1.4 = 安定版確定（AI 未計上） | v1.4 = **AI モジュール路線の確立＋UI 衛生**（AI 実装の追認） |
| v1.5 = オートメーション（プロセス制御/ビジュアルコマンド） | v1.5 = **オートメーション＋モジュールカタログ＋プロジェクト間共有**（外部部品とローカル力を太らせる） |
| V2.0 = **AI／MCP**（受け入れ口） | V2.0 = **MCP 公開（対外）＋ウィジェット／サンドボックス**。AI は既に内側にあるので「外向き公開」に焦点 |

要点: **AI を V2.0 から現在地へ引き上げ、MCP だけを V2.0 に残す**。v1.5 の主役は
「プロセスコントロール（§1-④の Job Object 強化を含む）」＋「モジュールカタログ（§2-A）」＋
「プロジェクト間共有（§1-②）」。これが「外部モジュールの取り込み・ローカルでできることを
増やす」という今回の方針の器になる。

### 号割り（ドラフト）
- **v1.4.x（UI 衛生・低リスク・すぐやる）**: ③ライト文字色バグ→UI カラー／ダイアログ追従／
  図形ハンドル左上／メニュー整理。①**Whisper をビルトイン外部コマンドフィルタで追加**。
  ④**ハング再現の特定**＋中断の確実化（小さく）。
- **v1.5.x（基盤工事・中リスク）**: ④**Job Object 化＋実行中プロセス一覧/Stop-all**（プロセス
  コントロール本線）。②**プロジェクト間エクスポート（origin 仮身）**。2-A **モジュールカタログ**。
- **v1.6 / V2.0（対外・大型）**: 2-D **AI によるフロー生成**、**MCP 公開**、ウィジェット/サンドボックス。
