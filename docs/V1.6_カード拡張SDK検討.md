## 0. 結論の先取り（このセッションの合意）

- v1.6 は「ゼロから作るSDK」ではなく、**v1.5 の既存拡張機構（外部フィルタ・ライブラリ・op）を
  「カード定義」として正式化・宣言化する仕事**。
- 境界線: **「一発実行で成果物を吐ける」= v1.6 圏 ／「常駐・リアルタイム・自前タイマー」= v2.0 圏**
  （生成デーモン規約 → docs/生成カード群企画.md §3）。
- パイロット: **ChillChordMaker（I:\ChillChordMaker）の wav 書き出しカード化が v1.6 の「口」**。
  オートプレイ（リアルタイム再生）は実装せず、**v2.0 常駐エンジンの要件洗い出しの試金石**とする。
- 各論（venvポリシー・パラメータ渡し・カスタムUI等）は**性急に決めない**。本ドキュメントの
  §6 未決論点に持ち越す。

## 1. 現状棚卸し — v1.5 は既に「半分プラグインシステム」

| v1.6 の目標 | v1.5 に既にあるもの | 場所 |
|---|---|---|
| プログラム＋JSONで拡張 | 外部フィルタ spec（name / type: filter・command・generator / {in} {out}） | flow.rs `FilterSpec` |
| 可搬な配布 | `.texos/filters/` へのプログラム同梱（import / remove / restore） | filters.rs |
| メニュー登録 | フィルタライブラリ（`カテゴリ/名前` でメニューが畳まれる） | filters.rs・menuBuilder |
| 動的カード | op カード（トリガ／タイマ／ウォッチャ）＋スケジューラ＋停止台帳 | ops.rs |
| Python 環境 | uv ベースの管理環境（uv→CPython→venv→パッケージ。システム Python 非依存。<br>`runtime/envs/<用途>/`・キャッシュ共有で env 追加の増分は小さい設計） | runtime/python.rs（v1.4.27 WS2） |

## 2. ギャップ — 足りないのは3つ

1. **設定フォームが固定**。内蔵フィルタは手書きダイアログ（BuiltinFilterDialog 758行）、
   外部フィルタは汎用ダイアログのみ。ユーザーカードが「自分のパラメータ」を持てない。
   ※ filters.rs に「フォーム自動生成（JSON Schema）はフェーズ2」の予見コメントあり。
2. **カード定義がライブラリの1行 {name, spec} でしかない**。説明・受け入れMIME・アイコン・
   バージョン・同梱プログラムとの紐付けを持つ「パッケージ」の概念がない。
3. **動的（プッシュ）側の拡張点がない**。op 種別は Rust 内で固定。ユーザーが「自分のリズムで
   発火するカード」（シーケンサー等）を書けない。

## 3. 提案骨子 — 3層のSDK

### Level 1: カード定義パッケージ（v1.6 の本体）

1フォルダ＝1カード。`card.json`（マニフェスト）＋プログラム本体＋README。

```json
{
  "id": "wav_synth", "name": "WAVシンセ", "version": "1.0",
  "menu": "ユーザーのカード/音",
  "program": { "name": "synth.py", "type": "generator" },
  "accept_mime": "text/plain", "output_ext": "wav",
  "params": {
    "freq": { "type": "number", "label": "周波数(Hz)", "default": 440 },
    "wave": { "type": "enum", "label": "波形", "values": ["sin", "saw", "square"] }
  }
}
```

- `params`（JSON Schema 風）から設定フォームを**自動生成**。
- 実行エンジンは既存の外部フィルタ経路をそのまま使う。バックエンド新規実装は
  「マニフェスト読取＋フォーム生成＋メニュー統合」に絞る。
- zip 配布は配布構想（SampleProject.zip）と整合。

### Level 2: 動的カード＝op の拡張（プッシュ系）

op スケジューラに「ユーザー op」を1種追加（例: `{"op":"user", "every":秒, "program":…}`）。
発火のたびにプログラムを1回実行して下流へ押し出す。
**プッシュ側は必ず op の停止台帳（pause・Stop-all・多重拒否）の下に置く** —
「要求駆動と自律安全設計.md」の思想（止めるのは作用）と整合させる。

### Level 3: カスタムUIパネル — 唯一の難所（v1.6 では割り切り推奨）

- (a) UIなし。設定フォーム＋出力プレビュー（既存 ImagePreview / AudioPlayer が表示）で済ます
- (b) sandboxed iframe で HTML パネル — 強力だがセキュリティ・レイアウト統合が重い

推奨は **v1.6 は (a)**。(b) は v2.0 の AI 支援・常駐エンジンと合わせて設計する。

sounddevice 不要の可能性 — アダプタ設計時に確認）。(a) では動かない。**未決**。

## 8. 設計原則 — OpenDoc の罠を避ける（2026-07-14 追記）

「なんでもカードに埋め込む」方向はOpenDoc（見た目重視・リソースを食うだけの複合
ドキュメント基盤）の轍を踏む。忘れてはならない事実:

> ChillChordMaker は、正しくランチャーカードを組めば**今の v1.5 でも TexoS から起動できる**。
> しかも TexoS を経由しない分**ネイティブに動く**。埋め込みより速くて軽い。

つまり TexoS には既に3つの統合レベルがあり、埋め込みは最後の手段:

| 統合レベル | 手段 | コスト | 適するもの |
|---|---|---|---|
| 起動 | ランチャーカード | ゼロ（ネイティブ実行） | 対話的な既存アプリ全般 |
| 変換 | フィルタ/generatorカード | 小（一発実行） | データを流したいエンジン |
| 埋め込み | 内蔵ウィジェット | 大（TexoSが抱える） | **デスクアクセサリ級のみ** |

**内蔵ウィジェットの上限 = 「クラシックだが手元に欲しい」デスクアクセサリ級**
（時計カード・電卓カードなど）。それ以外はランチャー／フィルタに合わせて設計するのが正解。

- v1.6 SDK への含意: SDK の目的は「アプリをカードとして抱える」ことではなく、
  **ランチャー／フィルタ型の統合を書きやすくする**こと。§3 Level 3（カスタムUI）の
  割り切りはこの原則から言っても正しい — 単なる先送りではなく、恒久的な歯止め候補。
- ウィジェット設計メモ（V3.0+ の「外部アプリ画面の取り込み＝埋め込みアプリ体験」構想）
  への歯止めとしても働く。あの方向へ行くときは本節を読み返すこと。

### 8.1 実証: tkinter 時計（I:\tokei\tokei.py）— 2026-07-14 実機実験

外部プログラムフィルタ（python.exe・type=コマンド・CMD `"{in}"`）に tokei.py を繋いで
実行 → **時計がネイティブに動いた**。「時計カードを内蔵する」必要すらない可能性を実証。
デスクアクセサリ級ですら埋め込み不要 — TexoS が提供すべきは描画の器ではなく
**ライフサイクル管理**（起動・把握・停止・自動起動）。

判明した問題と答え:
- **問題**: フィルタ経路は同期ジョブ前提のため、常駐アプリが実行中パネルに载り続け、
  中断・Stop-all に巻き込まれる。常用では誤爆リスク。
- **v1.5 の答え**: ランチャーカード（launcher.rs・v1.3.11）が既に detached 起動・
  入力を引数渡し・台帳非登録。python.exe をランチャー登録＋tokei.py を入力に繋げば解決。
  ただし fire-and-forget（TexoS からは止められない・見えない）。
- **v1.6 の設計項目「アクセサリ実行モード」**: ジョブとランチャーの中間管理層。
  detached だが把握する／実行中パネルとは**別枠の「常駐」リスト**／Stop-all **対象外**
  （緊急ブレーキは暴走フロー用 — 時計を殺すのは誤爆）・個別停止のみ／
  **プロジェクトを開いたら自動起動・閉じたら終了**（これでデスクアクセサリが完成する）。
- 補足: tkinter は stdin を読まないので「stdin で停止（q）」は効かない。
  対話的 GUI の終了はアプリ自身の UI で行うのが作法。

**結論（同日）: チップスレベルで解決** — 新機能ゼロ・レシピ1本（ユーザーズチップス Tip 7:
pythonw ランチャー）で「デスクアクセサリ」要求が実用レベルに達した。ソーク期間の思想
（v1.5=道具は完成・使い方の蓄積で解く）が機能した実例。これに伴い「アクセサリ実行モード」は
**必須機能→快適化オプションに格下げ**（常駐リスト・Stop-all 対象外・プロジェクト連動
自動起動が欲しくなった時に再浮上させる）。

**追試（同日）: ランチャーカードで成功。** tokei.py → ランチャー（Python 3.10）で
detached 起動を確認。実行中パネルに載らず、Stop-all の巻き込みなし。時計自身が
最前面・枠なし・透明度・テーマを右クリックメニューで持ち、完全なデスクアクセサリ体験。
- 残った唯一の傷 = python.exe のコンソール窓が一緒に出る。
  **解 = `pythonw.exe`（コンソールなしインタプリタ・Python 標準付属）をランチャー登録**。
  TexoS 側の変更ゼロ。→ ユーザーズチップス.md 行きの定番レシピ候補
  「Python GUI アクセサリは pythonw.exe でランチャー起動」。

## 10. パイロット実装と card.json 逆算（2026-07-15）

### 10.1 ヘッドレス CLI アダプタ — 実装と実証

`I:\ChillChordMaker\cli_render.py` を実装。`synth_engine` のみに依存し
（`audio_io`／`gui` は import しない＝sounddevice・tkinter を引き込まない）、
`WavExporter.export` の後段（TPDF ディザ→int16→`wavfile.write`）をそのまま再現。

```
python cli_render.py --in preset.json --out out.wav   # ファイル入力
python cli_render.py --out out.wav                     # 既定パッチ（引数なし）
type preset.json | python cli_render.py --in - --out out.wav   # stdin
python cli_render.py --in preset.json --out - > out.wav        # stdout（binary）
```

**実機確認済み（2026-07-15）**: 既定パッチ／実プリセット（BellRing.json）／stdin／未知キー混入
の4系統すべて成功。note_duration が出力長に正しく反映（Bell=2.0s・a440指定=1.0s）。
**§4・§5 の2つの予測を確定**:
- 「アダプタは薄い」→ 実質コア5行（`render_offline`＋ディザ＋write）。周辺は引数処理のみ。
- 「書き出しだけなら sounddevice 不要」→ **確定**。realtime 依存は AudioPlayer に隔離済みで、
  エクスポート経路は numpy/scipy のみ。既存の4層分離（§4）がそのまま効いた。

**実物先行で判明した設計要件（仕様先行では出なかった点）**:
- **入力＝パラメータ「束」であってバラのパラメータではない**。ChillChordMaker の入力は
  SynthParams 全体を `dataclasses.asdict` した JSON（既存のプリセット保存形式そのもの）。
  → §3 の card.json `params` は「個々のツマミ」ではなく **1枚のパラメータドキュメント**の
  スキーマ。TexoS 側は「フォームで JSON を編集 → 実身として保存 → generator に流す」。
  付箋＝定数カード（v1.4.17）の発展＝**構造化定数実身**が要る、という含意。
- ~~**出力パスの注入（`{out}`）が新規に要る**~~ **→ 誤り。`{out}` は既に完全実装済み
  だった（下記「§10.5 実機で判明」）**。generator は「どこに書くか」を TexoS が渡す必要が
  あるが、その機構（`{out}`／`{out_noext}`／出力読み戻し）は v1.4 の外部プログラム契約に
  最初からある。binary の stdout 捕捉は Windows で脆いので、実用は `{out}` 一時パス注入が堅い
  （アダプタの `--out -` は保険）。
- **`--in` 省略＝既定動作**を持てると「生成カードを置いた瞬間に1個出る」体験になる
  （入力未接続でも成立する generator の作法）。

### 10.2 card.json マニフェスト第1稿（ChillChordMaker から逆算）

```json
{
  "id": "chillchord_wav", "name": "ChillChord WAV", "version": "1.0",
  "menu": "ユーザーのカード/音",
  "execution": "oneshot",
  "program": {
    "type": "generator",
    "runtime": "python",
    "entry": "cli_render.py",
    "cwd": "self"
  },
  "io": {
    "input":  { "mode": "file", "arg": "--in",  "placeholder": "{in}",
                "mime": "application/json", "optional": true },
    "output": { "mode": "file", "arg": "--out", "placeholder": "{out}",
                "mime": "audio/wav", "ext": "wav" }
  },
  "requirements": ["numpy>=1.24", "scipy>=1.10"],
  "params_schema": "SynthParams"
}
```

- `execution: "oneshot"` — §4 で予告した「将来 `daemon` に増える」軸の第1値。
- `io.input.optional: true` — §10.1 の「既定パッチで成立」を宣言で表す。
- `io.output` に `arg`＋`placeholder` の両方 — TexoS は一時パスを生成して `--out {out}` で渡す。
  stdout モード（`"mode":"stdout"`）も列挙可能にし、テキスト系フィルタと binary 系を同じ枠で扱う。
- `params_schema` — ChillChordMaker では SynthParams（dataclass）が既にスキーマそのもの。
  第2稿では dataclass のフィールド定義（型・既定・範囲コメント）から JSON Schema を
  半自動抽出できるか検討（`vco_frequency: float = 220.0  # Hz 20-2000` のコメント範囲が
  そのままフォームの min/max になる）。当面は card.json に手書きスキーマを同梱で可。

### 10.5 実機で判明 — Task A（`{out}` 契約）は既に完成していた（2026-07-15）

`feat/v1.6-cards` ブランチで A に着手したところ、**`{out}` は追加不要だった**。

### 10.9 ステップ2 完了（2026-07-15）— `{out*}` 複数出力エンジン実装

v1.6 で唯一エンジンに手を入れる項目。**改修は局所で済んだ**（下流のカード生成は
元から Vec 対応＝L1391-1420 の縦積み）:

- **flow.rs `run_external_full`**: CMD に `{out*}` があれば一時フォルダ `outs_<nanos>` を
  生成して置換 → 終了後にフォルダ内全ファイルを**ファイル名の辞書順**で収集して
  `ExternalOutput.multi: Option<Vec<(ファイル名, バイト列)>>`（新フィールド）に。
  サイズ上限 512MB は**フォルダ合計**に適用。フォルダは読み取り後に削除（TEMP 孤児なし）。
- **flow_run.rs**: `NodeRun.outputs` を `(bytes, ext, mime, stem_override)` の4要素に。
  `{out*}` の各ファイルは**自分の拡張子**で ext/MIME を決め、**ファイル名の語幹がカード名**
  になる（`t_01_1_Dm7.wav` → カード「t_01_1_Dm7」— プログラムの命名が活きる）。
  成否ポリシーは単一出力と同一（非0→エラー・出力ゼロ→エラー）。
- `is_self_contained()` は `contains("{out")` 判定なので `{out*}` も自動的に「出力あり」扱い（無改修）。

### 10.10 「新規カードを登録」カード（2026-07-15）— 随時登録パターンの完成

**発端（dev 実機・本人発見）**: `{out*}` は終了時一括でしかキャンバスに出ない。ウォッチャで
随時登録しようとしたら「**登録する作用側のカードが無い**」— op=発火／作用=カードの分離設計の
正当な帰結としての穴。登録の本体は `import_new_project_files`（launcher.rs・v1.3.11）として
既存だが、UI コマンドでありカードではなかった。

**実装**: `{"builtin":"import_new"}`（カード名「新規カードを登録」・メニュー=OS機能グループ）
- **eval 側で完結**（セレクタと同じ流儀）: 入力を取らず spec.path のフォルダ
  （**空=プロジェクト直下**）を走査し、未登録ファイルをカード登録。新カードは本カードの下に
  5列グリッド。`is_self_contained` に追加（出力ペイロードなしが正常・speak と同格）。
- **既知判定は committed_path と origin_path の両方**（フロー出力の実身も窓仮身も二重登録し
  ない）。判定は登録直前＝並行発火の競合窓を最小化。
- **スキップ**: 先頭 `~`/`.`・拡張子 tmp/part/crdownload/bak（一時・隠し・ロックファイル）。
- **プロジェクト内=実身／外部フォルダ=窓仮身** — import_file を `import_file_into(p, …)` に
  分離してジョブ専用接続から再利用（in_project 判定は既存のまま）。
- フロント: メニュー＋設定ダイアログ（対象フォルダ text 欄・空=プロジェクト直下）。

**成立した統合パターン**（規約書に追記予定・ユーザーズチップス候補）:
- `{out*}` = **同期一括**（TexoS がプログラムを実行した成果・ジョブ束縛）
- **ウォッチャ → 新規カードを登録** = **非同期随時**（観測）— ネイティブ GUI アプリの書き出し
  （ChillChordMaker の BATCH EXPORT）・フォルダへの直接ドロップ・何でも拾う。
  設定は「**同じフォルダパスを2枚のカードに書く**」だけ。

テスト: `import_new_registers_and_dedups`（実プロジェクトfixture・登録2/スキップ3/再実行0/
不在フォルダはエラー）green・回帰86件 green・tsc green。
