# サブプロジェクト方針検討結果

検討日: 2026-06-12 / 入力: `docs/サブプロジェクト関連.txt`

> **2026-06-12 決定: 優先順位の反転。**
> サブプロジェクトの本実装（§3 移動・§4 削除・§5 クロスリンク）はコスト高のため後回しにし、
> **外部アプリ／OSとの連携（持ち出し）を先に整理・実装する**（§7）。
> サブプロジェクトは将来 OS 依存部分が減った段階で必須になるため、本書の設計は維持する。
> 着手時の前提決定: ①移動の UNDO は無し（逆移動で戻す） ②`origin_path == committed_path`
> カードは仮身化して移動（取り込み元ファイルは動かさない） ④親リンクの project_ref は相対パス化する。
> ③内部 Ctrl+X/C/V は「外部連携側から先に整理する」方針に変更（§7）。

## 0. 前提（現状アーキテクチャの確認）

- プロジェクト＝フォルダ＋`.texos/`（texos.db, cas/）。カード＝virtual_bodies（UUID）、
  実身＝CAS（SHA-256）。**relations はプロジェクトDB内ローカル**（from_id/to_id＝仮身UUID）。
- サブプロジェクト＝内包フォルダ＋親キャンバス上の project_ref カード（`create_subproject`）。
- フォーク（分岐）は vid を保持したまま全コピーする（`fork_structure_into`）。
  → **vid は世界一意ではない**。クロスプロジェクトのリンク同一性は
  **（プロジェクトパス, vid）の組**で扱う必要がある。
- ATTACH DATABASE による DB 間一括コピーは fork で実績あり
  → カード移動も同じ機構で実装できる。

## 1. 操作の一般化（メモ1〜5への回答）

操作を3層に分けるのが整理の軸:

| 層 | 操作 | 意味 | 状態 |
|---|---|---|---|
| 層1: 配置移動 | 同一キャンバス内ドラッグ | 座標変更 | 実装済み |
| 層2: 内部転送 | TexoS内のフォルダ間移動 | **仮身の所属変更**（ID不変・データ不滅） | 今回の本丸 |
| 層3: 境界転送 | OS⇔TexoS | 取り込み＝インポート／持ち出し＝エクスポート（コミットの一種） | 取り込みのみ実装済み |

一般化の方法: **「転送ペイロード」＝{対象カード集合, 操作(move/copy)}** という内部抽象を
1つ定義し、ジェスチャ（D&D・Ctrl+X/C/V・ピックアップ）はすべてこれにマップする。

### Ctrl+C/V と外部ドロップの違い（メモ3・4）

意味が根本的に違う:
- **内部転送＝参照の付け替え**（仮身が動く。実身は CAS に残り、ID は変わらない）
- **外部への持ち出し＝バイト列の複製**（実身のエクスポート＝コミット相当）

→ 同じ操作に見せない。**内部転送は OS クリップボードを経由しない**
（アプリ内のピックアップ状態／内部クリップボードで保持）。
OS クリップボードが登場するのは境界（層3）だけで、そこで明示的に変換する。

### Windows クリップボードとの関係の整理（メモ4）

- **受け（OS→TexoS）**: Ctrl+V／ドロップ＝インポート。実装済み（画像/テキスト/URL/ファイル、複数可）
- **出し（TexoS→OS）**: 仮身の一時実体化が必要で TEMP 孤児問題が再発する
  （V2.0課題1のピックアップと同根）→ **当面非対応のまま据え置き**。
  代替は v1.2 の「コミットしてプロジェクトフォルダで表示」
- **アプリ内 Ctrl+X/C/V**: 内部クリップボード（メモリ上）で実装。
  TexoS にフォーカスがある限り内部を優先

### 外部へのドラッグアウト（メモ3）

OLE ドラッグソース（DoDragDrop + CF_HDROP）が必要。V2.0課題1のまま据え置きでよい。
サブプロジェクト機能とは独立に後から足せる（層が分かれているため）。

## 2. 作成時の方針

1. **親リンクカード: 採用**。サブプロジェクト作成時、子キャンバスの原点付近に
   親への project_ref カードを自動配置（ラベル例「⬆ 親: <名前>」）。
   実装は `link_project` と同機構。
   - 注意①: 全コミット警告で「外部プロジェクト」赤警告にならないよう、親リンクは区別する
   - 注意②: project_ref は現状絶対パス。親フォルダごと移動すると切れる →
     内包関係は**相対パス化 or 開いた時に修復**（repair_mime_types の前例に倣う）
2. **「選択カードを内包して作成」: 採用**。カード選択中の右クリックメニューに追加。
   選択カードは新サブプロジェクトへ移動（移動の意味論は §3）。
3. **D&D 移動: 採用**。プロジェクトカードへのドロップ＝そのプロジェクトへ移動、
   親リンクカードへのドロップ＝親へ移動。同一ジェスチャ「カードへのドロップ＝移動」で統一。
   修飾キーでコピー（将来拡張、今は移動のみ）。

## 3. カード移動の意味論（新規・最重要）

`move_object_to_project(vids, dest)` を新設:

- **virtual_bodies 行を ATTACH で移す。vid は維持**（クロスリンク ID 安定の前提）
- **real_bodies 行＋CAS 実体を物理コピー**（INSERT OR IGNORE。同ハッシュなので重複しない）。
  理由: 「プロジェクト＝フォルダ」の自己完結原則（持ち出し・配布で壊れない）。
  フォークの「親 CAS 参照チェーン」方式とは敢えて変える（フォーク＝派生、移動＝所属変更で別概念）
- **コミット済み実ファイルはカードと一緒に移動**（親フォルダ→サブフォルダへ、committed_path 更新）。
  「カードがサブプロジェクトにある＝ファイルがサブフォルダにある」を保つ
  - **例外**: `origin_path == committed_path`（プロジェクト内取り込み元そのもの、v1.2.1 の教訓）
    → 取り込み元ファイルは動かさない。origin 参照の仮身として移す（要確認 → 要決定事項2）
- relations の扱いは §5
- **UNDO**: クロス DB の undo は複雑。第1段階は移動を UNDO 非対応とし
  「逆方向の移動で戻せる」ことで代替する案を推奨（→ 要決定事項1）

## 4. 削除時の方針

単一ルールにせず、**確認ダイアログでメモの a/b/c を全部使う**:

- 空 → そのまま削除（カードもフォルダも）
- 非空 → ダイアログ3択:
  - 「中身ごと削除」(b) — フォルダごと親の `.texos/trash/` へ退避すれば
    ソフトデリート（復活の呪文）と整合し、安全に提供できる
  - 「中身を親に出してフォルダだけ削除」(c) — §3 の move を全カードに適用するだけ。実装共通化
  - 「キャンセル」(a) — 既定ボタン
- **カードの削除とフォルダの削除を区別する**:
  - 内包サブプロジェクトのカードは唯一のハンドル → カード削除時は必ずフォルダの扱いを聞く
  - `link_project`（外部参照）のカード削除は参照削除のみ（フォルダ無傷、現行どおり）

## 5. リンク矢印（クロスフォルダリンク）— メモ案2を採用・具体化

- **同一性**: 端点は（プロジェクト, vid）。vid はフォークで複製されるため単独では世界一意でない
- **格納**: relations はローカル DB のまま、`peer_project TEXT` 列を追加（NULL＝ローカル）。
  クロスになったリンクは**両側の DB に行を持つ**（出側と入側で対称に）。
  移動操作は常に「開いているプロジェクト」がブローカーになるので、
  両 DB への書き込みは ATTACH で可能
- **表示**: 相手が同フォルダにいないリンク → カードに入力矢印／出力矢印アイコン
  （メモの決定どおり）。LinkLayer は矢印を描画しない（アイコンのみ）
- **ナビゲーション**: アイコンをダブルクリック → 相手プロジェクトを開いて該当カードにフォーカス
  （プロジェクト行き来＋選択範囲フォーカスの既存機構の組み合わせ）
- **両方のカードが別サブプロジェクトへ移動した場合**（メモの懸念）:
  移動のたびにブローカー（親）が両側の peer_project を更新すれば成立する。
  ただしサブプロジェクトを単体で開いて中のカードをさらに動かすと相手 DB を更新できない →
  **第1段階は「クロスリンクの付け替えを伴う移動は親（共通祖先）を開いて行う」制約**でよい
- **修復**: peer_project はパスなので壊れうる。プロジェクトを開いた時に peer の生存確認、
  不明なものは薄赤系シグナル（「窓の喪失」と同じ語彙）で表示
- **パイプライン（kind='flow'）**: スキーマ上はクロス可能にしておくが、
  **フロー実行はまず同一プロジェクト内のみ**（オートフロー MVP「小さく始める」と整合）
- **多プロジェクトへのリンク**: peer_project 列方式は1対1のまま将来 N 対応に自然拡張できる。
  今は無しで OK（メモどおり）

## 6. 実装の段階分け（2026-06-12 改訂: 外部連携を先行）

- **先行: 外部連携（持ち出し）** — §7。クリップボード持ち出し → OLE ドラッグアウトの順
- **後続 Phase 1**: `move_object_to_project`（§3）＋ 親リンクカード ＋
  「選択カードを内包して作成」＋ プロジェクトカード／親リンクへの D&D 移動
- **後続 Phase 2**: クロスリンク（peer_project 列・アイコン表示・ダブルクリックでフォーカス）
- **後続 Phase 3**: 削除ダイアログ＋フォルダの trash 退避

## 要決定事項 → 決定済み（2026-06-12）

1. **移動の UNDO**: **無し**で開始。逆方向の移動で戻せることを UI 上も前提にする
2. **`origin_path == committed_path` カードの移動**: 提案どおり**仮身化して移動**
   （取り込み元ファイルは動かさない）
3. **内部 Ctrl+X/C/V**: 外部アプリ／OS 連携側から先に整理する方針に変更（§7）。
   内部転送のジェスチャは外部連携で確立した転送ペイロード抽象に後から乗せる
4. **親リンクの project_ref**: **相対パス化あり**（内包の堅牢性優先。
   既存の絶対パス project_ref は読み込み互換を維持し、内包作成時のみ相対で書く）

## 7. 外部連携（持ち出し）の方針骨子 — 先行実装分

### 原則: エクスポート＝コミット

持ち出しは層3（境界転送）＝「バイト列の複製」。**外部へ出る実体は必ずコミット済み実ファイル**
とする。未コミット仮身を持ち出す操作は、その場でコミット（確認あり）してから
committed_path を渡す。
- これにより **TEMP 孤児問題（V2.0課題1）が構造的に消滅**する
  （一時実体化が不要。外部に渡すパスは常にプロジェクトフォルダ内の実ファイル）
- 「持ち出し＝エクスポート＝コミットの一種」という §1 の層モデルと意味論が一致する
- 貼り付けが後刻でも安全（クリップボード上のパスはプロジェクト内で生き続ける）

### 第1弾: クリップボード持ち出し（Ctrl+C）— 低コスト・高効果

ジェスチャ問題が無く（ドラッグと衝突しない）、Win32 クリップボード API のみで実装できる。
選択カード（複数可）に対して Ctrl+C ／右クリック「コピー（外部へ持ち出し）」:

| カード種別 | クリップボード形式 |
|---|---|
| ファイル実身（コミット済み） | CF_HDROP（複数ファイル対応） |
| 未コミット仮身 | コミット確認 → CF_HDROP |
| テキストカード | CF_HDROP ＋ CF_UNICODETEXT（本文。テキストとしても貼れる） |
| 画像カード | CF_HDROP ＋ CF_DIB/PNG（Word・ペイントに直接貼れる） |
| URL カード | CF_UNICODETEXT（URL 文字列） |
| 付箋 | CF_UNICODETEXT（本文）。ファイル化は対象外（既存の右クリックコミットで代替） |

- 実装: arboard はファイルリスト非対応のため、CF_HDROP（DROPFILES 構造体）は
  Win32 直叩き（OpenClipboard / SetClipboardData）。drag_drop.rs（受け側の独自実装）と
  対になる送り側モジュール
- 受け（Ctrl+V）は実装済みのため、これで**クリップボードの双方向が完成**する

### 第2弾: OLE ドラッグアウト（DoDragDrop + IDataObject）

- エクスポート＝コミット原則は同じ（ドラッグ開始時にコミット確認）
- 操作設計が必要（通常ドラッグはカード移動に割り当て済み）:
  長押しドラッグ／修飾キー＋ドラッグ／ピックアップモードの3案から実装時に選定
- 第1弾のクリップボード形式生成コードをそのまま IDataObject に流用できる

### 内部転送との接続（将来）

第1弾で確立する「選択カード集合 → 転送ペイロード → 形式変換」の流れが §1 の一般化の実装になる。
サブプロジェクト着手時、内部 Ctrl+X/V・ピックアップ・D&D 移動は同じペイロード抽象に
変換先（内部 DB 移動）を足すだけで接続する。
