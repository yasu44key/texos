実装はこの凍結仕様に従う。版割り = (A) v1.4.11 ／ (B)(C) v1.5 序盤。変更は本書改訂を伴う。

> ランタイム**」へ移る。録音/AI/外部プログラムが**裏で並行**に走り、ユーザーはその間も思考を続け、
> 口述しながら次を仕込める。これは v1.4.9 の録音ハングと同根の問題を、設計として正面から解く作業。

## 0. 結論（先に要点）

1. **モデルは2階層**。**実行単位＝ノード**（`execute_node`・v1.4.10 で確立）／**実行文脈＝ジョブ**
   （これから作る。1回の `run_flow` 起動＝1ジョブ）。並行とは「ジョブが複数同時に走る」こと。
2. **(A) 非ブロッキング実行が最初の一歩**（v1.4.11）。`run_flow` が長時間実行の間ずっと
   `state.current`（DB Mutex）を握る今の構造を解く。これだけで「録音/AI 中も UI が生きる」。
3. **(B) ジョブレジストリで singleton を撤廃**（v1.5 土台）。`flow_cancel`/`chat_cancel`/
   `rec_stdin`/`flow_running`（各1個＝単一フロー前提）を **`JobId` キーの台帳**へ。
   これは同時に `要求駆動と自律安全設計 §6.3` の**中央 kill スイッチ**になる。
4. **資源の複数活用は「資源タクソノミ＋並行セマンティクス」で定義**（§5）。何が排他で何が
   並行可かを資源ごとに決め、**セマフォ（許可数）**で調停する。並行上限は
   `要求駆動と自律安全設計 §6.2` の**ヒューズ**そのもの。
5. **プロセス通信は2方向に一般化**（§7）。制御 IN＝`rec_stdin` を**ジョブ別 stdin チャネル**へ／
   観測 OUT＝既存の `app.emit`（チャットトークン・Whisper 進捗）を**ジョブ別イベントストリーム**へ。

## 1. なぜ今これなのか（v1.4.9 録音ハングとの地続き）

録音ハングの根因＝`run_flow` が `state.current` を**実行の全期間**ロックする（`eval_filter` が
録音プロセスの終了までブロックするため）。v1.4.10 では「再入を弾く」対症療法（`flow_running`）で
止めたが、**根治はロックを手放すこと**。手放せれば:
- 録音/AI 実行中もカード操作・閲覧・編集ができる（フリーズしない）。
- 複数ジョブを同時に走らせる素地ができる（録音しながら別の AI、口述→whisper を並行）。

つまり (A) は「録音ハング修正の残り半分」であり、並行実行の入口でもある。

---

## 2. 2階層モデル：ノードとジョブ

| | **実行単位＝ノード** | **実行文脈＝ジョブ** |
|---|---|---|
| 何 | フィルタ/外部/AI/ジェネレータ 1個の実行 | 1回の実行要求（`run_flow` 起動）。部分グラフの pull 評価全体 |
| 実装 | `execute_node()`（v1.4.10・確立済み） | これから。`Job{ id, kind, cancel, control, progress, resources }` |
| 状態 | ステートレス（入力→出力＋exit/stderr） | ライフサイクルを持つ（実行中/完了/失敗/中断） |
| 並行 | 1ノードは1スレッド | **複数ジョブが同時に走る** |

**ジョブのライフサイクル**: `Queued → (資源許可 acquire) → Running → {Done | Failed | Canceled}`。
完了で資源許可を release、結果カードを materialize（DB 書き込み）、UI へ `job:done` を emit。

---

## 3. (A) 非ブロッキング実行 ＝ ロック規律（v1.4.11・最優先・低リスク）

**原則: DB ロックは「短いクリティカルセクション」でだけ握る。長時間の実行（外部プロセス・AI・録音）
の間は手放す。**

現状の `run_flow`/`eval_filter` は `p: &Project`（= `state.current` ガードからの借用）を実行中
ずっと持ち回る。これを次の規律へ:

1. **読む（ロック）**: 終端 spec・入力グラフ・入力バイト列を**スナップショット**として取り出す。
2. **走る（ロック外）**: `execute_node` を**ロックを手放して**呼ぶ（外部/AI/録音はここ）。
3. **書く（再ロック）**: 結果を CAS 保存・カード生成・矢印・seq 書き戻し。短時間で済む。

実装メモ:
- `eval_filter` は pull 再帰で DB を断続的に読む。素朴には「読む↔走る」が交互に来るので、
  **入力収集フェーズ（locked, 速い）と実行フェーズ（unlocked, 遅い）を段で分ける**現構造
  （v1.4.10 で既に「収集→実行」に整理済み）が効く。実行フェーズだけロック外へ出す。
- v1.4.11 は **単一フロー前提を維持**（`flow_running` ガードは残す）。つまり「同時に1ジョブ」
  だが「実行中もUIは生きる」。並行（複数ジョブ）は (B) で解禁。段を分けることでリスクを抑える。
- SQLite は WAL なので、書き込み中でも読みは並行可。クリティカルセクションを短く保てば衝突しない。

## 4. (B) ジョブレジストリ ＝ singleton 撤廃（v1.5 土台 ＝ 中央 kill スイッチ）

現 `AppState` の単一スロット（＝「同時に1つ」を物理的に強制している箇所）:

| 現フィールド | 役割 | ジョブ化後 |
|---|---|---|
| `flow_cancel: AtomicBool` | フロー中断（`break_flow`） | `Job.cancel`（ジョブ別） |
| `chat_cancel: AtomicBool` | チャット中断（`ai_chat_cancel`） | `Job.cancel`（同上に統合） |
| `rec_stdin: StdinSlot` | 録音 stdin（`flow_send_stdin`） | `Job.control`（ジョブ別 stdin、§7） |
| `flow_running: AtomicBool` | 多重起動ガード（v1.4.10） | レジストリの存在＝実行中。許可数で制御 |

```
struct Jobs { map: Mutex<HashMap<JobId, Arc<Job>>> }
struct Job {
    id: JobId, kind: JobKind, label: String, started_at: i64,
    cancel: AtomicBool,                 // 中断（break）
    control: StdinSlot,                 // 制御 IN（'q' 等。録音/対話）
    // progress/状態は emit で UI へ（§7）。所有資源の permit は実行中だけ保持。
}
```

- `break_flow(job_id)` / `flow_send_stdin(job_id, text)` / `cancel_all()` は**台帳引き**になる。
- **`cancel_all()` ＝ `要求駆動と自律安全設計 §6.3` の中央 kill スイッチ**（カードが画面外でも
  残る最後の物理停止）。`taskkill /T` ツリーkill は既存。
- UI の「フロー実行中…」パネルは**ジョブ一覧パネル**へ拡張（§8）。

## 5. 資源の複数活用の定義（資源タクソノミ × 並行セマンティクス）

**「資源の複数活用」とは: 複数ジョブが同じ/異なる資源を同時に使うときの可否と調停を決めること。**
資源ごとに並行性が違う。混ぜると壊れる（同じマイクで2録音、同一パスへ同時書き込み等）。

| 資源 | 並行性 | 調停（セマフォ/ロック） |
|---|---|---|
| **DB（current Project / SQLite）** | 単一書き手・短時間 | (A) で実行中は手放す。書きは短いクリティカルセクション。WAL で読みは並行可 |
| **CAS（.texos/cas）** | 追記専用・内容アドレス | **ロック不要**（同一内容＝同一ハッシュ＝冪等。並行 store は安全） |
| **音声入力デバイス（dshow mic）** | **排他**（同一デバイスで2録音は不可） | **デバイス名キーのセマフォ＝1**。別マイクなら並行可 |
| **AI エンドポイント/モデル（Ollama 等）** | サーバ側で直列化・VRAM制約 | **エンドポイント単位の許可数**（既定1〜2・設定可）。keep_alive 常駐と相性 |
| **外部プログラム / CPU** | 有界並列 | **グローバル「重ジョブ」許可数**（既定＝コア数前後・可変）＝ §6.2 ヒューズの並行上限 |
| **出力ファイルパス（committed/origin）** | 同一パスへの同時書き込み禁止 | **パス単位ロック**。prefix 連番 `seq` の採番も**直列化**（書き戻し競合の防止） |
| **外向き作用（送信・起動・削除）** | §3 作用クラス | セマフォではなく**人間ゲート**（`要求駆動と自律安全設計 §3`）。ここは並行性の問題でなく安全の問題 |

**定義の核**: ジョブは起動時に**必要資源を宣言**し（`NodeKind`＋spec から導出: デバイス名・AI
エンドポイント・「重い外部」か）、対応する**許可（permit）を acquire してから Running**、完了で
release。許可が取れなければ Queued で待つ（or 即エラー＝設定可）。

## 6. セマフォ ＝ 資源許可（ヒューズと同一物）

```
struct ResourceLimits {
    heavy: Semaphore,                         // 重い外部プロセスの並行上限（既定 = N）
    ai: HashMap<Endpoint, Semaphore>,         // AI エンドポイント別
    device: HashMap<DeviceName, Semaphore(1)> // 入力デバイス別＝排他
}
```

- **許可数＝ `要求駆動と自律安全設計 §6.2` のヒューズ**（「1実行あたり…並行プロセスに上限」）。
  安全のための上限と、資源保護のための上限は**同じ機構**で実現できる。
- 上限超過時の挙動は2択（設定可）: **待つ（Queued）** か **即エラー（拒否）**。録音のような
  排他資源は「拒否＋案内」（v1.4.10 の再入エラーの一般化）、CPU 重ジョブは「待つ」が自然。
- permit は RAII（取得トークンの Drop で release）。`RunningGuard`（v1.4.10）の一般化。

## 7. プロセス通信（IPC）＝ 双方向に一般化

既にある2つの原語を**ジョブ別**に引き上げるだけ。新しい配管は最小。

### 7.1 制御 IN（ジョブ → 子プロセスへ送る）
- 現: `rec_stdin`（単一）＋ `flow_send_stdin(text)` で 'q' を送り録音を正常終了。
- 後: `Job.control`（ジョブ別 stdin）＋ `flow_send_stdin(job_id, text)`。録音停止・対話プログラム
  への入力・将来の「一時停止/再開」コマンドの共通口。**汎用子プロセス制御チャネル**。

### 7.2 観測 OUT（ジョブ → UI へ返す）
- 現: `app.emit("...")` をチャットのトークン逐次表示・Whisper ダウンロード進捗で使用済み。
- 後: **ジョブ別イベント**へ規格化: `job:started` / `job:progress`（%・行・stderr）/
  `job:stdout` / `job:done` / `job:failed`（payload に `job_id`）。UI は購読してジョブパネルと
  カードの緑シグナルを更新。長時間ジョブの**生きた進捗**が見える（録音経過・AI生成中・変換中）。

### 7.3 ジョブ間（将来・v1.5 モジュール）
- 現: pull 評価が中間ペイロードを**メモリで**次段へ渡す（中間ファイル/カードを作らない）。
- 将来: 長時間ジョブ同士のストリーム接続（名前付きパイプ/チャネル）は**部分グラフ＝モジュール**
  （`共有とモジュール設計.md §2`）の実行モデルと一緒に設計。**今は保留**（塞がないだけ）。

## 8. (C) 背景ジョブパネル（UI ＝ 中央 kill スイッチの表面）

- 現「フロー実行中…」1行パネルを、**実行中ジョブの一覧**へ。各行: ラベル／種別アイコン／経過／
  進捗／**停止（control 'q'）**／**中断（cancel＋taskkill）**。最下部に **Stop-all**。
- カードが画面外・プロジェクト切替後でも**パネルに残る**（§6.3 の「最後の物理停止」）。
- 来歴（provenance, §6.4）: 生成カードに「どのジョブが・何を入力に」を緑シグナル＋relations で。

## 9. 自律安全との接続（要求駆動ドキュメントとの一致点）

本設計は安全設計の**実行基盤**を兼ねる。意図して同じ機構に寄せる:
- **並行上限セマフォ（§6）＝ ヒューズ（安全§6.2）**。
- **ジョブレジストリ＋Stop-all（§4/§8）＝ 中央 kill スイッチ（安全§6.3）**。
- **イベントストリーム（§7.2）＝ 可視化（安全§5「サイレント自律を画面に出す」）**。
- ただし**作用クラスの門（安全§3: 削除/送信/外部起動）は別レイヤ**。セマフォは「資源の取り合い」を
  調停するもので、「不可逆・外向きを人間ゲートで止める」のは capability 層の仕事。混同しない。

## 11. 決定事項（凍結・2026-06-27）

旧オープン論点を確定。以後はこの既定で実装する（変更は本書改訂を伴う）。

1. **(A) ロック手放しの境界＝「DB 接触は短いクリティカルセクション、実行はロック外」を徹底**。
   `run_flow`/`eval_filter` は `&Project` を持ち回らず、DB 触りごとに `with_db(&state, |p| …)`
   （current を lock→読/書→即 unlock）で行う。`execute_node`（外部/AI/録音）は**いかなるロックも
   持たずに**呼ぶ。pull 再帰の各ノードは「短い読み（locked）→実行（unlocked）→短い書き（locked）」を
   繰り返す。これで長時間ロックは構造的に消える（プロトタイプで境界を確認しつつ進める）。
2. **上限超過の既定**: **排他資源（マイク／同一 AI エンドポイント超過）＝拒否**（即エラー＋案内。
   v1.4.10 の再入エラーの一般化）。**CPU 重ジョブ＝待つ（Queued・FIFO）**。資源クラスごとに固定。
3. **AI エンドポイント同一性** = URL 正規化（trim・ホスト小文字・末尾 `/` 除去）。**既定許可数=1**
   /エンドポイント（Ollama はサーバ側で直列化。設定で増やせる）。
4. **出力パス/seq 採番** = **プロジェクト単位の採番ロック**で `seq` 書き戻しを直列化。パス衝突は
   materialize 時の短ロック内で既存カード照合（v1.4.10 の固定名上書きロジックを踏襲）。
5. **ジョブは揮発**（アプリ再起動で消える）。永続化しない。終了時に実行中プロセスは `taskkill /T`。
6. **フロント emit** = `job:progress` は**スロットル**（最大 ~10/s・ジョブ別）。トークン/行は欠落
   させず累積はバックエンド側が保持（チャットの既存方式を踏襲）。

## 12. 実装計画（A+B+C 通し・凍結）

### 12.0 共通の下ごしらえ（A の前に・破壊なし）
- `with_db(&AppState, |p: &Project| -> T)` ヘルパー（current を lock→クロージャ→unlock）。既存の
  `let guard = state.current.lock()` 群を段階的にこれへ寄せる土台。まず `run_flow` 系だけ移行。

### 12.A 非ブロッキング実行（v1.4.11・新機能なし・単一フロー維持）
- `run_flow`/`eval_filter` を `&Project` 持ち回りから `with_db` 規律へ書き換え。実行フェーズ
  （`execute_node`・shell 起動）はロック外。`flow_running` ガードは**残す**（同時実行は当面1）。
- 不変条件: 出力カード生成・命名・連番・skipped/errors・録音 stdin・集約/ファンアウト・循環検出は
  すべて従来どおり（v1.4.10 と同じ安全網＝ユニットテスト＋実機録音）。
- 体感: 録音/AI/外部プログラム実行中もキャンバスが固まらない。**録音ハングの根治**。
- 完了で **v1.4 系を「並行の入口まで来た安定版」として一区切り**。

### 12.B ジョブレジストリ（v1.5 序盤・singleton 撤廃）
- 型: `Jobs{ map: Mutex<HashMap<JobId, Arc<Job>>> }` を `AppState` に追加。`Job{ id, kind, label,
  started_at, cancel: AtomicBool, control: StdinSlot }`。
- 撤廃: `flow_cancel`/`chat_cancel`/`rec_stdin`/`flow_running` → ジョブ別フィールドへ移送。
- コマンド改修（**job_id 引数化**。「後方互換は新コマンド併設で吸収」は **2026-07-05 改訂:
  併設せず一気に置き換え**——内部APIでありフロントも同時改修するため。ユーザー決定＝
  `docs/v1.5_実装指示書.md` 全体方針3）:
  `run_flow` は起動時に Job を登録し `job_id` を返す → フロントが以後の制御に使う。
  `break_flow(job_id)` / `flow_send_stdin(job_id, text)` / 新 `list_jobs()` / 新 `cancel_all()`。
- `cancel_all()`＝中央 kill スイッチ（`要求駆動と自律安全設計 §6.3`）。`taskkill /T` は既存流用。

### 12.C 資源セマフォ＋イベント規格化＋背景ジョブパネル（v1.5 序盤）
- 型: `ResourceLimits{ heavy: Semaphore, ai: Map<Endpoint,Semaphore>, device: Map<Name,Semaphore(1)> }`
  を `AppState` に追加。ジョブは spec/NodeKind から**必要資源を導出**し permit を RAII 取得
  （`RunningGuard` の一般化）。超過時は §11.2 の既定（拒否/待つ）。
- 並行解禁: `flow_running` の「同時1」を撤廃し、**資源許可が許す限り並行**。run_flow は
  `#[command(async)]`（既存）＝ワーカースレッドで複数走る。
- イベント規格: `job:started/progress/stdout/done/failed`（payload に `job_id`）。`execute_node` /
  `run_external_full` の進捗（既存の on_token・whisper 進捗）をこの規格へ寄せる。スロットルは §11.6。
- UI: 「フロー実行中…」1行 → **背景ジョブパネル**（一覧・経過・進捗・停止(control)・中断(cancel)・
  最下部 Stop-all）。カードが画面外でも残る（最後の物理停止）。来歴は緑シグナル＋relations。

### 12.D 検証方針
- A: 既存ユニットテスト緑＋実機（録音中にカード操作できる／録音→停止→WAV／集約・AI・shell）。
- B/C: 並行特有の検証＝①2録音（別デバイス可・同デバイス拒否）②録音中に AI 並行③重ジョブ多数で
  許可数まで並行・以降待ち④Stop-all で全停止⑤デッドロック無し（資源取得順序を固定）。
- **資源取得は常に同一順序**（device→ai→heavy）で取り、デッドロックを構造的に防ぐ。

### 12.E スコープ外（このフェーズで作らない・塞がないだけ）
- ジョブ間ストリーム接続（名前付きパイプ）＝モジュール（部分グラフ）実行と co-design（v1.5 後半+）。
- 作用クラスの門（削除/送信/外部起動の人間ゲート）＝capability 層（`要求駆動と自律安全設計 §3`・別レイヤ）。
- ジョブの永続化・分散実行。
