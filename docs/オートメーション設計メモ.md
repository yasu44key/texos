## 0. 起点となった気づき（2026-06-18 ユーザー）

- フィルタで分かったこと: **CMD の子プロセスとして立ち上げれば、あらゆるプログラムを
  起動・制御できる**。プログラムの登録・コントロールの基礎になる。
- コマンドラインで制御できる "お行儀のよい"（歴史的に行儀の良い）プログラムは、
  **CLI オプションが充実**し、**戻り値（exit code）で実行結果が分かる**。
- 図形は「ビジュアルにもロジックが組める」ことの証明だった（含まれるカードに対して
  コマンドを実行できる）。この**ビジュアルコマンド**の充実も検討対象。

→ v1.5 系のテーマ = **オートメーション**。2本柱: ①プロセスコントロールカード、
②ビジュアルコマンド。両者は「**図形（スコープ）＋プロセスコントロール ＝ 領域内の
カードへ foreach**」で統合される。

## 1. プロセスコントロールカード（フィルタの一般化）

### 1.1 何を足し、何を流用するか
既存フィルタ（`flow.rs`）は「データ → 変換 → データ」の一直線。プロセスコントロールは
これを**プログラムの起動・制御**へ一般化する。**難所は既に実装済み**で流用できる:

| 流用できる足場（実装済み） | 新しく足す軸 |
|---|---|
| async 実行（`run_flow` は `#[tauri::command(async)]`） | **exit code による制御フロー（分岐）** |
| タイムアウト（`timeout_secs` 既定 60） | 成功／失敗で下流ノードを選ぶ配線 |
| taskkill /T のツリー kill・中断ボタン | exit code・stdout・stderr を**結果値**として扱う |
| stdout/stderr 捕捉・出力 512MB 上限・stdin 遮断 | （任意）戻り値で結果カードの内容を切り替え |
| `{in}`/`{out}`/`{in*}`/`{inN}` テンプレート、cmd /C raw_arg | |
| Type 別カード配色（フィルタ緑／コマンド シアン／ジェネレータ 琥珀） | |

### 1.2 核心 = exit code が制御フローを生む
- 今のフローは線形のデータ変換。**戻り値で分岐**が入った瞬間、キャンバスは
  **ビジュアルなシェル／Makefile／CI** になる。
- "お行儀のよい CLI" の条件（豊富なオプション＋意味のある exit code）は、そのまま
  **合成可能（composable）であるための条件**。ここを v1.5 で決め切る。
- 配線案（要設計）: フローエッジに「成功時のみ／失敗時のみ／常に」を持たせる。
  relations kind='flow' の属性 or 新 kind。色で可視化（成功=緑／失敗=赤の意味を再定義）。

### 1.3 設計の分岐点 = まず one-shot に絞る
- **採用: 一括（one-shot）＋ exit code 分岐**。実行して終わる→戻り値を読む型。
  pull 評価モデル（中間はメモリ、最終段だけ実身カード化）を壊さない。安全・低リスク。
- **後送り: 常駐・対話プロセス**（stdin ストリームで REPL を生かし続ける）。プロセスの
  ライフサイクル管理が要り、pull 評価と相性が悪い。ウィジェット（V2.0）の議論と合流。

### 1.35 時間制限と暴走停止（2026-06-18 ユーザー論点）
一般アプリ起動には「無制限」オプションが欲しい。が、ただ外すと暴走を止められなくなる。
**核心: 今の timeout は性質の違う2つを混同している**——フィルタ（有限で終わるべき変換）と
アプリ起動（終わらないのが正常）。「制限を外す」でなく**モード分割＋正しい制御**で解く。

> **原則: 「無制限」＝「自動で殺さない」であって「殺せない」ではない。PID／ハンドルを必ず
> 保持し Stop を常設する。危険なのは"タイマーが無い"ことでなく"ハンドルを失う"こと。**

- **モードA フィルタ（変換）**: 現状のハードタイムアウト（既定60秒 taskkill /T）。維持。
- **モードB 長時間バッチ**: 総時間でなく**アイドルタイムアウト**（「N秒 出力が無ければ停止」）。
  正常な長尺は出力し続け、ハングは黙る → これを watchdog に。
- **モードC アプリ起動（GUI/常駐）**: **detached 起動・同期で待たない**。PID 追跡のみ。
  起動カードに**「実行中」状態＋Stop**を常設。さらに**「実行中プロセス」一覧パネル**
  （Stop / Stop-all。カードが画面外でも中央のキルスイッチが残る＝暴走停止の本体）。
- **タイマー非依存の共通網（無制限でも効く）**: 出力 512MB 上限は timeout と独立に維持／
  TexoS 終了時の扱いを detached（GUIは生かす）/tracked（バッチはツリーkill）で分岐。
- **既存資産の転用**: `break_flow`＋AtomicBool＋taskkill /T はそのまま常設 Stop に使える。
- **実装案**: `timeout_secs` を三択に拡張 —— 正の秒数＝ハード／0 or 空＝アイドル監視／
  -1＝無制限（detached・Stop常設）。Type（フィルタ/コマンド/ジェネレータ）で既定を変える。

### 1.4 旧計画からの吸収
- 旧 v1.4.x 候補 `{stdin}`/`{stdout}` カード = パイプ端点の明示カード化 → この系列の一部。
- 旧 v1.4.x 候補 **プログラムのフィルタ化**（csv.c → コンパイル → csv.exe を処理ノード化）
  = 自己拡張ループ（v1.3.3 で gcc 実証済み）の延長 → プロセスコントロールの素直な応用。
- フィルタライブラリ強化（横断再利用）も同系列。ウィジェット（V2.0）への橋渡し。

### 1.5 戻り値（exit code）の定義（2026-06-18 確認）
- 「0=正常、非0=エラー」は MS-DOS → Windows → POSIX まで共通。ただし**値域が違う**:
  Windows = 32bit DWORD（負・`0xC0000005` 等 NTSTATUS 系もあり、**signal 慣習なし**）／
  POSIX = 下位 8bit（0–255）・シェル慣習 **128+N = signal N で終了**（130=Ctrl+C 等）。
  → **特定の非0値の意味は OS／プログラム固有で移植不可**。横断保証は「0 か、0 以外か」だけ。
- TexoS の契約（マルチプラットフォーム前提）:
  1. **既定の分岐 = success/failure の二択**（Rust `ExitStatus::success()` == exit 0）。緑=成功/赤=失敗。
  2. **生の exit code（`code()`: `Option<i32>`）を結果値として保持**し、上級者向けに特定値マッチ
     分岐を後から足せる（「値の意味はプラットフォーム依存」と UI に明記）。
  3. **3状態を区別**: 正常(0)／プログラムが報告したエラー(≠0)／**TexoS が打ち切り（timeout・中断の
     taskkill）・Unix の signal 終了（`code()`==None）**。3番目を「失敗」に混ぜない（既存 taskkill 経路と整合）。

## 2. ビジュアルコマンド（図形＝スコープ）

### 2.1 図形が証明したこと
図形はすでに**空間的包含**を実装済み: 図形クリック＝上のカードをまとめて選択、
図形ドラッグ＝上のカードごと移動、階層化（中心が乗る前面図形は親に従う）。
これは「ビジュアルにロジックが組める」ことの実証 —— **空間的配置がそのまま操作の対象集合**
を決めている。

### 2.2 統合の核 = 空間的 foreach
- 次の一歩: **含まれるカードへコマンドを実行**する。
- 統一の核:

  > **図形（スコープ）＋プロセスコントロールカード ＝ 「この領域のカード全部に
  > このプログラムをかける」**（空間的な foreach）。

- **空間的包含がループ／スコープというプログラム構造になる**。図形の境界がスコープ、
  内部のカード集合が反復対象。これが TexoS 固有の「ビジュアルにロジックを組む」の正体。
- 実装は地続き: 包含判定（実装済み）＋ `run_flow` の入力集合に「図形内のカード」を渡す。

### 2.3 ビジュアルコマンドの語彙（要設計）
何を「図形に対するコマンド」として出すか。スコープ creep を避け、まず既存機能の foreach 化から:
- **格子整列（図形に乗るカードを格子に並べ直す）= v1.4.x で先行実装**（2026-06-18 ユーザー提案）。
  ビジュアルコマンドの最小核＝「図形スコープ × 既存操作（整列）の foreach」。既存 `cardsOnShape`／
  `notesOnShape`（包含判定・実装済み）＋ `alignSelected("grid")` を選択非依存にして接続するだけ。
  整頓という"無害な操作"から入り、後で対象を「フィルタ／プロセスコントロール実行」へ広げる足がかり。
- 既存フィルタ／プロセスコントロールを**含まれる各カードへ適用**（最有力・基盤再利用）。
- まとめて実身化／持ち出し（既存バルク操作の空間版）。
- 将来: 集計（含まれるカード数・合計サイズ）、条件抽出（型でフィルタ）など。

## 5. 要求駆動への再定義（フロー制御の背骨・2026-06-27 ユーザー）

オートフローを使い込んだ結論: **TexoS はデータ駆動ではなく要求（リクエスト）駆動**。
下流のリクエストが上流へ伝搬し、最上流からデータが生成されて流れ戻る。フィルタの連続
パイプライン化を決めた時点で実は決まっていた性質で、`eval_filter`（lib.rs の再帰 pull
評価）が既にこれを実装している。

- **データは下流へ、リクエスト（pull）は上流へ。** 向きが逆の2レーン。
- **シンク＝リクエストの発生源**という再解釈で全体が一本化する:
  `wavPlayer（再生したい）→ text2wav（元テキストをくれ）→ AI（材料をくれ）→ 最上流の源`。
  `run_flow`（終端カードの pull）は既にこれ。トリガー（§7）はこの発火を自動化するだけ。
- 計算機科学的には後ろ向き連鎖（Prolog）／遅延評価（Haskell）／能動的推論の系譜。
  「必要な情報があるから問題が発生し、解決のために行動する」＝生物の欠乏駆動と同型。
- ⚠ この再定義は v2.0 の背骨。**自律構築（リクエスタ／アーキテクト／コンストラクタ）の
  安全設計は別ドキュメント `docs/要求駆動と自律安全設計.md` に分離**。本メモは
  非自律＝配管・起動・可視化に集中する。

## 6. ノード分類・色分け・ポート・Void・タップ（2026-06-27 ユーザー論点）

現在は全部 kind='filter'（type=filter|command|generator）＋ launcher。要求駆動グラフでは
**役割（ロール）**で整理すると配線と安全が綺麗に割れる。

### 6.1 ノードのロール分類
| ロール | 入出力 | 例 | 既存対応 |
|---|---|---|---|
| **源 source** | 入力なし→出力 | Mic2wav・Camera2pics・URLスクレイパ・フォルダ/コンテナエクスプローラ | generator型（Mic2wav 実装済み） |
| **変換 transform** | 入力→出力 | Whisper・pandoc化・AI変換・img系 | filter/command型（実装済み） |
| **作用 sink** | 入力→（副作用・出力なし） | wavPlayer・オペレータ起動・送信・削除 | **新設**。**作用クラス**を持つ（§7） |
| **起動 trigger** | （データグラフ外）pull を発火 | タイマ・各ウォッチャ | **新設**（§7） |
| **分岐 router** | 入力→成功/失敗/常時 で出力先選択 | リクエストスイッチャ | exit code 分岐（§1.5）の具体化 |

### 6.2 色分け
type 別配色（フィルタ緑／コマンド シアン／ジェネレータ 琥珀）を**ロール基準**へ拡張。
特に **sink は作用クラスで縁色を変える**（純粋/可逆=通常、不可逆=橙縁、外向き/拡散=赤縁）。
危険が一目で分かる＝安全の可視化（§7・別ドキュメント）と直結。

### 6.3 入力/出力ポート（必要な所だけ）
カード全体＝1ポートの現行モデルは単純で良い。**ポートが効くのは2箇所だけ**:
- **多入力の順序可視化**: `{inN}` は今「矢印を張った順」で不可視・脆い。入力ポートで
  番号を明示・固定する。
- **router の多出力**: 成功/失敗エッジ（§1.5）に出力ポートが要る。

→ 全カードをポート化するとUIが煩雑。**load-bearing な router 出力・多入力ノードから
段階導入**、単入出力は暗黙ポート（カード全体）のまま。

### 6.4 Void ノード（安全な仮置き）
2用途を1カードの2モードで:
- **スタブ（構築の仮置き）**: 未設定の placeholder。pull しても何もしない／素通し。
  破線・グレーで「未設定」を可視化。骨格を先に組み、後で実ノードに差し替える。
- **Void シンク（/dev/null）**: 出力を明示的に捨てる。**危険シンクを繋ぐ前の安全な既定**。
- 安全との接続: 「**Void の骨格は何も起きない＝安全**。人間が Void を実ノードに差し替える
  ＝武装」という構図になり、構築と安全弁が同じ操作で表現できる。

### 6.5 タップ＝中間データの可視化（直接連結だと様子が見えない問題）
現行 pull は中間をメモリで素通しし**最終結果だけカード化**（クリーンだが観測不能）。
解決は新機構を足さず**既存のデータカード／ドロップポイント（"drop:" 空入力）を
「エッジ上のタップ」に流用**:
- **覗き見（probe）**: エッジに空データカードを置く → その地点のペイロードを実行毎に
  実体化（デバッグ）。エッジ単位で on/off。構築アンカーも兼ねる。
- **蓄積（accumulate）**: タップに append モード → 定点観測の時系列が溜まる
  （フィジカル＋タイムストリームの種）。**予算（§7・前提⑤）でディスク膨張を抑える**。
- **実行ログ**: コード上の `FlowReport`（created/updated/outputs/skipped/errors）を
  pull ツリー全体のラン・レポートとして構造化表示（任意でカード化）。今はフィルタ memo に
  散在しているのを一元化。
- 設計原則: **既定はクリーン（メモリ素通し）、覗きたい所にカードを置く＝空間的 opt-in**。
  既存の「中間カードを作らない」モデルを壊さない。

→ 6.3〜6.5 は少数の primitive に収束する: ロール＋作用クラス色 ／ 必要箇所のみポート ／
Void（スタブ＋捨て） ／ エッジ上のデータカード（タップ＝覗き・蓄積・構築アンカー）。

## 7. 起動系トリガーと安全弁（非自律部分・2026-06-27）

トリガーが入るとアプリが初めて「黙って自律的に動く」。配管・起動レベルの安全弁を先に固める
（自律構築 R／A／C の安全は `docs/要求駆動と自律安全設計.md`）。

- **トリガー＝run_flow の自動発火ラッパ**。スケジュール／監視 ＋ 対象終端ID を持つだけで
  データグラフの外側。タイマ→定点観測、ファイル／フォルダ／データ／コンテナ ウォッチャ→変化検知。
- **作用クラスで段階化（核心）**: 純粋/追記=自動許可 ／ 不可逆ローカル=可逆へ降格（削除→trash・
  上書き→新版）／ 外向き=武装 or 人間確認・既定禁止 ／ 拡散（閾値超ファンアウト）=ハード停止。
- **可逆性の濠**: 実身/仮身＋CAS＋ソフトデリート＋trash で**ほとんどの操作が既に可逆**。
  自律は「可逆・可視・追記のみ」の領域に閉じ、その境界に人間ゲートを置く。
- **capability 層で判定**: 危険ラベルは実際の delete/send/exec を握る層が付ける。
  **ノード設定やAIの自己申告を信じない**。
- **武装/解除** ＋ リソース起動ノードの per-node「自動発火許可」フラグ。
- **ヒューズ（前提⑤）**: 1実行あたりの外向き行為数・触ファイル数・反復・並行プロセス上限。
  既存の 512MB／アイドル監視が種。
- **中央 kill（前提③）**: 実行中プロセス一覧＋Stop-all（カードが画面外でも残る）。
  `break_flow`＋AtomicBool＋taskkill /T を常設 Stop に転用。
- **人間工学の罠**: ゲート過多は自己武装解除を招く。**自動許可を広く、ゲートする集合を
  「本当に不可逆／外向き」だけ小さく**保つ。
- 段階: §3 の段階導入「5. タイマー／ドロップ受け入れ」を、ここで「トリガー＋作用クラス
  安全弁」として具体化（exit code 分岐 §1.5 と router §6.1 が前提）。
