# カード統一モデル検討結果（付箋廃止・論理グループ・プロトコル指向）

検討日: 2026-06-12 / `docs/V2.0課題.md` §0 の 1〜3 に対するユーザー決定とその具体化。

> **改訂（2026-07-01・ユーザー決定＝§1 付箋の統一移行は保留し実務優先）**: 使い込みの結果、付箋は
> 「マップの案内役／プログラムのコメント」という独立した役割で重宝している（大きい文字＝見出し・注釈で
> 全体の案内になる）。テキスト実体が欲しい時は既存の「内容でテキストカードを作成」で足りる。したがって
> **§1 の付箋→カード統一移行は当面おこなわない**。方向転換＝**付箋のまま役割を充実させる**:
> ①独自の色付け ②文字サイズ選択肢の拡張 ③**タイトルと本文でフォントサイズを分ける**、など。
> もし将来どうしても統一する場合でも、付箋は **「定数化カード」＝実体を持たない読み出し専用のシステム
> テキスト**（no real body・CAS に載せない不変テキスト）として置き、フロー矢印に意味を持たせて
> 「テキストの読み出しだけ」を担わせる形に限定する（＝現在の text カードや実身とは別カテゴリの“定数”）。
> §2 論理グループ・§3 プロトコル原則は本改訂の影響を受けない。

## 決定の要旨

1. **付箋（notes テーブル）は廃止し、カードの派生に置き換える**。
   根幹（virtual_bodies）は完全共通化し、ビューのみを変える（オブジェクト指向の原則）。
   別テーブルはアジャイル式プロトタイプの負の遺産と位置づける。図形も必要になれば同方式。
2. **論理グループを導入する**。図形グループ（空間的・視覚的）はパイプライン処理に向かない
   ため、論理的な所属関係を持つグループを別に設ける。これによりサブプロジェクトの
   必要性はさらに下がる。
3. **プロトコル指向・マルチプラットフォーム見据えの設計を原則として明文化**。
   構造はシンプルであるほど移植しやすい。

統一後の TexoS プロトコルは3概念に収束する:

| 概念 | 実体 | 説明 |
|---|---|---|
| **実身** | real_bodies | バイト列＋MIME（CAS、不変） |
| **仮身** | virtual_bodies | kind 付きの出現（カード。すべての見た目はビューの差） |
| **関係** | relations | kind 付きエッジ（link / flow / group / sequence …） |

付箋・図形・グループ・フィルタ・タイマーはすべてこの上の「変種」であり、新テーブルを作らない。

## 1. カード統一（付箋のカード派生化）

### kind 列の導入

- `virtual_bodies.kind TEXT` を追加（best-effort ALTER の前例どおり）。
  値: `file | text | note | url | project | folder | filter | timer`（将来 `shape | group`）
- 既存 DB はプロジェクトを開いた時に ref 列（url_ref / project_ref / folder_ref …）から
  推定して埋める（`repair_mime_types` の前例）。以後、変種判定は kind を正とする
- v1.4 オートフローのフィルタカードは最初から kind='filter' で作る（タイミングが合う）

### 付箋の移行設計

- **notes.id（UUID）を vid としてそのまま virtual_bodies へ移す** —
  ユーザー指摘の「識別子で判断できれば置き換えやすい」の実装。
  **relations の from_id/to_id は無変更で生き残る**（v1.3.1 で入った
  「relations の端点が notes.id か vid か」の例外コードがすべて消える）
- real_id は `note:sentinel`（`url:sentinel` の前例）。本文は専用列（`text` 相当）に保持
  （CAS に載せない: 付箋はインライン高頻度編集でハッシュ churn が無意味。
  ファイル化したい時は既存の text カード化＝コミットで合流）
- width / font_size / bold → スタイル JSON 列（将来の変種共通のスタイル置き場）
- file_ref（テキストファイル連携）は機能ごと移設
- ソフトデリート列・trash 整合も引き継ぐ
- **NoteCard.tsx はビューとして存続**（kind='note' のレンダラ）。UI・操作感は変えない

### 移行の安全策（2026-06-12 簡略化決定）

- 運用開始3日でデータが僅少のため、**移行ツールは作り込まない**。
  プロジェクトを開いた時の単純な一括変換のみ。変換に乗らない旧データは
  手動削除、または後続の正規化ツールでの強制削除も許容（ユーザー決定）
- それでも **変換前の texos.db バックアップ**（`.texos/backup/` へコピー）だけは行う
  （コストほぼゼロのため）
- UNDO スタック（meta.ui_undo_stack）の旧 note 系オペは再生不能になるため、
  **移行時にスタックをクリア**
- 正規化ツール（メンテナンスリリース）は**付箋移行の後に**作成する（順序確定）

### 図形の扱い

- 当面 **shapes テーブル維持**。論理グループ（§2）導入後、図形は「純粋な視覚注釈」に
  役割が戻るため、別テーブルのままでも矛盾しない（ユーザー判断「必要であれば同じでもよい」）
- 統一する場合は kind='shape' で付箋と同じ手順（id 維持・スタイルJSON）。V2.0 で再判断

### 効果

- App.tsx の notes 特別扱い（noteSizes・自動レイアウト障害物・矩形選択・削除時の
  relations 掃除…）が一本化される。**次セッション②の App.tsx リファクタリングを
  先に済ませておくと移行が楽**（useSelection 等の分離と相性が良い）
- サブプロジェクト移動・クロスリンク・flow 入力・Ctrl+C 持ち出しの全機能が
  「カードだけ」を相手にすればよくなる（V2.0課題 §0-2 の懸念が解消）

## 2. 論理グループ（グループのカード化）

### 方式の決定

ユーザー提示の2案「カードにグループID」「カードに所属カードへのリンク」のうち、
後者を形式化した **「グループ自体をカードにする」方式を採用**:

- グループカード = kind='group' の仮身（real_id は `group:sentinel`）
- 所属 = relations **kind='group'**（スキーマ予約済み）のエッジ: グループカード → メンバー
- group_id 列方式を採らない理由: 1所属限定・入れ子不可・グループ自体を操作対象にできない

### この方式が買うもの

- **グループが一級オブジェクト**になる: flow 矢印をグループカードに繋げば
  **メンバー一括のパイプライン処理**（今回の動機そのもの）。
  オートフロー設計のフェーズ2に「グループカード＝バッチ入力」として追記
- 複数所属・入れ子（グループのグループ）が relations の自然な性質として手に入る
- 移動・削除・持ち出し等の既存カード操作がグループカードにそのまま適用できる

### 図形グループとの棲み分け（確定）

- **図形 = 空間的・視覚的**（上に乗ったカードをまとめて動かす・選ぶ。論理なし。現状維持）
- **論理グループ = グループカード + kind='group' エッジ**（パイプライン・集合処理の対象）
- 橋渡し: 「図形上のカードを論理グループ化」コマンド（図形→グループカードへの昇格）。
  ウルトラC（図形グループ）を論理グループの入口として活かす

### サブプロジェクトとの関係

- 論理グループで「集合化・まとめ処理・整理」は足りる。サブプロジェクトの残存価値は
  **フォルダ写像（持ち出し・配布の単位）と別キャンバス**のみ
- ユーザーの読み（OS依存が減ればサブプロジェクトすら不要になりうる）と整合。
  先送り決定（`docs/サブプロジェクト検討結果.md` 冒頭）をさらに裏付ける
- 将来案: グループカードのダブルクリック＝メンバーだけを表示する**フォーカスビュー**。
  「根幹共通・ビューのみ変える」原則の応用で、別キャンバスの必要性もほぼ消える

## 3. プロトコル指向・マルチプラットフォーム（設計原則）

- **構造の単純化を最優先の設計原則として明文化**: 新機能はまず
  「実身・仮身（kind）・関係（kind）」の3概念で表現できないかを検討し、
  新テーブル・新概念の追加は最後の手段とする
- **Win32 依存の隔離**: os_icon・drag_drop（受け）・クリップボード持ち出し（v1.4.x）・
  OLE ドラッグアウト（将来）を1つのモジュール境界（例: `src-tauri/src/win/`）に集約。
  他コードは OS 非依存のインターフェースだけを見る
- **データ配置はプロジェクト自己完結（.texos 内）を優先**（メンテ課題3はこの方向で決定。
  アプリ設定のみ OS 作法の場所）
