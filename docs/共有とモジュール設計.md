## 0. 結論（先に要点）

1. **共有には直交する2レーンがある**: **データレーン（中身の共有）** と **フローレーン（構造の共有）**。
   別物として設計する。混ぜると必ず食い違う。
2. **フローモジュール＝名前付きの再利用可能な部分グラフ**。これは1つの概念で、その別の顔が
   **図形スコープ（境界）／ライブラリ（保存）／跨プロジェクト共有（移送）／制御フロー（中の実行）**。
   ＝**まとめて co-design する**。バラバラに作らない。
3. **これにより積み残しが正常化される**:
   - **多プロジェクトへのエクスポート（アイデアメモ0626 ②）は独立機能としては不要化** →
     「データ共有（origin 仮身）」＋「フローモジュール共有」へ分解吸収。
   - **プロジェクト正規化（`normalize_project`）はほぼ不要化** → 後方互換を踏襲してきたので
     大移行は要らない。**GC（孤児 CAS 掃除）程度**に縮退。

## 1. 2つのレーン

| | **データレーン（中身の共有）** | **フローレーン（構造の共有）** |
|---|---|---|
| 共有する対象 | ファイルの**中身**（実身＝CAS のブロブ・実ファイル） | **部分グラフ**（カード＋矢印＋filter_ref の spec） |
| 性質 | 重い・内容アドレス（SHA-256）・不変・1個の実体 | 軽い・参照とパラメータの束・パラメトリック |
| 既存の仕組み | 実身/仮身、`window_of`（内部レーン）、`origin_path`（外部レーン）、CAS、プロジェクト=フォルダ、コミット | `filter_ref` の spec、`filter_library.json`／`launcher_library.json`（**単一カードのみ**）、フォーク継承（プロジェクト全構造のコピー） |
| 跨プロジェクト | `origin` 仮身（外部レーンの再利用）＝「向こうに窓を置き、実体は元に残す」 | **まだ無い**（＝今回の発見・要設計） |
| 不変条件 | 「同一プロジェクト内に同じ実体を2つの実身として登録しない」（v1.3.9 根幹原則） | モジュールは**実体を持たず**、実行時に各プロジェクトで**依存を解決**する |

**要点**: 今のライブラリは「**1枚のカード**」しか共有できない。ユーザーの言う「出来上がった
フローモジュールのライブラリ化」は **複数カード＋矢印の塊＝部分グラフを一個の部品として** 保存・
再配置・共有することで、これは現状に**無い**。データの共有（origin 仮身）とは別レーン。

## 2. フローモジュール ＝ 名前付きの再利用可能な部分グラフ

### 2.1 同じものの4つの顔
- **図形スコープ（ビジュアルコマンド）** = モジュールの **境界**（空間的包含が「どのカードが
  このモジュールに属すか」を決める）。
- **ライブラリ化** = モジュールの **保存**（部分グラフに名前を付けてアプリ共通に置く）。
- **跨プロジェクト共有** = モジュールの **移送**（別プロジェクト／別 PC へ運ぶ）。
- **制御フロー（分岐・ループ）** = モジュールの **中の実行**と**境界をまたぐ流れ**。

→ この4つを別々のデータモデルで作ると破綻する。**「部分グラフ＝モジュール」という1つの表現**を
先に決め、4つの顔をそこから導く。

### 2.2 モジュールが満たすべき性質（オートフロー設計への制約）
1. **自己記述**: モジュールは自分の **入力／出力／依存（必要なプログラム・フィルタ）** を宣言する。
   別 PC・別プロジェクトで **所在解決**（`.texos\filters → PATH`、モジュールカタログ）できる。
   ＝ ffmpeg/whisper のような外部依存を「未導入なら案内」できる土台（1.4.6 Ollama 案内と同型）。
2. **パラメトリック**: 同じモジュールを違う入力で実体化できる（ドロップポイント＝入口、
   prefix/連番＝出口の命名、デバイス名や閾値などの差し替え）。
3. **合成可能（composable）**: モジュールの中にモジュール（ネスト）。図形スコープの入れ子が
   そのままモジュールの入れ子になる。`docs/オートメーション設計メモ.md §1.2`「合成可能であるための
   条件＝豊富なオプション＋意味のある exit code」と地続き。

### 2.3 データモデルの方向性（実装は v1.5・ここでは“塞がない”ことだけ決める）
- **モジュール = {境界（どのカード群）, 内部の relations, 宣言された IN/OUT ポート, 依存リスト,
  パラメータ}** を1つの JSON にシリアライズできる形にする。
- 既存の **フォーク（`fork_structure_into`：CAS 再帰コピー＋ATTACH で全構造コピー）** は
  「プロジェクト丸ごとの複製」だが、モジュールは「**部分グラフ＋（データは持たず参照）**」。
  フォークの“構造コピー”ロジックは**部分グラフ版に一般化**できる（再利用候補）。
- **図形（shapes）が境界の第一候補**。`cardsOnShape`/`notesOnShape`（包含判定・実装済み）が
  「モジュールに属すカード集合」を与える。図形にモジュール属性を持たせる案。

## 3. 積み残しの正常化（このメモの実利）

### 3.1 多プロジェクトへのエクスポート（アイデアメモ0626 ②）→ 独立機能としては不要化
- 当初案: 「選択カードを他プロジェクトへ送る＝すべて origin 仮身で配置」（Pick Up/Drop の代替）。
- **再整理**: これは2つの操作に分解できる。
  - **データを向こうで使いたい** → **データレーンの跨プロジェクト共有＝origin 仮身**（既存の外部
    レーンをそのまま使う。実体は元に残り、向こうは窓）。これは「エクスポート」という新機能でなく
    **既存の origin 仮身を跨プロジェクトに開くだけ**。
  - **処理（フロー）を向こうでも使いたい** → **フローモジュールの共有**（§2）。データではなく構造。
- 結論: **「エクスポート」という独立カテゴリは要らない**。`v1.4.0_計画.md §4` の「プロジェクト間
  データ共有」は **データレーン側（origin 仮身の跨プロジェクト化）** に一本化し、フロー側は
  モジュール共有として別建てにする。Pic Up/Drop On（OLE）は従来どおり V2.0。

### 3.2 プロジェクト正規化（`normalize_project`）→ GC 程度に縮退
- 当初設計（`V1.3.9_閲覧と安全策設計.md ③`）: 「最新へ確定→履歴を手放す→孤児回収」を順番厳守で
  行う**元に戻せない**大型コマンド（リフレッシュ→ゴミ箱空→UNDO 切詰め→孤児 CAS 掃き）。
- **再整理（2026-06-26 ユーザー）**: 開発を通じて **データの後方互換が一貫して踏襲**され、列追加も
  「開き直しでマイグレーション」で吸収できてきた＝**大移行（リフレッシュ・履歴手放し）は実運用上不要**。
  実害があるのは**孤児（到達不能な CAS ブロブ・trash 残骸）が溜まること**だけ。
- 結論: **`normalize_project` は GC に縮退**。
  - 残すべき最小機能 = **孤児 CAS／不要キャッシュの掃除**（到達可能性＝生存カード／UNDO スタック／
    trash／フォークチェーンを生存扱い。誤ると「復活の呪文」が壊れるので**安全側**で）。dry-run 付き。
  - 捨ててよい = 「全リフレッシュ」「履歴手放し」「大物実体化のオプトイン」等の重い手順
    （後方互換が効いている前提では過剰）。
  - 付随: **CAS／サムネキャッシュの役割整理**（`v1.4.0_計画 §3.2`・ユーザー「混乱している」）は
    この GC 設計と一緒にやると筋が良い（何が生存で何が孤児かを定義する作業＝同じ）。

## 4. リファクタリングへの含意（v1.4.10・新機能なしで“塞がない”形に）

このメモから、リファクタリングが**満たすべき制約**が出る（＝単純化で拡張を閉ざさない指針）:

1. **flow 実行モデルの統一は「1ノード実行」だけでなく「部分グラフ実行」を見据える**。
   現状の `eval_filter`（再帰 pull）は単一終端からの評価。モジュール（境界つき部分グラフ）／
   制御フロー（分岐）を将来載せるため、**「実行単位＝ノード」「実行文脈＝グラフ／スコープ」**を
   分離した形に整える。`build_cmdline`/`run_external_cwd`/`run_ai`/shell/generator/record の
   分散ディスパッチを **「ノード種別 → 実行 → 結果（payload＋exit code＋stderr）」** の一本道へ。
2. **`FilterSpec` のノード種別を体系化**（今は ~25 項目が暗黙に同居）。種別＝
   {内蔵フィルタ / 外部コマンド / ジェネレータ / AI / shell / launcher / record …}。
   将来の **exit code 分岐・モジュール境界・依存宣言・パラメータ** を載せられる余地を残す
   （いきなり破壊的に作り替えない。serde 後方互換を維持しつつ、アクセサ／判別を整理）。
3. **relations（矢印）に制御属性の余地**: `kind='flow'` に「成功時/失敗時/常に」を将来持たせる
   （`オートメーション設計メモ §1.2`）。今回はモデルを汚さず、**拡張点として意識**しておく。
4. **共有の2レーンを混ぜない**: データ（実身/仮身/origin/CAS）とフロー（spec/部分グラフ）の
   コードパスを概念的に分ける。ライブラリ機構を「単一カード」から「部分グラフ」へ一般化する
   余地を残す（`filter_library`/`launcher_library` の延長線）。
5. **正規化は GC として小さく**（§3.2）。重い `normalize_project` を作らない方針を計画へ反映。
6. **ドキュメント整備**: 陳腐化した「AI/MCP=V2.0」「エクスポート②」「重い正規化」を本メモの
   再整理に合わせて更新（`v1.4.0_計画.md`・`バージョンアップ計画.md`・`NEXT_SESSION.md`）。

## 7. ショートカット検討から派生した具体的操作仕様（2026-06-28・副産物）

起票の経緯: v1.4.12 のショートカット整理（`F:\yoshi\Documents\TexoSMain\ショートカット整理.txt` ＋
Help オーバーレイの検討）を進める中で、抽象的だった「2レーンの跨プロジェクト共有」に対する
**具体的なユーザー操作（クリップボード semantics・ライブラリ化UI）**が落ちてきた。本節はそれを
§1〜§6 の地図に接続して記録する（**実装は v1.5系**。ここでは操作仕様の確定として残す）。

### 7.1 Ctrl+C / Ctrl+V の再定義 ＝ データレーンの跨プロジェクト仮身（§3.1 の具体UI）
現状 `Ctrl+C` は「OS へ実体をエクスポート（HDROP）」に割り当て。これを**仮身コピーへ振り替え**、
OS エクスポートは右クリックの「**実体をクリップボードにコピー**」へ移設する。

- **OSエクスポート（移設先）**: 右クリック特別「クリップボードにコピー」→「**実体をクリップボードに
  コピー**」に改名。**仮身は実身化せず**、指し示す実体を辿って HDROP に格納。**赤シグナル（窓喪失）の
  仮身は CAS から復元して実身化してから**実体をコピー。実身はそのまま実体をコピー。**複数選択対応**。
- **Ctrl+C ＝ 仮身としてコピー**（`Ctrl+D`／`Ctrl+左ドラッグ`＝化身 と同じ「仮身を作る」系の一員）。
  - 実身を Ctrl+C → その実身を指す仮身を作る情報をクリップボードへ。
  - 仮身を Ctrl+C → 同じ実身（窓の先）を指す仮身。
- **Ctrl+V ＝ その場に仮身を貼り付け**。**別プロジェクトに切り替えてから Ctrl+V するとプロジェクトを
  超えて仮身が貼り付く**＝元の仮身が指す実身を指す仮身になる（外部フォルダでも別プロジェクトでも
  「実身を指す」が保たれる）。**複数選択も同様**。
- **混合（仮身/実身混在）**でもそれぞれの対応で実施。**複数選択時は関係矢印も維持**。ただし
  **プロジェクト境界をまたぐ矢印はつながない**（→ §6 の「データレーンとフローレーンが交差する点」
  および「プロジェクト間通信・データ共有・実身仮身の関係」を要検討の論点として残す）。
- → **これで「プロジェクト間コピー」が完成**する。§3.1 で「origin 仮身を跨プロジェクトに開くだけ」と
  書いた抽象を、`Ctrl+C/V` という具体操作に落としたもの。**内部レーン（window_of）の跨プロジェクト版**
  が必要になる（指し先カードIDがプロジェクトをまたぐ＝解決規則の拡張。§6 の未決項目）。

### 7.2 選択フローのライブラリ化 ＝ フローレーンの部分グラフ化（§2 の具体UI）
「**選択された複数カードの状態をライブラリ化**」することで、**コピーとライブラリ化を同じ素材で実現**する
（部分グラフ＝モジュールの保存＝§2.1「ライブラリ化＝モジュールの保存」の顔）。

- **選択時の右クリック「名前を付けて実身をライブラリ化する」**: 部分グラフ（カード＋矢印＋spec）に
  加え、**実身をどこかに保持**する必要がある（**プロジェクト内に置くのが良い**）。
  ＝ §6 最終論点「モジュールが内部で実身を生む＝その実体はどちらの所有か」への**一案＝ライブラリ化時に
  実身をプロジェクト内に保持し、モジュールはそれを参照**（データレーンとフローレーンの交差をここで確定）。
- **未選択・キャンバスの右クリック「ライブラリから貼り付け」**: 実身付きの**一連の接続されたフロー**を
  まるごと配置。**プロジェクト外（プロジェクト未オープン）では貼り付け不可**。回避策＝元プロジェクトで
  一度貼り付け→選択 `Ctrl+C`→コピー先プロジェクトで `Ctrl+V`（＝ 7.1 の跨プロジェクト仮身に乗る）。
- **`Ctrl+B` ＝ 実身化して貼り付け**（任意提案）: 貼り付けと同時にデータも実体化する版。
  ＝ モジュール展開時に「参照のまま」か「実体化」かを選べる出口。

### 7.3 §6 オープン論点への反映
本節の操作仕様は、§6 の未決項目のいくつかに**具体的な答えの方向**を与える:
- 「データ origin 仮身の跨プロジェクト版」→ **7.1 の Ctrl+C/V**（内部 window_of の跨プロジェクト解決が要）。
- 「モジュールが内部で実身を生む＝実体の所有」→ **7.2 のライブラリ化時にプロジェクト内へ実身保持**。
- 「フローレーンとデータレーンが交差する点」→ **ライブラリ＝部分グラフ＋同梱実身**という形で交差を定義。
- 新規の未決項目: **プロジェクト境界をまたぐ関係矢印は張らない**方針の是非（プロジェクト間通信の設計へ）。

## 8. T1 決着 — モジュール境界（2026-07-05 ディスカッション合意）

前提: モジュール＝名前付きの再利用可能な部分グラフ（§2）。T1 で決めたのは「どのカードが
モジュールに属すか」の決め方。`オペレーション層設計.md §5.4`（ノードカード確定・IN 側改修＝
relations.attrs）の決着を受けた続き。オペ層 §3 の制約（受容体/要求体が取り付く前提）を満たす。

### 8.1 境界 = 図形＋ロック（ハイブリッド）

- 通常は従来どおり**中心点包含で動的**（`cardsOnShape` の判定を踏襲。自由に出し入れ）。
- 図形メニューに「**メンバーをロック**」トグルを追加。ロック中は:
  **ドラッグアウト不可**／**ドラッグインは警告付きで可**／図形に**ロック表示**。
- **ライブラリ化はロックを前提とするスナップショット**（保存の瞬間にメンバー集合が固定される）。
  編集の自由（動的包含）と部品の安定（固定）をロックの ON/OFF で切り替える。

**追補（2026-07-08 v1.5.6 実機確認での決着）— メンバーシップは所属であって幾何ではない**:
- 図形の動的包含は「ゆるいグループ」概念であり、それを根拠にロックすると図形のリサイズや
  Shift 移動（図形のみ動かす）でメンバーが外れてしまう（ユーザー指摘）。
- **ロック＝その瞬間に乗っていたカード id のスナップショットを図形が持つ**（shapes.members・
  JSON 配列）。以後の保護（アウト不可・削除不可）は id 照合＝図形をどう変形しても守られる。
- **図形にメンバーを持たせる**（カードに所属を持たせる案は不採用）: §8.2 多重所属が自然
  （複数の図形のリストに同じ id が入るだけ）／解除・図形削除でメンバーシップも消える＝
  宙ぶらりんが構造的に出ない／図形=モジュール=シリアライズの単位（§10）と器が一致する。
- ドラッグインは警告付きで可＝**所属にも追加**。万一メンバーが図形の見た目の外に出ても
  （リサイズ等）、図形右クリック「**メンバーを選択**」で id から回収できる。
- ロック解除＝所属を消してゆるいグループへ戻る。再ロック＝新しいスナップショット。

### 8.2 非階層・多重所属

- **図形に親子関係は持たせない**。重なり＝**所属関係の表現**であり、1枚のカードが
  **2つ以上の図形（モジュール）に所属できる**。
- モジュールのメンバー集合＝「中心がその図形内にあるカード」。他図形への所属とは独立に取る。

### 8.3 ロック × 多重所属の規則 = 仮身分裂

- **両方ロック済み**の図形 A・B の重なりに所属するカード X があり、B がドラッグされて A を
  離れるとき: **X は仮身化して B と共に外へ出る**。A に残る X は実身/仮身のまま**不変**。
  B と共に出た X は**同じ実身を指す仮身**。＝両方のロック（メンバー保全）を、データレーンの
  原則（窓）で同時に満たす。（「図形を引き延ばして回避」の旧案は撤回・2026-07-05）
- 片方のみロックの場合は分裂しない: A のみロック→X は A に残る（B が手放す）。
  B のみロック→X は B と共に移動（A から普通に抜ける）。
- **内部矢印の追従（形式化・Fable 導出）**: 分裂時、B 内部の関係矢印（相手も B メンバー）は
  複製仮身側へ付け替え、A 内部の矢印は元に残る。両図形の外への矢印は元に残す（保守的既定）。
  ＝各モジュールの内部グラフが分裂後も完結する。
- ロック図形**自体**の移動はメンバーごと一緒（従来のグループ移動）。ロック図形を**縮めて**
  メンバーがこぼれる操作は警告。

### 8.4 独立性判定と移送形態（T2 の種）

- **独立モジュール**（境界をまたぐ flow 矢印なし＝関係が内部で閉じている）→
  **実身化して移動が可能・ライブラリ化（実身同梱）可能**。
- **非独立**（またぐ矢印あり）→ またぎ点に **IN/OUT バーチャルカード**（ドロップポイントの
  一般化）を接続して**仮身化でコピー**。ライブラリ化も仮身ベース。
  **元プロジェクトに穴を開けない**（実身化して移動は現在許可しているが、モジュール移送では
  仮身が既定）。
- **ポート＝境界をまたぐ矢印の実体化**。宣言は強制しない（またぎがそのまま IN/OUT になる）。
  §7.2「ライブラリ化時に実身をプロジェクト内へ保持」と同方向の確定。

### 8.5 v1.5 の実行意味論 = 透過（インライン展開）

- ライブラリから貼り付け＝**配置ごとインライン展開**。展開後のカードは他のカードと
  **完全に同等**（フロー制御・オペ層の対象になる）。
- 現在でも「まとめて仮身コピー」＋「実身化して移動」でほぼ同等が実現しており、モジュールは
  **それにライブラリ化・命名・コンテナとしての図形との連携を与えるもの**、という位置づけ。
- 畳み込み表示・「畳んだ塊に▶」・モジュールエディタ（全体像把握の仕組み）は**次段階（V2.0系）**。
- **誤解防止**: 畳み込み＝最適化コンパイルの類ではない。**カードそれぞれの属性とフロー矢印を
  まとめて扱えるだけ**（ユーザー明言・2026-07-05）。

### 8.6 モジュール属性の置き場

- v1.5 は**図形 spec の拡張**（名前・ロックフラグ・依存リスト等を図形に持たせる）。
  kind='module' のセンチネル実身カードは**作らない**——畳み込み表示を導入するとき（V2.0）に再検討。

### 8.7 残タスク（T2/T3 へ）

- **T2**: IN/OUT バーチャルカードの具体 → **§9 で決着（2026-07-05）**。
- **T3**: シリアライズ JSON の形（メンバー・relations・配置・spec・依存リスト。
  実身の同梱/参照の条件は 8.4 で確定済み。フォーク構造コピー `fork_structure_into` の
  部分グラフ版への一般化が実装候補）。

## 9. T2 決着 — IN/OUT バーチャルカード（2026-07-05 ディスカッション合意）

### 9.1 生成タイミング = 「必要な時に生まれる」が原則

- **自動生成**: フローの一部を選択して**モジュール化コマンド**を使ったとき、境界をまたぐ
  矢印のまたぎ点に IN/OUT を自動付与（§8.4 の実体化はこれ）。
- **手動設置**（意図的な宣言）: ①フロー全体を最初から組むとき「先に入口・出口を置いて中を組む」
  ②図形に乗って閉じている（独立な）モジュールに、意図的に IN/OUT を付けたいとき。
- **モジュール化の範囲は3水準**: フロー矢印のつながり（連結成分）全体／図形に乗っているもの／
  図形にロックされているもの。

### 9.2 貼り付け後の振る舞い = 残す・自動削除しない・「溶解」で消す

- 展開された IN/OUT バーチャルカードは**残る**（貼り付け直後はそこへ矢印を繋ぐ。インライン
  展開なので以後は自由に編集できる。差し替え可能な口として働く）。
- 右クリック「**このカードを溶解**」を用意: 繋がれているフロー矢印を**繋ぎ先へ繋ぎ変えて**
  カードが消える（足場を畳む明示操作。IN/OUT どちらにも適用）。

### 9.3 OUT バーチャルカード = 実行トリガー（受容体の最小形）

- OUT カードに ▶（実行）を付け、押すと**さかのぼって pull 実行**され、
  **結果のカードが横に生まれる**。OUT カード自身は**消えずに残る**（何度でも押せる口）。
- 役割は**実行系のトリガーのみ**に限定（それ以外の機能は持たせない）。
- コスト判断: ▶ ボタンの実装が高くつくなら、v1.5 最小は「溶解」のみでも可（▶ は望ましい）。
- 将来: ここに req 矢印（kind='req'）を差せば `オペレーション層設計.md §5.4.1` の受容体
  そのものになり、「畳んだ塊に▶」（V2.0）の前身となる。

### 9.4 データモデル（形式化・Fable 導出・T3 と同時に検証）

- IN/OUT バーチャルカードは **kind='op' の一種（op:"in" / op:"out"）** を提案。
  付箋統一のセンチネル実身パターン・トリガ/タイマ/ウォッチャ（オペ層 §5.4.1 グループB）と
  同じ器に乗せ、新 kind を増やさない。OUT の ▶ ＝「設置型トリガが終端に接続された形」と
  意味論が一致する。異議があれば T3 の確定時に見直す。

## 10. T3 決着 — シリアライズと配布（2026-07-05 ディスカッション合意）

### 10.1 ライブラリは個人のもの（AppData）・配布はプロジェクトで

- **filter_library と同じ流儀**: モジュールライブラリ＝アプリ共通（%APPDATA%）＝**個人の道具箱**。
  ライブラリは配布経路ではない。
- **配布＝キャンバスに展開した状態でプロジェクト（TexoS フォルダ zip）を渡す**。受け取り側が
  右クリック「ライブラリに登録」で自分の道具箱へ。SampleProject.zip 配布構想にそのまま接続。
- 利点として明記: **ライブラリが勝手に他人に渡らない**（プロジェクトにライブラリは付いていかない）。
- 新コマンド「**プロジェクトに、すべての個人フィルタとモジュールを書き出し**」＝バックアップの代用。
- 保存形式（Fable 導出）: **モジュール1個＝1フォルダ**（module.json＋blobs/実身コピー）。
  単一 JSON への base64 埋め込みはしない（巨大データ対応・zip 化が容易・filter_library とは別建て）。

### 10.2 実身は常にコピー同梱（**§8.4 の上書き**・2026-07-05 T3 討議）

- **ライブラリ化は常に実身のコピーを同梱する**。持っておかないと動かなくなるため（埋め込みの
  動画・音声・画像も許容。画像生成・AI エンジンの入力も想定内）。元プロジェクトは不変＝
  穴も開かず、元プロジェクトの移動・削除にも強い。
- §8.4 の「非独立＝ライブラリ化も仮身ベース」は**廃止**。仮身ベースの共有は §7.1 の
  Ctrl+C/V（プロジェクト間の直接移送）の役割として整理。ライブラリからの貼り付けは
  §7.2 どおり**実身付きで配置**（blobs を対象プロジェクトの CAS へ materialize）。
  独立/非独立の区別は「実身化して移動」の可否（§8.4）と IN/OUT 自動付与の有無にのみ効く。
- **巨大データ警告**: ライブラリ化時に合計サイズがしきい値を超えたら警告（ユーザー発案・採用。
  しきい値は実装時に決定＝例 100MB・実測調整）。基本はテキスト指示書などの軽データを期待。

### 10.3 依存の扱い = 自動収集＋初回アテンション＋配布文書の定型文

- 依存（外部プログラム name/path・AI エンドポイント・ollama モデル・builtin 種別）は
  **spec から自動収集**して module.json に記録。手動の依存スキーマ欄は設けない。
- 新環境での初回実行時、未導入の依存があれば**アテンション**（1.4.6 Ollama 案内・
  「環境を構築する」ボタンと同じ流儀。インストールが走るカードは特に）。
- 配布文書の定型文を用意: 「このモジュールは外部プログラムを使用します。初回起動時に
  インストールを求められます」。

### 10.4 パラメトリックは「開いて自己編集」＋コメント文化

- **貼り付け時のパラメータダイアログは作らない**（そこまで親切でなくてよい・透過展開と整合）。
  配布は TexoS フォルダ zip → 開いてから自己編集。
- **配布元がパラメータ編集ガイドを文書として同梱**し、キャンバス上に
  「このカードを環境に合わせて編集してください」等の**コメント（付箋）を添えて配布する文化**を
  推奨（`docs/ユーザーズチップス.md` 化の候補）。
- 注意: 付箋に矢印をつけると入力（プロンプト定数・v1.4.17）になるため、**案内コメントは
  矢印なしで置く**。
