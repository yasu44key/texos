## 1. 収穫 — 当初の野望がコードに貫かれている

v1.5.10 を実コードで点検した結論: **基盤（実身/仮身/関係 ＋ SQLite ＋ CAS）はOS非依存で、
OS依存は外殻にのみ隔離されている。** 2026-06-12 の「Win32依存を1モジュール境界に隔離／
データはプロジェクト自己完結」方針が、決定文どおりに守られていることを確認した。
**これが今後の基盤となる確証が、最大の収穫。**

| 層 | OS依存 | 実ファイル | 状態 |
|---|---|---|---|
| 基盤（3概念プロトコル） | **ゼロ** | `db.rs` `objects.rs` `cas.rs` `modules.rs` | SQLite+CASのみ |
| フローエンジン | プロセス起動/kill のみ | `flow.rs`（`cmd /C`↔`sh -c`、`taskkill`↔`child.kill`） | 両分岐とも実装済み |
| 外殻（OS統合） | Windows実装＋各OS分岐 | `os_integration.rs`（win/mac/linux 全分岐実装済） | ○ |
| 外殻（劣化フォールバック） | Windows実装＋null | `os_icon.rs`（非Win→`None`） | 優雅に劣化 |
| Windows専用モジュール | 丸ごと `#[cfg(windows)]` | `clipboard_out.rs` `drag_drop.rs` | 他OSでは非コンパイル |
| フロントエンド | **ゼロ** | `src/**` | platform分岐・ハードコードパス無し |

補足:
- 依存クレートに移植障壁なし（`rusqlite` bundled・`reqwest` rustls-tls・`image`・`zip`・
  `arboard`・`dirs`・`chrono` 等はすべてクロスプラットフォーム）。
- `windows`/`windows-core` は `[target.'cfg(windows)']` ゲート下で、他OSではコンパイル対象外。
- Windows専用モジュールの呼び出し側（`clipboard_in.rs:67`・`objects.rs:2178` 等）は
  既に `#[cfg(windows)]`/`#[cfg(not(windows))]` ペアでゲート済み。穴は少ない見込み。
- **確定に必要な唯一の作業**: 実機で一度 `cargo build` を通し、無条件参照の穴を洗い出す
  （WSL2/VM で低コストに実証可能）。

## 2. OSティア分け（現実的な射程）

Tauriの都合ではなく、TexoSの核（外部プログラムをフィルタとして繋ぐ ＋ 自由なファイルシステム）が
各OS制約とどう噛むかで決まる。

- **Linux / macOS（デスクトップ）** ◎ — 同一アーキ。recompile＋外殻の穴埋め。**本命。**
  Mac配布時はコード署名/notarization。
- **iOS / Android** △ — Tauri 2 はmobileターゲット対応（`#[cfg_attr(mobile, …)]` 等が既にコードにある）。
  だが iOS は任意プロセス起動禁止＋強いFSサンドボックスで、**オートフローの柱が動かせない**。
  → `.texos` の**閲覧/編集クライアント**（キャンバス・3概念閲覧・付箋編集・HTTP経由のAIカード）
  としてなら有意義。フル機能は不可。移植問題ではなく製品判断。
- **Webブラウザ** ✗（現アーキ） — ローカルファイル＋ローカルプロセス＋ローカルSQLiteが存在意義。
  純ブラウザ(WASM)版はその3つを失う。実現するなら「TexoSデーモン ＋ ブラウザクライアント」の
  **クライアント/サーバ分割の別アーキ**。フィルタ実行はサーバ側。V2.0射程外の大構想として名前だけ確保。

## 3. パス可搬性 — 絶対パスのトークン化（本ドキュメントの主題）

### 問題 — ただし「根絶」ではなく「分離」（2026-07-10 作者補足で訂正）

DB内で外部を指すパスが**ホスト絶対パス**で保存されている。特に Windows の
「ドキュメント」「デスクトップ」等は**OS言語でフォルダ実名が変わるエイリアス**であり、
ユーザ名・OS・言語をまたぐと即座に壊れる。単一OSでも**配布・持ち出しで破綻する**（トリガーB）。

**しかし絶対パスの全廃は誤り。** ドライブ間をまたいで外部データを参照する仮身（＝プロジェクト外の
別ドライブのファイルへの「窓」）は**正当な第一級機能**であり、そこでは絶対パスが本質的に必要。
むしろ**絶対パスがここに残っているのは、この正当な用途があるから**とも読める。したがって狙いは
「絶対パスの根絶」ではなく、**トークン化できるものはトークン化し、真に外部の絶対参照は残したまま
OS抽象の境界へ分離する**こと。消してはいけない — 分ける。

### 現状のパス保持列（`virtual_bodies`）

| 列 | レーン | 内容 | 現状 |
|---|---|---|---|
| `committed_path` | 内部 | プロジェクト内の実ファイル | **要監査**: 取り込み時 `path` をそのまま保存。プロジェクト基準の相対化は未確認（絶対の可能性） |
| `origin_path` | 外部 | 借用元（informational only・凍結） | 絶対パス。§5 の「借用元フォルダで表示」の記録元 |
| `folder_ref` | 外部 | フォルダカードが指す先 | 取り込み時 `path` をそのまま保存＝絶対 |
| `project_ref` | 外部/内部 | 他 `.texos` プロジェクト参照 | 内包=相対化可能／外部リンク=絶対 |
| `url_ref` | — | URL（file://以外はFS非依存） | 対象外（file:// のみ注意） |

### 設計方針: `%変数%` トークン方式

**DBには常にトークン形で保存し、読み出し時に実行機で展開する。** ホスト絶対パスを
load-bearing データとして DB に固定しない（＝水泡に帰さない設計の、OS境界への適用）。

**コード内に既に前例がある**: `filters.rs:283` が Start Menu 走査で `%ProgramData%` /
`%APPDATA%` 展開を使用済み。同じ発想を参照パス全体へ一般化する。

想定トークン（展開は `dirs` クレートで per-OS 解決）:

| トークン | 展開元 | 解決する問題 |
|---|---|---|
| `%PROJECT%/…` | プロジェクトルート | 内部レーンの相対化（移動・配布で不変） |
| `%HOME%/…` | `dirs::home_dir` | ユーザ名差・OS差 |
| `%DOCUMENTS%/…` | `dirs::document_dir` | **ローカライズされた「ドキュメント」実名差** |
| `%DESKTOP%` `%DOWNLOADS%` 等 | `dirs::*_dir` | 同上、必要に応じ追加 |
| （どの既知ルート外）生の絶対パス | — | best-effort・凍結。展開不能なら窓喪失表示 |

原則:
1. **保存はトークン形のみ**。展開したホストパスをDBに書き戻さない。
2. **取り込み時に最長既知プレフィックス一致でトークン化**（例: Documents配下 → `%DOCUMENTS%/rel`）。
3. **内部レーン（`committed_path`）は `%PROJECT%` 相対**に統一（要監査項目の是正）。
4. **展開不能・不在は既存の「窓喪失（薄赤）」表示に合流**（§5 の追跡しない方針・仮身喪失表示と整合）。

### 正当な絶対パス — 消さずに分離する（作者補足 2026-07-10）

`%変数%` トークン化は「既知ルート配下」に効く。だが**別ドライブ・任意の外部場所を指す仮身**は
トークン化できず、絶対パスのまま保持するのが正しい。ここで問題になるのは保存形式ではなく、
**「参照先が生きているか」の判定と喪失時の赤シグナル表示が、OSに非常に強く依存する**こと:

- ドライブのマウント/アンマウント・ドライブレター（`D:\`）↔ マウントポイント（`/mnt/…`）の差
- ネットワークパス（UNC `\\host\share`）・リムーバブル・クラウド同期フォルダの扱い
- 存在確認・アクセス権・シンボリックリンク解決の挙動差

**これが絶対パスコードが外殻に残っている本当の理由**であり、`os_icon.rs` などと同じ「OS方言」枠。
よって外部絶対参照は**専用のOS抽象境界（リゾルバ＋生存プローブ）に隔離**する:

- 保存: 真に外部の絶対参照は絶対パスのまま（トークン化しない）。ただし**種別タグ**を付ける
  （`local-abs` / `unc` / `removable` など）ので、リゾルバがOSごとに正しく解決・判定できる。
- 判定: `path_liveness(ref) -> Live | Missing | Unknown` を**OSごとに実装**（Win/mac/linux 分岐、
  `os_integration.rs` と同じ構造）。同期I/Oでブロックしないよう非同期プローブが前提。
- 表示: `Missing` は既存の「窓喪失（薄赤）」へ、`Unknown`（未マウント等・後で復活しうる）は
  区別できると親切（薄赤より弱い「保留」表示の余地）。**赤シグナルは明示必須** — 静かに失敗させない。

→ 内部レーンの相対化（`%PROJECT%`）／既知ルートのトークン化（`%DOCUMENTS%` 等）／
真の外部絶対参照のOS抽象リゾルバ、の**3系統に分離**するのが本設計の核。

### アプリ自身のデータ位置（`%APPDATA%` 相当）— 既に per-OS 抽象済み（作者補足 2026-07-10）

「アプリが自分のデータ/設定/キャッシュをどこに置くか」は各OSで全く違う。だが**ここは§3の
仮身の参照パスとは別軸**で、**TexoS は既に正しく抽象化できている**:

- app_data 根は `app.path().app_data_dir()`（`lib.rs:629`）で解決＝Tauri が per-OS 変換:

  | OS | app_data_dir（`identifier = com.yoshi.texos`） |
  |---|---|
  | Windows | `%APPDATA%\com.yoshi.texos`（Roaming） |
  | macOS | `~/Library/Application Support/com.yoshi.texos` |
  | Linux | `$XDG_DATA_HOME/com.yoshi.texos`（無ければ `~/.local/share/com.yoshi.texos`）＝XDG準拠 |

- ローカルキャッシュ系は `dirs::data_local_dir()`（`runtime/ollama.rs:33`）＝これも per-OS 抽象。
- `runtime/python.rs` は既に「**パスはすべて app_data 起点・OS分岐は runtime/ 内に閉じ込め・
  外部コマンド名は定数化**」と可搬性方針を先取り明記。→ **設計としては正しい方向に既にある。**

つまり**「%APPDATA% を各OSぶん自前で持つ」必要はない** — Tauri/`dirs` が肩代わりする。
Linux も XDG は crate 実装済みで、フル自前ではない。残る作業は下記の3点のみ:

1. **doc/コメントのWindows方言の是正**: `python.rs` の `app_data = %APPDATA%\com.yoshi.texos\` の
   ような**コメント表記**は Windows 前提。コードは可搬（app_data起点）だが、文言は per-OS 中立に直す。
2. **macOS の勘違い注意（ユーザ想定への補正）**: データはアプリ（`.app`）フォルダ**内には置かない**。
   `.app` はコード署名済みで**読み取り専用**扱い、内部に書くのは不可。macOS の作法は
   `~/Library/Application Support/<id>`（＝Tauri が返す場所）。**「アプリフォルダ内に持つ」は不可**。
3. **OS固有ロケーションを走査する機能は外殻扱い**: `list_installed_apps`（`filters.rs:293`）は
   `%ProgramData%`/`%APPDATA%` の Start Menu を走査＝**Windows専用**。Start Menu は mac/linux に
   無いので、mac は `/Applications`、linux は `.desktop`（`/usr/share/applications`＋
   `~/.local/share/applications`）を見る別実装が要る。これは `os_icon.rs` 等と同じ OS方言（外殻）層。

### 先行実装（v1.8.3・2026-08-26）— 「カレント＝プロジェクト」の規約だけ先に入れた

トークンリゾルバ本体（`%DOCUMENTS%` 等）はまだだが、**内部レーンの相対化に相当する
規約**は先に動くようにした。きっかけはウォッチャの監視パスが「フルパス必須」で、
手打ちが苦痛だったこと（作者フィードバック）。

- `util.rs :: resolve_project_path(root, s)` を1箇所に置いた。規約は3つだけ:
  **空欄＝プロジェクトフォルダ／相対＝プロジェクト基準／絶対＝そのまま**。
  絶対パスは潰さない（別ドライブ参照は正当な第一級機能・§3 の「消してはいけない — 分ける」）。
- 適用先: ウォッチャの監視パス（`ops.rs`）・外部プログラムの出力先 `out_dir`・
  記録（tap）の出力先・「新規カードを登録」の対象フォルダ（`flow_run.rs`）。
  従来これらの相対パスは**プロセスの CWD 基準**で、事実上壊れていた。
- 保存はユーザが書いた形のまま（解決結果を書き戻さない）＝**ホスト絶対パスを DB に
  焼き込まない**。設定ダイアログの「参照…」でプロジェクト配下を選ぶと、UI 側で
  相対パスへ畳んでから保存する（`relativizeToProject`・バックエンドと対の規約）。
- ウォッチャの既定が「プロジェクトフォルダ」になったので、`preflight.rs` の自己発火検査も
  **解決してから**比べるようにした（でないと「空欄 vs ルート」が別物に見えて警告が黙って
  消える）。あわせて、その実行が実際に直下へ書くときだけ警告するよう精度を上げた
  （ウォッチャ＋「新規カードを登録」の対は何も書かない＝発振しないので黙る）。

→ トークン化に着手するときは、`%PROJECT%/…` をこの関数の入口で受けるだけで済むはず
（相対パスは実質 `%PROJECT%` 相対の別表記）。移行対象は「この規約より前に絶対パスで
書かれた既存カード」だけになる。

## 4. あなた（作者）の関与方針

- **基盤＋Windows参照実装は作者が持ち続ける。** 比較優位は設計・プロトコル・思想であって、
  OSごとの外殻方言埋め（クリップボード/D&D/アイコン/起動）ではない。
- **綺麗なモジュール境界こそ「他OS開発者に任せる」を可能にする資産。** 隔離を決めた戦略的
  ペイオフをここで回収する。OS統合を「ここを各OSで実装せよ」という文書化された契約面として明示する。
- **公開時期**（V2.0課題 §0.6）: ①使い倒す→②知人→③評判次第でOSS。契約面に対しOSごとの貢献者を募る。
- **近い将来の低コスト検証**: 作者が WSL2/VM で一度 `cargo build` を通し、コンパイルゲートの穴だけ潰す。
  フル移植を抱えずに「移植可能」を実証できる。

## 5. 割り切りの枠組み

- **データ層＝普遍（アプリが保証・絶対に妥協しない）**: `.texos`（`texos.db` + `cas/` +
  `snapshots/`）はバイト単位で可搬。SQLite・内容アドレスCASはOS非依存。**規律＝§3のパス3系統分離**
  （内部＝相対／既知ルート＝トークン／外部絶対＝種別タグ付きで保持）。プロジェクト自己完結な部分が
  可搬なら、Windows で作ったプロジェクトは Mac/Linux で同一に開く。
- **機能層＝OS方言（開発者が埋める・無くても動く）**: 外殻機能は per-OS で優雅に劣化。
  `os_icon.rs` の「非Win→None」パターンを全外殻点に一般化し、部分移植のOSでも起動して動く状態を保つ。
  **外部絶対参照の生存判定・赤シグナルもこの層**（ドライブ/UNC/マウントはOS依存が強い）。
  データ層で「参照を持つこと」は保証し、機能層で「その参照が今生きているか」をOSごとに埋める分担。

→ 一言で: **データ層は普遍、機能層はOS方言。** これは「OSSに乗る／全部自前で持たない」思想を
OS境界に適用したもの。当初の「各OS上に思考ツールOSを敷く」野望と同じ方向を向いている。

## 6. 追補 — 可搬性はパスだけではない（2026-07-10 リーチ拡張）

§1〜§5 は「コードの移植」と「パスの可搬性」を扱った。だが実コードを再点検すると、
可搬性の敵はあと4方面ある。**特に 6.1 と 6.2 は「.texos データは普遍」という §5 の
主張に対する残った例外**であり、トリガーB（配布）で §3 と同時に顕在化する。

### 6.1 フィルタCMD文字列 — データの中に棲むOS方言（最大の盲点）

`FilterSpec.cmd`（`flow.rs:14`）は**ユーザデータ**としてフィルタカード／モジュールに保存される。
実行器は `cmd /C` ↔ `sh -c` で切り替わる（§1）が、**文字列の中身は翻訳されない**:
`dir`↔`ls`・`type`↔`cat`・`%VAR%`↔`$VAR`・`.exe` 拡張子・パス区切り・引用符規則、全部が方言。

つまり **`.texos` フォルダがバイト単位で可搬でも、「そのプロジェクトのフィルタが動く」ことは
可搬でない**。SampleProject.zip 配布（同梱バイナリ＝per-OS資産）はこの問題の直撃を受ける。

対策の方向（実装は配布と同じ波で）:
- **モジュール／フィルタに対象OS宣言**（`os: ["windows"]` 等）を持たせ、非対応OSでは
  §3 の窓喪失と同系の**赤／保留表示**にする（静かに失敗させない原則の適用）。
  v1.5.10 で module.json にコメントを含めた前例があり、欄の追加は低コスト。
- **builtin フィルタ（ai / t2i 等）はOS非依存**なので、配布物は builtin 優先で組むと可搬性が上がる。
- 将来: 同一モジュールの**OS別コマンド変種**（`cmd_win` / `cmd_unix`）。翻訳器を作るのは過剰、
  変種を併記できれば十分（「全部自前で持たない」思想と整合）。

### 6.2 ファイル名・文字規約 — `.texos` データ可搬性の残る敵

CAS はハッシュ名なので**免疫**。危ないのは人間が命名する**コミット済み実ファイル**とフォルダ:

- **Unicode 正規化（日本語ユーザ直撃）**: macOS のファイルAPIは NFD（濁点・半濁点を分解）で
  名前を返すことがある。「プロジェクト.md」の「ジ」「ェ」が別バイト列になり、
  `WHERE committed_path = ?1` の**文字列一致が Mac で静かに外れる**。対策＝取り込み・照合の
  入口1箇所で **NFC 正規化**を通す。
- **大文字小文字**: Win/mac 既定は非区別、Linux は区別。v1.3.11 #10 で `path_inside` を
  堅牢化した前例があるとおり方向は意識済みだが、Linux では**逆向きの罠**（`A.md` と `a.md` が共存）になる。
- **Windows 禁止文字・予約名・MAX_PATH**: Linux/mac で作れる `a:b?.txt` や `CON.md` は
  Windows で開けない。**朗報: 逆方向はほぼ安全**（Windows が最も厳しい規則なので、
  現在の Windows 産データは他OSでそのまま通る）。将来 mac/linux 版が生むデータのために、
  コミット時のファイル名サニタイズを**最厳格＝Windows規則で統一**しておくのが安い保険。

### 6.3 `kill_tree` の Unix 側潜在バグ — 移植初日に踏む

`flow.rs:971` の非Windows分岐は `child.kill()` のみ。これは **`sh` だけを殺して孫プロセスを
残す** — Windows 側コメント自身が「cmd だけが死に実体の孫プロセスが残る」と説明している
**まさに同じ問題**の Unix 版。定石は `setsid`（プロセスグループ化）＋ `killpg`。

放置すると、暴走プログラムの強制終了（`MAX_OUTPUT_BYTES` 上限・中断ボタン）という
**自律安全設計の安全装置が他OSで実質無効**になる。トリガーAの初回ビルド時に最優先で直す1点。

### 6.4 runtime 自動導入（「アプリが面倒を見る」思想）の per-OS マトリクス

Ollama流の自動導入は現状 Windows 前提。**他OS対応の実作業の過半はおそらくここ**:

| runtime | 現状 | mac | linux |
|---|---|---|---|
| Ollama | `winget` 前提（`ollama.rs:92`） | brew / 公式dmg | curl インストーラ |
| whisper.cpp | **Windowsバイナリzip固定**（Cargo.toml注記） | 公式バイナリ無し→要ソースビルド or 別配布 | 同左 |
| uv/Python | `UV_EXE_NAME` は **cfg分岐済み**（`python.rs:35-37`・良い前例） | tar.gz展開＋`chmod +x` | 同左 |
| GPU加速 | DirectML/CUDA 系 | **Metal**（別レーン） | CUDA/ROCm |

- **macOS 固有の罠**: ダウンロードした実行バイナリには quarantine 属性（Gatekeeper）が付き
  **実行拒否される**。xattr 除去 or 署名の手当てが必須（知らないと導入が全部無言で失敗する）。
- `python.rs` の「OS分岐は runtime/ 内に閉じ込め・コマンド名は定数化」方針が正解。
  全 runtime をこの流儀に揃えるのが移植作業の実体。

### 6.5 WebView・UI の暗黙差 — 「フロントエンドOS依存ゼロ」への注記

§1 の「ゼロ」は**コード**の話。実行エンジンは WebView2(Chromium) / WKWebView(Safari) /
WebKitGTK と**三者三様**で、日本語IME挙動・フォント（Yu Gothic→Hiragino/Noto）・
Ctrl↔Cmd ショートカット・Linux の Wayland/X11 差（クリップボード・D&D）が表面化する。
設計変更は不要、「初回実機起動で洗い出す」で足りる。フォントスタックのCSS手当てだけは先行可能。

### 6.6 検証インフラ — Mac を買わずに検証する

§4 の「WSL2 で低コスト検証」の**上位互換**: GitHub Actions のマトリクスビルド
（windows / ubuntu / **macos** ランナー）で `cargo build`＋テストを回せば、**Mac実機を
持たずに macOS のコンパイルが通る**。リポジトリは push 済みなので今すぐ仕込め、
トリガーAを実質前倒しできる。配布形式（msi ↔ dmg+notarization ↔ AppImage/deb）は
OSS化（③）時の課題として名前だけ確保。

### 6.7 Docker — 「アプリの配布」には不向き、「フィルタ実行系」には有望（作者アイデア 2026-07-10）

機種依存を取り除いた配布版としての Docker 案。**適用面を分けると評価が反転する**:

**✗ TexoS本体（GUIアプリ）のコンテナ配布は不向き**
- ネイティブ WebView が使えず、GUI は X11/Wayland 転送頼み。Win/mac では Docker 自体が
  VM（WSL2/仮想化）前提で、**「軽量クロスプラットフォーム配布」の理念と正面衝突**する。
  本体は Tauri ネイティブ配布（msi/dmg/AppImage）が正解のまま。

**◎ フィルタ実行系のコンテナ化は、§6 の問題を3つ同時に解く**
- **6.1 CMD方言が消える**: コンテナの中は常に Linux。`sh -c` 一本になり、モジュールの
  コマンドが全OSで同一に動く。OS宣言欄も「container なら不要」になる。
- **6.4 runtime導入マトリクスが消える**: whisper/t2i/Python をイメージにピン留めすれば、
  per-OSダウンロード・quarantine・chmod の全てがイメージ側の責務になる（Ollamaが実質この思想）。
- **サンドボックスが手に入る**: 要求駆動の自律安全設計・OSS化時のフィルタ配布の安全性
  （V2.0課題 §0.6）に、隔離実行がそのまま効く。
- **§3 との綺麗な接続**: `%PROJECT%` トークンはコンテナのマウントポイント（`-v project:/work`）に
  そのまま写像できる。トークン化設計がコンテナ実行の前提整備を兼ねる。

**留保（正直な難点）**
- Docker Desktop は Win/mac で重い前提条件（インストール・常駐・ライセンスは個人無料）。
  **既定はネイティブ実行のまま、コンテナは opt-in の実行バックエンド**とする（軽量理念を守る）。
- **GPU**: Linux/WSL2 の NVIDIA はコンテナから使えるが、**mac の Metal はコンテナから使えない**
  → Mac で t2i をコンテナ実行すると CPU オンリー。加速が要る builtin はネイティブレーン維持。
- 位置づけ: フィルタ実行の**第3のバックエンド**（①ネイティブコマンド ②builtin ③container）。
  §2 の「TexoSデーモン＋ブラウザクライアント」大構想とも地続き（実行系の分離という同じ方向）。
