## 1. 目的（2026-10-30 ユーザー）

AnythingLLM（ローカル AI で PC のほぼ全部を扱えるデスクトップアプリ）を入れてみて、少し悔しかった。
TexoS でも同じようなことをやってみたい。

棚卸しすると、看板機能の多くは TexoS がすでに持っていた（§2）。**負けているのは機能の量ではなく入り口**。

- いまの「声で頼むとカードが並ぶ」（v1.12）は、音声カード・役割の付箋・コンストラクタを**自分で並べてつなぐ**必要がある。
  慣れた人でないと、それができることに気づかないし、組めない。
- → **エージェントカードを1枚ポンと置けば話せる**ようにする。カードの中から、コンストラクタ・実行・検索・タイマを
  呼び出してくっつけていく。**入り口を1つにする**（ユーザー案・2026-10-30 合意）。

TexoS らしさ（AnythingLLM との違い）:

- AnythingLLM はチャットの一往復で処理が消える。**TexoS ではエージェントが組んだフローが枠の中に残る**
  （再実行・手直し・持ち出しができる資産になる）。チャットは入り口、成果はキャンバス。

## 2. 棚卸し（2026-10-30 コードと docs で確認）

AnythingLLM の看板 → TexoS の手持ち:

- Web 検索・スクレイピング → web_search（SearXNG・v1.9.0）・web_fetch / feed / capture（v1.7）。**ある**

- 外部の AI から操作 → MCP 接続（v1.11）。**ある**（AnythingLLM のサイトには記載なし）
- 会議の書き起こし・音声 → 音声カード（v1.10）・マイク録音 / Whisper（v1.12）。**部品はある**

## 3. 決定事項（2026-10-30）

1. **入り口は1枚のエージェントカード**。音声カードやコンストラクタを人がつなぐ必要をなくす。
2. **今の音声カード・コンストラクタは残す**（慣れた人が自分で組む部品）。エージェントカードの中身は

## 4. エージェントカード（`builtin:"agent"`・🤖 エージェント）

### 4.1 形

```
 ┌──────────── 🤖 エージェント ────────────┐
 │ 会話（直近の数往復）                      │
 │ ……                                       │
 │ [ ここに入力 ……………… ] 🎙 ▶             │
 └──────────────────────────────────────────┘
        │ 会話ログ.md（実身・AI カードの履歴と同じ流儀）
        └─ 来歴の矢印 ─▶ ［枠: 🏗 組んだフロー］ ─▶ 結果
```

- メニューの**いちばん上**に「🤖 エージェントを置く」。空のプロジェクトの案内にも出す（気づけることが本題）。
- 入力はカード上の欄、または 🎙（音声サーバーを流用・押して話す）。返事は欄に出し、設定で読み上げ。
- 設定画面は AI カードと同じ `AiSettingsDialog`（`variant="agent"`）。モデルの入れ替えを他のカードと同じ使い勝手に。

### 4.2 1ターンの流れ（AI に道具を選ばせる）

AI には毎回「次の一手」を決まった形の JSON で返させる（Ollama `format` / OpenAI 互換 `json_schema`。
`tools` 能力のあるモデルなら tool calling も可。v1.12 で JSON 形式の実績あり）:

- `answer` — そのまま答える（雑談・質問。**何も作らない**）
- `search` — RAG 検索（§5）／Web 検索
- `build` — コンストラクタに設計図を作らせて並べる（construct.rs の流用・既存カードへの接続も込み）
- `run` — 組んだフローを実行する（§4.3 の作用クラスで止める）
- `read` — 実行結果の出力を読む（③の結果要約と同じ切り出し）
- `schedule` — タイマを**停止状態で**置いてフローにつなぐ（§6）
- `ask` — 人に確認する（欄に質問を出して待つ）

ループ: 一手 → 結果を会話に足す → 次の一手 … `answer` で終わり。**上限 `max_steps`（既定 8）**＝ヒューズ。
中断はカードの ■ と既存の中央停止。

### 4.3 動かしてよい範囲（作用クラス・`要求駆動と自律安全設計.md` §3 / §6）

- 判定は**並べたカードの種類で Rust 側が決める**。AI の自己申告は信じない（同 §6-1）。
- **自動で実行してよい**（純粋・追記）: AI・テキスト系 builtin・記録・RAG 検索・付箋・実身の新規作成。
- **人の ▶ を待つ**（武装）: 外部プログラム（`program`）・シェル・PC 上の既存ファイルに触るもの・タイマの稼働開始。
  待つときは枠に「▶ を押すと実行します」を出し、会話にも理由を書く。
- **Web 読み取り（web_fetch / search）**は外向きだが読むだけ → 未決（§8-2）。
- 実行は1ターンにつき1枠まで。消すのは UNDO（v1.12 と同じまとめ積み）。

### 4.4 v1.12 からの差分（作るもの）

- `agent.rs`（新規）: ループ・道具の振り分け・作用クラス判定・会話ログ。
- construct.rs: 設計図を作る部分を関数として外から呼べるように（いまは ▶ 構築の一括処理）。
- flow_run: 「この枠のフローを実行して出力を返す」入口（`run_flow_with_prompt` の延長）。
- フロント: エージェントカードの面（会話表示と入力欄）。カードの上で会話できるのは初。
- 音声: 🎙 は voice_server の文字起こしだけを使う（振り分け役は通さない＝エージェントが自分で判断する）。

## 5. RAG カード（`builtin:"rag_index"` と `builtin:"rag_search"`）

### 5.1 形

```
 [フォルダ / ファイル群] ─▶ [📚 索引] ─▶ 索引.ragidx（実身）
 [問い] ─▶ [🔎 検索] ◀─ 索引.ragidx ─▶ 抜粋.md（出典つき） ─▶ [AI カード]
```

- **索引**: テキストを切り分け（日本語は段落と句点で・既定 500 字・重なり 80 字）→ 埋め込みモデルでベクトル化 → 保存。
  対象は txt / md / pdf（テキスト抽出）/ docx。**CAS のハッシュで差分だけ**作り直す（TexoS の強み）。
- **検索**: 問いをベクトル化 → 上位 k 件（既定 6）を出典（ファイル名・位置）つきの Markdown で出す。
  AI カードにつなげばそのまま「資料つきの質問」になる。エージェントの `search` も同じ関数を呼ぶ。

### 5.2 中身の選び方

- 埋め込み = Ollama `/api/embed`（OpenAI 互換 `/v1/embeddings` も）。候補は日本語に強い `bge-m3`、軽い `nomic-embed-text`。
  能力検出の `embedding` でモデル一覧を絞る（既存の仕組み）。
- 保存 = **SQLite（rusqlite は導入済み）にベクトルを BLOB で入れ、総当たりのコサイン類似度**。数万チャンクまでは十分速く、
  依存が増えない。足りなくなったら sqlite-vec へ（そのときに）。
- ~~実身にするのは索引ファイル1つ（`.ragidx`＝SQLite）。~~ → 実装では `.texos/rag/<名前>.sqlite` に置き、
  カードの出力は**索引レポート（Markdown）**にした（毎回数十 MB の実身が CAS に積もるのを避ける・§5.3）。

### 5.3 実装メモ（2026-10-30・未コミット・実機未確認）

- `src-tauri/src/rag.rs`（新規）: 切り分け `chunk_text`・埋め込み `Embedder`（Ollama `/api/embed`／OpenAI 互換
  `/embeddings`・16件ずつ・素の OS スレッドで）・差分の作り直し `update_index`（文書ごとに sha256・文書ごとに commit
  ＝中断しても済んだ分は残る・モデルか切り分けの長さが変わったら全部）・総当たり検索 `search_index`。
- 索引レポートの1行目 `<!-- texos-rag-index: 名前 -->` が「どの索引か」の印。検索カードは入力のうち印のあるものを
  索引の指定、それ以外を問いとして読む。→ **索引カード → 検索カード ← 問い**とつなぐと、検索の前に差分の
  索引更新が走る。
- 実行は `flow_run.rs eval_filter` の tap の手前（集めた入力をまとめて渡す＝ファンアウトしない）。
  検索で0件（索引が空）は no-data。

### 5.4 PDF と Word（2026-10-30 ユーザー依頼）

- 既定の拡張子に `pdf` `docx` を足した（`txt,md,markdown,csv,log,pdf,docx`）。既存の索引は作り直さず、
  次の実行で PDF・Word の分だけ新規として入る。
- docx = 既存の zip クレートで `word/document.xml` を開き、`<w:t>` を拾う（段落・改行＝改行、タブ＝タブ、
  実体参照を戻す）。表のセルも段落なので「キー 機能 Shift+A …」の並びで入る。
- PDF = **pdf-extract 0.12（MIT）**を追加。壊れた PDF の panic は `catch_unwind` で受ける。
  文字が10字未満＝スキャン画像だけの PDF は「OCR が要ります」を索引レポートの注意に出して飛ばす。
  行番号は取り出した本文の行（ページ番号ではない）。
- 索引カードの受け入れ型を `*/*` に（PDF・Word のカードもつなげる。文書でない入力は注意に出して読まない）。
- 実測: Word 2本（Blender ショートカット集 2899 字・リギング手順 204 字）正しく取れた。
  日本語 PDF 3本（アドオンのマニュアル）は pdftotext とほぼ同じ量が取れた（MeshTools 9786 字・0.6 秒など）。
  画像だけの PDF 2本は正しく「文字がない」。Word＋PDF＋画像 PDF を混ぜたフォルダ → 文書3・98 チャンク・
  「複製のショートカット」→ Word の表の「Shift+D／Alt+D オブジェクトの複製」が2位（0.57）／
  「ボクセルリメッシュの細かさ」→ Voxel マニュアル PDF が上位3つ。
- 残り: スキャン PDF の OCR・pptx / xlsx・PDF のページ番号での出典。

## 6. スケジュール（既存タイマの接続）

タイマ op はもうある。足りないのは「エージェントやコンストラクタから置けない」こと:

- コンストラクタの受け付ける `call` に `timer` を足す。**必ず停止状態で置く**（v1.5.5 の流儀）。稼働は人の ▶ ＝武装。
- エージェントの `schedule` は「毎朝 7 時にこれをやって」→ フローを組む＋停止状態のタイマをつなぐ＋「▶ 稼働開始で動きます」。
- 曜日指定（`days`）を足すかは使ってから決める。TexoS が起動しているときだけ動く点は注意書きに出す。

## 7. 進め方（案）

1. **P1 RAG カード**（v1.13.0）— 単体で役に立ち、結果が決まっていて確かめやすい。エージェントの道具にもなる。
2. **P2 エージェントカード**（v1.13.1〜）— 本丸。まず `answer` / `build` / `run` / `read` の4手から。
   次に `search`・`ask`。閉ループがローカルモデルで実用品質に回るかは研究課題（同 §8）なので、
   実機で刻む。
3. **P3 スケジュール接続** — `timer` call と `schedule` の一手。小さい。

P2 を先にする手もある（核から触りたい場合）。そのときは RAG の代わりに Web 検索を道具にして始める。
