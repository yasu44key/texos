キャンバスから他アプリへのドラッグアウト、およびキャンバス内の他カードへのドロップ。

> **2026-06-12 更新**: サブプロジェクト検討の結果、本項目は**先行実装に昇格**。
> 方針は `docs/サブプロジェクト検討結果.md` §7（エクスポート＝コミット原則で
> TEMP孤児問題を解消。クリップボード持ち出し→OLEドラッグアウトの順）。

  実身は既存の「フォルダで表示」。そこから先のドラッグは Windows 任せ。

- **本実装する場合**:
  - OLE ドラッグソース（`DoDragDrop` + `IDataObject` の CF_HDROP 実装）が必要
  - 通常ドラッグはカード移動に割り当て済みのため、長押しドラッグ等の操作設計が必要
  - 渡すパスは「コミット済みなら実ファイル、仮身なら一時実体化したコピー」
  - 10（カードへのドロップ）はアプリ内で完結するので、ピックアップ状態（持ち上げ→
    別カードへ落とす）の UI を作れば OLE は不要。リンク作成 or 添付の意味論を要設計

## 6. プロジェクト間のデータ移動・共有ワークフロー（2026-06-19 追加）

ユーザーが「忘れていた」V2.0級の課題。**プロジェクト間の関係性を精査し、データの行き来と
ワークフロー連携を本実装する**。論理グループ（`カード統一モデル検討結果.md` §2）が一部を
肩代わりするが、フォルダ写像（配布単位）と別キャンバスを持つ"プロジェクト間"の連携は別課題。
設計の土台は `docs/サブプロジェクト検討結果.md` §3〜§5（移動・削除・クロスリンク）。

### 現状（できること）の棚卸し
- **フォーク（分岐）**: 兄弟プロジェクトを全構造継承で複製（CAS再帰コピー＋テーブル一括コピー、
  すべて仮身にリセット）。`fork_structure_into` / `create_subproject` 分岐モード。
- **内包（サブプロジェクト作成）**: 現 root のサブフォルダに子プロジェクト。`create_subproject` 内包モード。
- **既存プロジェクトへのリンク**: `link_project`（他の .texos を project_ref カードとして配置）。
- **行き来（ナビゲーション）**: `open_project_object`（project_ref を開いて current を切替）。
- → **データ"そのもの"を境界をまたいで移動・共有する手段はまだ無い**（フォーク＝全複製、
  リンク/行き来＝参照・切替であって移動ではない）。ここが本課題。

### 本実装したいこと
1. **サブプロジェクトへのデータ送り／戻り**: 現プロジェクトのカードをサブプロジェクトへ送る／
   結果を親へ戻す。CAS は内容アドレスなので**実身は複製せず共有**でき、「送り＝仮身（窓）が境界を
   越える＋必要時のみ materialize」という仮身モデルらしい設計が筋（要精査）。
2. **共有ワークフロー連携**: オートフロー（フィルタ／プロセスコントロール）を**プロジェクト境界を
   またいで**走らせる。サブプロジェクトを「再利用可能なワークフロー部品（モジュール）」として呼ぶ
   ——入力フォルダ＝送り／出力フォルダ＝戻りの規約（v1.5 系 AI/MCP 受け入れ口の規約と整合）。
3. **プロジェクト間の関係性の精査（クロスリンク）**: relations が境界をまたぐ場合の意味論。
   リンク先が移動/削除された時の追従・喪失表示（仮身の薄赤＝窓喪失と同系の扱い）。

### 設計上の論点（着手前に詰める）
- 実身の**共有 vs 複製**（CAS は本来グローバル共有可能だが現状はプロジェクトごとに `.texos/cas`。
  共有 CAS にするか、送受信時コピーか）。
- 送り＝**移動か参照（仮身）か**。仮身モデルなら「窓」が境界を越えるだけで実体は動かない。
- **自己完結性／持ち出し単位**（プロジェクト＝配布単位）との両立・セキュリティ。
- 論理グループ（kind='group'）で足りる範囲との切り分け。

→ 位置づけ: **V2.0（サブプロジェクト本実装の中核）**。v1.5 のオートメーション基盤
（プロセスコントロール／ビジュアルコマンド）が固まると、2 の「共有ワークフロー」が自然に乗る。

## 8. 分岐・反復・クラスカード（2026-08-05 追加・v1.7.3 ソーク中の議論からの送り）

v1.7.3 ソーク中に「次に何をやるか（オートメーション強化か機能充実か）」を議論した結果の保留分。
**この回で実施したのは生成系の制限時間バグ修正のみ**（未記入＝0＝無制限の統一）。以下は着手しない。

### 8-1. 確定した設計ライン（保留項目に共通する前提）

- **AI はコントローラではなく「判定器」**。経路（どのカードへ進むか）は人がグラフに描き、
  AI は**どの矢印を通すかだけ**を決める。一般的なエージェント（AI が次の行動を自分で決めて実行）は
  実行経路が AI の中にありグラフに現れないため、TexoS の理念（思考の外部化＝人が見て分かるグラフ）と
  正面衝突する。自律性は「分岐の判定を AI に任せる」までで取り、可視性・再現性・水泡に帰さない設計は崩さない。
- **分岐は push 側（op／req 矢印の世界）に置く**。pull（さかのぼり実行）は分岐と相性が悪い
  （両方の枝を辿ってしまう）。要求駆動（`docs/要求駆動と自律安全設計.md`）とはここで接続する。
- 順序の判断: カードを増やす（機能充実）は後からでもできるが、条件・反復は実行中核
  （pull 解決・ジョブ台帳・ヒューズ・preflight）に触るため、カードが増えるほど整合コストが上がる。

### 8-2. 分岐・ルーターカード（route）— **アイデア整理後に着手**

- `builtin:"route"`: 入力を評価し、出ている複数の req 矢印のうち1本（または複数）を発火する。
- 判定は2段: ①決定的ルール（正規表現・数値比較・JSONパス・空判定）②AI分類
  （分類プロンプト→ラベル→同名の矢印）。①だけでも実用＝AI 無しで動く（軽量配布の理念に合う）。
- 「結果により次に起動する AI カード／命令を選ぶ」という当初の要求は、これで直接満たせる。

### 8-3. 反復カード → サブフロー（畳めるグループ）— **アイデア整理後に着手**

- 反復（until／繰り返し）は**ヒューズ（max_fires 相当）必須**で設計する。暴走対策の作法が既にあるので、
  そこに乗せれば理念的に一貫する。
- 続いて欲しくなる部品: 検証カード（AI 出力が期待形式か判定→失敗なら route で再生成へ戻す＝
  自己修正するフローが人の目に見える形で描ける）、join（並列 AI の待ち合わせ。既存の集約
  cat/paste とは別物＝「揃うまで待つ」）。
- **サブフロー＝複数カードを1枚に畳んで名前を付け再利用する**。v1.6 カード拡張 SDK
  （「新規カードを登録」／カード化プログラム作成規約）と地続き。

### 8-4. クラスカード（データ＋メソッド一体）— **棚上げ（8-3 のサブフロー検討完了後に再考）**

- 提案の骨子: メソッドと変数を持つカードを作り、データと操作を一体にする。
- 懸念（再考時に必ず突き合わせること）: **実身の可搬性が壊れる**。TexoS の核は
  「実身はただのファイルで、TexoS の外でも開ける＝水泡に帰さない」こと。メソッドを抱えた実身は
  TexoS の外で意味を失う。
- 可搬性を壊さずに同じ便益を取る代替: ①サブフロー（＝名前付きメソッド束。データ側を一切触らない）
  ②型（MIME／拡張子）ごとの「よく使うフィルタ」を右クリック候補に出す（＝UI の問題として解く）。
- 判断: サブフローを使い込んでも足りないと感じたときに再検討する。

### 8-5. 今回見送った実装（ウォッチャー調査からの副産物）

ウォッチャーがプロジェクト切替後も動くのではという疑いを調査し、**継承は起きていない**ことを
コードで確認した（再調査不要）。根拠:

- スケジューラ tick は現在のプロジェクトの op カードしか列挙しない（`ops.rs` tick）。別プロジェクトを
  開いている間、元プロジェクトのウォッチャーはフォルダを読みにすら行かない。発火直前にも root 一致を再確認。
- 「新規カードを登録」（import_new）は起動元 root で開き直したジョブ専用接続だけを使う
  （`flow_run.rs` run_flow_inner → open_project_at(root)・state.current 非依存）。切替先の盤面に
  カードが登録されることは起こらない。
- カード id は UUID なので、発火とプロジェクト切替が重なるレースでも切替先で id が解決されることは実質ない。

「切替先でも動いて見える」の**真因は表示**: ジョブ台帳は各ジョブが project_root を持つのに、
`Jobs::list()` が返す `JobInfo` がそれを捨てており、実行中パネルにプロジェクトのフィルタが無い。
起動元で走り続けているジョブ（設計どおり正しい動作）が切替先の画面にも並ぶ。

保留にした対策（いずれも実装しない）:

1. `JobInfo` に project_root を載せ、パネルは現在のプロジェクトのジョブだけを行として表示。
   他プロジェクト分は消さずに「他プロジェクトで実行中 N件」の1行に畳む
   （完全に隠すと Stop-all＝中央 kill の対象が見えなくなり安全設計上まずい）。
2. `dispatch` に起動元 root を持たせ `run_flow_for` で照合（レースの筋を塞ぐ・数行）。

なお「別プロジェクトから戻った直後に留守中の変化でまとめて発火する」挙動は**仕様通りで問題なし**と
確認済み（スケジューラのランタイム状態を切替時にクリアする案は取り下げ。timer の every も同様に現状維持）。
