## 1. なぜこの4枚か（目的の転回・2026-08-08）

ユーザーが目的そのものを言い直した。

- **旧**: 現行 OS の UI への不満 → 同じ悩みを持つ人に配る。
- **新**: AI エージェントが高次の指示だけで運用を担うようになり、「よりよい OS UI」としての
  存在意義は薄れた。代わりに見えたのは、**「〜をどう実現すべきか」への回答を TexoS という
  ビジュアル言語で表現できる**こと＝**人と AI のコミュニケーション記法**としての価値。
  長文ドキュメントより速く伝わる。
- **配布は副産物・忘れてよい**。立ち位置は1970年代の BASIC の手製プログラム＝真のパーソナル
  コンピュータ。方針は「**とりあえず自分のために作る・公開してもよいように作る**」。
  ただし**可読性（エージェントが読める形にすること）は捨てない**。

この転回に対する評価（セッション内で提示・ユーザー同意）:

> 存在意義は薄れたのではなく**軸が移った**。エージェントが強くなるほどボトルネックは
> 「できるか」から「**正しくやったか確かめ、直せるか**」へ移る。チャットは線形・揮発・
> 結論しか見せないのでこの用途に向かない。実際、AI設計審査の設計欠陥2件（枠が溶ける／
> 反証迎合）は**構造化された中間出力をグラフとして読んだから**見つかった。
> よって水泡に帰さない＋CAS＋グラフは**エージェント時代にこそ効く**。
> **帰結**: ファイルマネージャ部分・OS ラッパー部分（V1.1）の相対価値は下がり、
> **グラフ・中間生成物・diff/fork/再実行**の価値が上がる。優先順位はこれに従う。

**4枚の選定基準**: 「記法として何が言えないか」。上ほど安く、下ほど効きが大きい。

| | カード | 何を可能にするか | 状態 |
|---|---|---|---|
| ① | 役割ポート | 意味（誰が何の担当か）が**面から読める** | **実装済** |
| ② | 記録カード | 推論の途中が**残って読める** | **実装済** |
| ③ | 問い合わせカード | 記法が**双方向**になる（会話の構造） | 未着手 |
| ④ | 反復カード | 言える階級が広がる（DAG →有界ループ） | 未着手 |

## 2. ①② 実装済みの内容（`6a79983`・main直・**push はまだ**）

版数は **1.7.4 据え置き**。`release:` ではなく `feat:`。**v1.8.0 のリリース号は4枚揃ってから**
（ユーザーはそれまでローカルで使い込む方針）。コード中のコメントは目標版数 `v1.8` で書いてある。

### ① 役割ポート（矢印 `attrs` の `role:"system"`）

付箋 → AI カードへ「役割」の矢印を引くと、付箋の中身が**システムプロンプト**になる。

- `flow.rs:240` `EdgeAttrs.role`（無し＝従来）
- `flow_run.rs:1012` `role_system` 退避 → `:1123` 抽出して `continue`
  ＝**通常入力に数えない → ファンアウトを起こさない**（束カードが不要）
- `flow_run.rs:1206` 適用は **spec を clone して `system` を差し替えるだけ**
  ＝`execute_node` / `run_ai` は無改造。AI 以外に繋がれたら `report.skipped` で通知
- `when` / `carry` は適用しない（役割は条件分岐の対象でなく直結の配線）
- `objects.rs set_relation_attrs` に `role`（空文字で解除）
- UI: `App.tsx handleFlowRelationClick` に「この矢印が運ぶもの（役割）」／
  `LinkLayer.tsx edgeLabel` に「役割」表示（実機では赤い破線＋ラベルで実行フローと別物に見える）

### ② 記録カード（`builtin:"tap"`）

素通ししつつ、通った中身を固定名で上書き保存＋カード化。

- `flow_run.rs:802` `write_tap_record` ／ `:1227` 分岐
- **集約/ファンアウト判定の手前**で return するので入力は何本でもよい（2本目以降 `_2`）
- 名前＝`prefix`（既定はラベル）、出力先＝`out_dir` があればそこ、無ければ直下
- **罠**: 2回目に `import_file_into` を呼ぶと同じ実体を指すカードが2枚でき
  「同一プロジェクト内に同じ実体を2つの実身として登録しない」（v1.3.9 根幹原則）を破る。
  → `committed_path` 一致の生存カードの `real_id`/`mtime` **だけ差し替える**。
  回帰テスト `flow_run::tap_tests::tap_writes_once_then_overwrites_same_card`

## 3. ③ 問い合わせカード（途中で人に聞く）— 未着手

**何のためか**: いま人が介入できるのは**前（付箋を書く）か後（出力を読む）だけ**で、途中がない。
「ここで私に聞け」をグラフ上に置けると、**バッチ処理からコミュニケーションの構造へ変わる**。
§1 の「人と AI の共通の記法」を一番直接に満たすのはこれ。

### 前例（ゼロから作らない）

- **ドロップポイント**（`real_id` が `drop:` で始まるカード）＝「人のファイル投入待ち」。
  未投入なら `flow_run.rs` の入力収集で **`report.skipped` に入れて continue**（no-data にはしない）。
  問い合わせカードはこの**「問い版」**にあたる。
- **ジョブへの流し込み**＝`proc.rs:19 flow_send_stdin(job_id, text)` と `lib.rs:89 AppState.control`
  （`StdinSlot`）。**実行中のジョブへ外から文字列を送る口が既にある**（録音停止の 'q'）。
  「答えを流し込む」はこの形の再利用で作れる。
- ジョブ台帳は v1.5.2 WS-C で**ジョブごとに専用 DB 接続＋並行実行**になっている
  ＝1本のジョブを待たせても他は動く。

### 設計の分かれ目（ここを最初にユーザーと決める）

- **案A: 止めて待つ**（真の対話）。eval の途中でジョブが問い合わせイベントを出し、
  答えが来るまでブロック。`job.control` と同型の「答えスロット」を1本足す。
  - 長所: グラフに描いたとおりに会話が流れる。中断（`job.cancel`）も既存機構で効く。
  - 短所: ジョブが1本占有される（並行化済みなので致命的ではない）。
    アプリを閉じたら待ちは消える＝**答えを永続化するかどうかの判断が要る**。
- **案B: 止めない**（no-data ＋ 答えをカードに保存 → 人が答えてから再実行）。
  ドロップポイントと完全に同じ流儀。実装は最小。
  - 長所: 既存の pull／no-data 機構にそのまま乗る。実装がほぼタダ。
  - 短所: 「会話」にならない。1往復ごとに人が ▶ を押し直す。
- **案C: 両方**（既定は A、未応答のまま閉じたら B に劣化＝答えは `virtual_bodies` に残す）。

**私（前セッション）の推奨**: **案C を目標に、まず案B で骨を通す**。
理由＝答えをカードに永続化する仕組み（B）は A でも必要になる（水泡に帰さない設計と整合）。
B が動けば A は「待つかどうか」の差だけになる。逆順だと永続化を後付けすることになる。

### 決めるべきこと

1. 答えの保存先: 付箋（`note_text`）に書き戻す／`filter_ref` に持つ／専用列。
   **付箋に書き戻す案が有力**（面から読める＝①②と同じ思想。履歴も残る）。
2. 質問文の置き場: カードの `prefix`/`note` か、上流の付箋を質問文として受けるか
   （後者なら**役割ポートの再利用**＝`role:"question"` が素直）。
3. 待ちの UI: 背景ジョブパネル（v1.5.2）に「応答待ち」行を出して、そこで答えるか、
   カード自身がキャンバス上で入力欄になるか。**後者のほうが記法として一貫する**。
4. `preflight`／ヒューズとの関係: 応答待ちのジョブがタイマ・ウォッチャで積み上がらないか。

## 4. ④ 反復カード（収束するまで回す）— 未着手

**何のためか**: 判定 → 反証 → **修正して再判定**。実際の熟考もエージェントの仕事も反復する。
いま矢印の循環は `flow_run.rs:894` `visited.insert` でエラーになるので、
この記法では「練り直す」が**そもそも言えない**。4枚の中で唯一**言語の表現力の階級を変える**。

### 既存議論（`docs/V2.0課題.md §8`）— 必ず読むこと

- **§8-1（制約・最重要）**:
  - **AI はコントローラではなく「判定器」**。経路は人がグラフに描き、AI は
    **どの矢印を通すかだけ**決める。AI が次の行動を自分で決める一般的エージェントは
    実行経路がグラフに現れず、思考の外部化と正面衝突するので採らない。
  - **分岐は push 側（op／req 矢印）に置く。pull（さかのぼり実行）は分岐と相性が悪い**
    （両方の枝を辿ってしまう）。
  - 条件・反復は実行中核（pull 解決・ジョブ台帳・ヒューズ・preflight）に触るので、
    **カードが増えるほど整合コストが上がる**＝先にやるべき、という順序判断。
- **§8-2 ルーターカード（`builtin:"route"`）**: 判定は2段＝①決定的ルール（正規表現・数値比較・
  JSONパス・空判定）②AI 分類。①だけでも動く＝AI 無しで実用（軽量配布の理念）。
- **§8-3 反復**: **ヒューズ（`max_fires` 相当）必須**。続いて欲しくなる部品＝
  検証カード（出力が期待形式か判定→失敗なら戻す＝自己修正が目に見える）、
  join（並列 AI の待ち合わせ。集約 cat/paste とは別物＝「揃うまで待つ」）。
  **サブフロー＝複数カードを1枚に畳んで名前を付け再利用**（v1.6 カード SDK と地続き）。

### 設計の分かれ目

- **案A: グラフに循環を許す**。`visited` を「世代付き」にして有界ループを認める。
  - 短所: pull 解決の中核を触る。§8-1 の「pull は分岐と相性が悪い」に正面から当たる。
- **案B: 循環を許さず「反復＝上流の再評価」にする**（DAG を保つ）。
  反復カードが自分の上流サブグラフを、**メモ（`EvalMemo`）を消しながら N 回引き直す**。
  前回の結果を次の周に渡す口（フィードバックスロット）が要る。
  - 長所: 循環判定・pull 中核に触らない。ヒューズは反復カードの中で完結。
    停止判定も反復カードの内部制御であって「グラフの分岐」ではない＝§8-1 と衝突しない。
  - 短所: 「前回の結果」の注入口という新概念が要る。ただしこれは**役割ポートと同型**
    （`role:"previous"` で前周の出力を差し込む、等）＝①の機構が再利用できる。

**私（前セッション）の推奨**: **案B**。理由＝§8-1 が pull での分岐を避ける方針を既に確定させており、
案A はその方針に逆らう。案B なら反復は「1枚のカードの内部実装」に閉じ込められ、
グラフは DAG のまま＝可視性・再現性が崩れない。

### 決めるべきこと

1. 停止条件の表現: 回数上限のみ／テキスト一致・正規表現／AI 判定（§8-2 の route と同じ2段構え）。
   **§8-2 の判定器をそのまま停止判定に使えるはず**＝route と反復を**同じ判定機構**で作れるか検討。
2. 前周の結果の注入方法（上記 `role:"previous"` 案）。
3. **記録カードとの相互作用（重要）**: いま tap は固定名上書きなので、反復すると各周が消える。
   反復の中に tap を置いたら `_1, _2, _3` と周回番号を付けたい。
   → tap に「反復中は連番」の挙動を足すか、周回番号を実行文脈として渡すか。
4. ヒューズの置き場: 既存のタイマ／ウォッチャの `max_fires` と同じ流儀に揃える。
5. 中断（`job.cancel`）が反復の途中で確実に効くこと（AI を何周も回すので必須）。

## 5. 作業の作法（前セッションで踏んだ失敗を含む）

- **★ Rust を触ったら、動作確認を頼む前に必ずビルドする。**
  前セッションで `cargo test` と `tsc` だけ通して「実機で確認してください」と依頼し、
  ユーザーは**変更前のバイナリ**で実行して `未知の内蔵フィルタ: tap` に当たった。
  - リリース exe: `npm run tauri build -- --no-bundle` → `src-tauri/target/release/texos.exe`
    （**起動中はロックされるので要終了**。デスクトップショートカットはここを指す）
  - dev で見るなら `npm run tauri dev`（`target/debug/texos.exe` ＋ vite:1420）
  - **診断のコツ**: エラー文字列がソースのどこにしか無いかを grep すれば
    「実装漏れ」か「古いバイナリ」かが一発で切り分けられる
    （`未知の内蔵フィルタ` は `flow.rs run_builtin` にしかなく、新コードなら到達しない経路だった）
- **組んだだけで納品しない。1周流して出力を読む。** プロンプト設計の欠陥は静的には見えない
  （枠が溶ける／反証迎合はどちらも実走で初めて出た）。
- DB を外から組むときは **TexoS を終了してから**（起動中に書いても UI に反映されない）。
- コミットは main 直・件名にプレフィクス（`feat:` / `fix:` / `docs:` / `release: vX.Y.Z`）。
  リリース時は版数3か所（package.json / tauri.conf.json / Cargo.toml）＋Cargo.lock。

### 多視点グラフの設計則（実走で判明・規約 §4 に記載）

1. 並行（横）は**別コンテキストでなければ意味がない**。1プロンプトで「4つの視点で」と頼むと
   同じ文脈で条件づけられて必ず収束する。配線の問題であってモデルの賢さの問題ではない。
2. 束カードは邪魔者でなく**「何を材料にしたか」の記録**になる。
3. **枠は持ち回る**。前提を固定する段と消費する段が離れると途中で溶ける（実測で最終段が
   確定済みの前提を「未決定」と言い出した）。→ 下流の束の1本目に常に前提を入れる。
4. **迎合対策を入れると反対側へ迎合する**（反証を全件「認めた」）。中間段の処理を2値にせず
   「認めた（結論を変える）／認めた（条件に反映）／退けた」の3値にし、全件認容なら自己申告させる。
5. 確信度は**理由を要求しないと演出になる**。
6. 実測: Ollama `gemma4:latest`（8B）で AI カード1枚 13〜23秒／7段で約120秒（ロード済み）。
