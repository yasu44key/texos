## 1. なぜこの4枚か（目的の転回・2026-08-08）

ユーザーが目的そのものを言い直した。

- **旧**: 現行 OS の UI への不満 → 同じ悩みを持つ人に配る。
- **新**: AI エージェントが高次の指示だけで運用を担うようになり、「よりよい OS UI」としての
  存在意義は薄れた。代わりに見えたのは、**「〜をどう実現すべきか」への回答を TexoS という
  ビジュアル言語で表現できる**こと＝**人と AI のコミュニケーション記法**としての価値。
  長文ドキュメントより速く伝わる。
- **配布は副産物・忘れてよい**。立ち位置は1970年代の BASIC の手製プログラム＝真のパーソナル
  コンピュータ。方針は「**とりあえず自分のために作る・公開してもよいように作る**」。
  ただし**可読性（エージェントが読める形にすること）は捨てない**。

この転回に対する評価（セッション内で提示・ユーザー同意）:

> 存在意義は薄れたのではなく**軸が移った**。エージェントが強くなるほどボトルネックは
> 「できるか」から「**正しくやったか確かめ、直せるか**」へ移る。チャットは線形・揮発・
> 結論しか見せないのでこの用途に向かない。実際、AI設計審査の設計欠陥2件（枠が溶ける／
> 反証迎合）は**構造化された中間出力をグラフとして読んだから**見つかった。
> よって水泡に帰さない＋CAS＋グラフは**エージェント時代にこそ効く**。
> **帰結**: ファイルマネージャ部分・OS ラッパー部分（V1.1）の相対価値は下がり、
> **グラフ・中間生成物・diff/fork/再実行**の価値が上がる。優先順位はこれに従う。

**4枚の選定基準**: 「記法として何が言えないか」。上ほど安く、下ほど効きが大きい。

| | カード | 何を可能にするか | 状態 |
|---|---|---|---|
| ① | 役割ポート | 意味（誰が何の担当か）が**面から読める** | **実装済** |
| ② | 記録カード | 推論の途中が**残って読める** | **実装済** |
| ③ | 問い合わせカード | 記法が**双方向**になる（会話の構造） | **実装済** |
| ④ | 反復カード | 言える階級が広がる（DAG →有界ループ） | **実装済** |

**着手順を③④で入れ替えた（2026-08-08・ユーザー判断）**。理由は `V2.0課題.md §8-1` の順序判断＝
条件・反復は実行中核（pull 解決・ジョブ台帳・ヒューズ・preflight）に触るので、カードが増えるほど
整合コストが上がる。③は既存機構（ドロップポイント／`flow_send_stdin`）の再利用でほぼ独立に足せる。
上の表の並びは「記法としての効きの大きさ」順であって、実装コスト順ではない。

## 3. ③ 問い合わせカード（途中で人に聞く）— **実装済（v1.8・案B）**

**何のためか**: いま人が介入できるのは**前（付箋を書く）か後（出力を読む）だけ**で、途中がない。
「ここで私に聞け」をグラフ上に置けると、**バッチ処理からコミュニケーションの構造へ変わる**。
§1 の「人と AI の共通の記法」を一番直接に満たすのはこれ。

### 決めたこと（2026-08-08・ユーザー判断）

**案C（止めて待つ＋永続化）を目標に、まず案B（止めない）で骨を通す**。
答えをカードに永続化する仕組みは案A でも必要になるので、逆順だと後付けになる。

### 実装（`builtin:"ask"`）

**ドロップポイントの「問い版」**。あちらが人のファイル投入待ち、こちらが人の言葉待ち。
実装もその流儀に揃えた（未回答なら no-data・エラーにしない・eval 側で完結）。

- **答えの置き場＝付箋**（§3「決めるべきこと」1 の有力案を採用）。`role:"answer"` の矢印で
  問い合わせカードに繋いだ付箋の中身が答えになる。①役割ポートの機構をそのまま再利用。
  付箋にしたのは、答えが**面から読めて・その場で直せて・プロジェクトに残る**から。
- **答え箱は勝手に用意する**。未回答で付箋も無いときは、**付箋を作って矢印まで引く**
  （`create_answer_note`）。「答えてください」と言われても書く場所が無い、を起こさないため。
- **付箋の中身は全部 `>` の引用**（質問＋そのとき届いていた材料・40行/1200字で打ち切り）。
  引用行は答えとして読まない（`flow::answer_text`）。**素の行を1行でも書くと、誰も答えて
  いないのにフローが先へ進む**ので、ここは回帰テストで固定した。
  材料まで書き写すのは**人が何を見て答えたかを残す**ため（答えだけ残っても後から読めない）。
  作るのは1回だけで、以後この付箋には触らない（人の答えを消さない）。
- 出力＝**答えの文字列だけ**（text/plain・名前は `prefix` かカード名）。材料も一緒に下流へ
  渡したいときは連結カードで束ねる（束は「何を材料にしたか」の記録になる＝規約 §4-2）。
- 通常入力は**質問の文脈**。無くてもよい（`preflight` の「入力0」検査から除外）。
- 質問文は spec の `question`（未設定ならカード名）。
- UI: 制御メニューに「問い合わせ（途中で人に聞く）」／矢印メニューに「役割＝答え」／
  矢印ラベルに「答え」／設定フォーム（聞くこと・出力名）。

### 案B の性質（承知のうえで残した制限）

**再実行では上流も走り直す**。AI の出力について聞いた場合、2回目に出てくる案は人が読んだ案と
違うことがある。緩和として、聞く手前に記録カードを置いて読んだ案を残す
（`scripts/build_ask_demo.py` がその形）。**根治は案C**＝ジョブを止めて待てば、
答えたときの上流の値がそのまま生きる。答えの永続化は済んでいるので、案C は
「待つかどうか」の差だけで足せる。

### 検証状況

`cargo test --lib` **122 passed**（③の新規4件: 引用の落とし方・未回答で止まり付箋ができる・
付箋を増やさない・材料の引用が答えに化けない）。確認用プロジェクト
`F:\yoshi\Documents\TexoS\カード実験_問い合わせ`（`scripts/build_ask_demo.py`）。
見るところ: ①1回目は「答え待ち」で止まる（エラーではない）②答えの付箋が現れ、質問と
下書きが引用で入っている ③付箋に答えを書いて2回目で `決定稿1.md` ができる
④答えが空のあいだは何度実行しても進まない。

## 4. ④ 反復カード（収束するまで回す）— **実装済（v1.8・案B）**

**何のためか**: 判定 → 反証 → **修正して再判定**。実際の熟考もエージェントの仕事も反復する。
矢印の循環は `flow_run.rs` の `visited.insert` でエラーになるので、この記法では
「練り直す」が**そもそも言えなかった**。4枚の中で唯一**言語の表現力の階級を変える**。

### 決めたこと（2026-08-08・ユーザー判断）

**案B（循環を許さず DAG を保つ）を採用**。`V2.0課題.md §8-1` が pull での分岐を避ける方針を
既に確定させており、案A（`visited` を世代付きにして循環を許す）はそれに逆らう。案B なら
反復は「1枚のカードの内部実装」に閉じ込められ、グラフは DAG のまま＝可視性・再現性が崩れない。

### 実装（`builtin:"loop"`）

**要は、前周の値を「エッジ」ではなく「実行文脈」に置いたこと**。これで戻り矢印は
グラフに描けるのに評価では遡らない線になり、循環判定にも pull 解決の中核にも触らずに済む。

- `flow_run.rs LoopCtx` — ジョブ内で持ち回る揮発文脈。`prev`（反復カード id → 前周の出力）と
  `rounds`（入れ子の周回番号）。**反復の外では空**＝従来の評価に一切影響しない。
- `flow_run.rs collect_input_edges` — フェーズ1（入力収集）を eval_filter から切り出した。
  反復カードが**同じ収集を周ごとに呼ぶ**ため。切り出しで挙動は変えていない。
- `flow_run.rs run_loop_node` — 周と周のあいだにやることは2つだけ:
  ①上流サブグラフのメモを消す（消さないと同じ結果が配られて2周目が実行されない）
  ②前周の出力を `ctx.prev` へ置く。
- **戻り矢印**＝`attrs {"role":"previous"}`（反復カード → 上流のどれか）。
  `collect_input_edges` は**上流を評価せず** `ctx.prev` を引く。**1周目は空**を運ぶ
  （no-data にすると伝搬型の下流が丸ごと止まり、1周目が実行されずに反復が始まらない）。
  役割つきでも `role:"system"` と違い**入力には数える**（材料だから。戻し先は束カードにする）。
- **ヒューズ**（§8-3 必須要件）＝`max_rounds`（未指定3・`flow::LOOP_MAX_ROUNDS=50` に丸める）。
- **停止条件**＝`until`＋`pattern`。判定は `flow::judge_text`（`contains` / `not_contains` /
  `regex` / `not_regex` / `empty` / `not_empty`）で、**spec にもノードにも依存しない純関数**。
  §8-2 のルーターカードの枝選択にそのまま使える形にしてある＝**route と反復が同じ判定機構**。
  未知のモード・不正な正規表現は**エラーにする**（false を返すと「止まらない反復」になり、
  しかも原因が画面のどこにも出ない）。
- **記録カードとの相互作用**（宿題だった件）: `write_tap_record` に `round_suffix` を追加。
  反復の中では `各周_1.md` `各周_2.md` …（入れ子なら `_2_3`）。外では従来どおり固定名。
- `preflight.rs collect` — 戻り矢印を到達グラフに入れない。入れると反復が毎回
  「データ循環」エラーとして報告されるが、実行は DAG のままで循環していない。
- `scripts/texos_flow.py` — `loop()` と `flow(…, role="previous")`。ビルダーの循環検出も
  戻り矢印を辿らない。**反復カード以外から戻り矢印を引いたら例外**（間違えると前周が永遠に
  空のまま静かに回り続け、気づけない失敗になる）。戻り矢印の無い反復カードは警告。
- UI: 右クリック→制御→「反復（納得するまで繰り返す）」（周回数→停止語の2段プロンプト）／
  矢印メニューに「役割＝前周の結果（反復の戻り）」／矢印ラベルに「前周」。

### 検証状況

`cargo test --lib` **118 passed**（新規6件: `judge_text` の全モード・ヒューズの丸め・
周回接尾辞・停止判定・引き直す範囲が戻り矢印を辿らないこと・記録カードの周ごと命名）

- **`カード実験_役割と記録`** — ①②の動作確認用。
- **`カード実験_問い合わせ`** — ③の動作確認用（`scripts/build_ask_demo.py`）。
  下書き(AI)→問い合わせ→束→仕上げ(AI)。1回目は答え待ちで止まり、付箋に書いて2回目で通る。
- **`カード実験_反復`** — ④の動作確認用（`scripts/build_loop_demo.py` で再生成できる）。
  お題→束→AI推敲→記録→反復、＋反復→束の戻り矢印。**実機で1周流すのはこれから**。

### 多視点グラフの設計則（実走で判明・規約 §4 に記載）

1. 並行（横）は**別コンテキストでなければ意味がない**。1プロンプトで「4つの視点で」と頼むと
   同じ文脈で条件づけられて必ず収束する。配線の問題であってモデルの賢さの問題ではない。
2. 束カードは邪魔者でなく**「何を材料にしたか」の記録**になる。
3. **枠は持ち回る**。前提を固定する段と消費する段が離れると途中で溶ける（実測で最終段が
   確定済みの前提を「未決定」と言い出した）。→ 下流の束の1本目に常に前提を入れる。
4. **迎合対策を入れると反対側へ迎合する**（反証を全件「認めた」）。中間段の処理を2値にせず
   「認めた（結論を変える）／認めた（条件に反映）／退けた」の3値にし、全件認容なら自己申告させる。
5. 確信度は**理由を要求しないと演出になる**。
6. 実測: Ollama `gemma4:latest`（8B）で AI カード1枚 13〜23秒／7段で約120秒（ロード済み）。
