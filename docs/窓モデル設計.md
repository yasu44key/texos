# 窓モデル設計（v1.3.10〜）— 仮身はカードIDで実身を指す

最終更新: 2026-06-21 / ステータス: **設計確定・実装中（v1.3.10）**

## 目的（ユーザーの言葉）

実身/仮身の仕組みで**プロジェクト内ファイル管理を拡張**する。ユーザーが従来どおり
自由にプロジェクトフォルダを扱って（リネーム・フォルダ分け・移動・削除）も、TexoS
キャンバスが維持される。「TexoS から見ると混乱」な状態でも、カードの関係性は壊れない。

## 背景（なぜ作り直すか）

これまでの窓解決は **real_id（内容ハッシュ）一致** と **パス一致** に依存していた。
- 内容が同じ実身は CAS ハッシュが衝突し real_id を共有 → 仮身が複製元でない別カードに追従。
- 複製元の実ファイルがリネームされると、記録した旧パスと一致しなくなり外れる。
- 実体喪失でも real_id 共有の別カードや CAS に黙って落ち、赤くならない。

根本原因は「**窓の対象を内容やパスで当てている**」こと。窓は**カード同士の関係**であり、
内容でもパスでもなく**相手の実身カードを ID（不変）で指す**べき。

## いちばん簡単な原理（これだけ）

1. **1つの実ファイル = 1枚の実身カード**（重複実身の防止＝v1.3.9 問題点1で担保）。
   実身カードは**安定したカードID**を持つ。編集で中身が変わっても、リネームでパスが
   変わっても、**同じ実身カード**であり続ける。
2. **内部の仮身 = その実身カードを `window_of`（カードID・不変）で指すポインタ**。
3. **表示の解決ルール（全カード共通）**:
   - 自分が実ファイルを持つ（実身）→ それを読む
   - `window_of` がある（内部仮身）→ 指し先カードの**生きた実ファイル**を辿る
     - あれば読む（リネーム・編集に自動追従）
     - 無ければ**赤シグナル**（CAS は保険のみ。real_id 兄弟解決には落とさない）
   - それ以外（外部・旧データ）→ **従来どおり**（②real_id兄弟→③origin_path→④CAS→⑤fork）
4. **CAS = 保険＋タイムマシンだけ**。live の表示経路には使わない。「CASから復元」と
   force 再コミットのときだけ CAS を読む。
5. **シグナル = 辿った先に生きた実体があるか**。実身も仮身も同じ規則。

## 内部レーン / 外部レーンの分離（過去の資産を凍結）

| | 内部の仮身（新モデル） | 外部ファイルの仮身（凍結・1.3.9以前のまま） |
|---|---|---|
| 参照の持ち方 | `window_of`（実身カードID） | `origin_path`（外部パス） |
| 解決 | カードIDを辿る → 生きた実体 / 赤 | origin_path → CAS → 実ファイル作成 |
| リンク切れ | 赤・カードIDは不変なので再リンクで復活 | 赤・CAS参照・materialize（従来どおり） |

**1枚のカードでは排他**（内部=window_of / 外部=origin_path）。だから干渉しない。

## 実装方針（追加だけ・既存に触れない）

`resolve_view_conn` は **②③④⑤の既存コードに一切手を入れず**、①の直後に内部レーンを
1段足すだけ:

```
① 自分が committed 実ファイルを持つ → それを読む          … 既存のまま
★ window_of がある（内部仮身）→
      resolve_live_file(window_of) で「生きた実ファイル」だけを辿る
        あれば → 返す（"window"）
        無ければ → CAS（赤）/ none（赤）。②へは落とさない
② real_id 兄弟解決                                        … 既存のまま（旧データ用）
③ origin_path（外部ファイル）                              … 既存のまま・凍結
④ CAS                                                     … 既存のまま
⑤ フォーク                                                … 既存のまま
```

`resolve_live_file(vid)`: その仮身チェーンの「own committed が実在する実ファイル」だけを
返す（CAS・origin・real_id兄弟には落ちない）。無ければ None。

`window_of` を持たないカード（外部・旧データ）は新ルートに入らず、**従来と完全に同じ経路**
を通る。＝過去の資産（外部ファイルの取り扱い）に指一本触れない。

## window_of を記録する箇所

- **duplicate_virtual（仮身を作成）**: 複製元が
  - 内部仮身（window_of あり）→ その window_of を継承（チェーンの根＝実身を指す）
  - 内部実身（committed_path あり）→ window_of = 複製元カードの id
  - 外部仮身（origin_path のみ）→ 従来どおり origin_path を複製（window_of なし）
- **import_file の重複登録（問題点1）**: 2枚目以降の内部仮身は window_of = 既存実身カードの id。

## TexoS内リネームとセット（同じ刻みで）

OS でリネームすると committed_path がずれて毎回赤になるので、**TexoS内リネーム**を用意する:
実ファイル改名＋committed_path 更新（カードIDは不変）→ 仮身は全部自動追従。連番ファイル名
（FILE(1)(2)）の付け替え問題もこれで解決。

## 正規化コマンド（将来・このモデルの上で）

ユーザーが自由に整理した結果を TexoS が吸収する:
- サブフォルダに移動されたファイルを探して再リンク
- 改名されたファイルはユーザーに指定を促す（再リンク）
- 消えたファイルは CAS から復活
これらは「赤シグナル＝実体喪失」のカードを対象に、再リンク／CAS復元を一括で回す。

## 移行（既存データ）

`window_of` 未記録の旧仮身は、原理的に複製元を復元できない → 従来ヒューリスティック
（real_id/パス）にフォールバック据え置き。新規に作り直せば正しくなる。best-effort ALTER で
列追加、既存行は NULL。
